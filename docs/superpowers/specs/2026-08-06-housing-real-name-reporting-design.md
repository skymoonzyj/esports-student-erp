# 房态实名入住导出与人工报送设计

- **日期：** 2026-08-06
- **状态：** 设计已逐段确认，待实施计划
- **所属阶段：** 阶段 3 房态第三实施单元
- **上游规格：** `2026-08-03-housing-room-status-design.md`

## 1. 背景与目标

房间目录、房态基础、入住生命周期、调房、退房、问题房和本人/家庭住宿门户已经在本地实现。第三实施
单元补齐内部运营需要的实名入住名单、人工报送状态、敏感权限、完整审计和响应式后台页面。

本单元完成后，超级管理员或被明确授予敏感权限的工作人员可以：

1. 按时间范围、楼栋、楼层、营期和人员类型生成实名入住批次。
2. 同时下载内容一致的 Excel 和 CSV 版本。
3. 重新下载历史批次，且内容不受后续人员或住宿资料变化影响。
4. 标记已经人工报送，并在发现错误时作废原批次、创建关联的更正批次。
5. 在不泄露实名内容到页面、日志或审计元数据的前提下追溯每次敏感操作。

ERP PostgreSQL 继续作为唯一业务主记录。文件只在获权下载请求中即时生成，不长期保存在公开目录或本地
文件系统。未来公安在线 API 只消费本规格定义的版本化报送快照，不绕过 ERP 直接读取内部业务表。

本聚焦规格对上游房态规格第 5.7、13、14.3、15 和 17 节中的第三实施单元要求作细化，并正式把
`voided` 和更正链加入报送批次状态。其他房态、入住和延期边界继续沿用上游规格。

## 2. 范围

### 2.1 本单元包含

- 实名报送批次、不可变加密快照、状态机和更正链。
- 时间、住宿范围、营期和人员类型筛选。
- 入住人员与未成年监护人两张规范化逻辑表。
- Excel 工作簿与 CSV 压缩包即时生成和历史重下载。
- 人工报送时间、备注、作废原因和更正关联。
- `housing.reports.export_sensitive` 敏感权限及楼栋/楼层对象范围。
- 生成、下载、报送、作废、更正、拒绝和失败审计。
- Windows、macOS、平板和手机共用的响应式后台页面。
- 本地 PostgreSQL、后端、Web 和四视口浏览器自动化门禁。

### 2.2 明确延期

- 当地公安住宿系统在线 API 及其厂商适配器。
- Docker Compose、镜像、NAS 部署、生产备份恢复和容器验收。
- 生产密钥托管、生产监控和灾难恢复演练。
- 评价录像、GPU、OCR、自助报名支付和天赋测评。

全部 ERP 业务项目开发完成后再统一进行 Docker/NAS 专项。本单元不得修改容器部署状态，也不得把本地
测试通过描述为生产可用。

## 3. 已确认的核心规则

1. 时间范围采用半开区间 `[开始时间, 结束时间)`；住宿记录与该范围有任何重叠即纳入。
2. 只纳入已经确认实际入住的住宿记录；未确认入住的预约和已取消预约不进入实名报送名单。
3. 同一人员在范围内调房时，每个房间住宿时段分别形成一行，以完整还原调房历史。
4. 未成年学员存在多名有效监护人时，全部有效监护人都进入导出。
5. 同一批次同时提供 Excel 和 CSV 两个下载入口，两种格式来自同一不可变快照。
6. 获权人员可以重新下载历史批次；每次下载重新鉴权并记录审计。
7. 已人工报送的错误批次不能覆盖。必须作废原批次、填写原因，再生成关联的更正批次。
8. 文件不长期保存；版本化、加密、不可变的业务快照长期保存在 PostgreSQL。

## 4. 时间与筛选语义

所有用户输入和页面展示使用 `Asia/Shanghai`。API 使用带时区时间戳，数据库保存绝对时间。

### 4.1 时间范围

请求必须提供 `range_start` 和 `range_end`，且 `range_start < range_end`。住宿时段与请求范围重叠的判定为：

```text
actual_check_in_at < range_end
AND effective_actual_check_out_at > range_start
```

尚未完成二次确认退房的记录把结束时间视为正无穷。`checkout_pending` 中的
`checkout_requested_actual_at` 只是待管理员核对的离开时间，不是权威 `actual_check_out_at`，不能提前截断
实名住宿范围；导出行显示待确认状态。管理员二次确认后才使用 `actual_check_out_at` 判断实际住宿重叠。
调房边界使用旧住宿的实际结束时间和新住宿的实际开始时间，半开区间保证边界时刻不会重复计算同一房间。

### 4.2 住宿范围

生成请求必须明确选择以下一种范围：

- 全部获权范围；
- 一个或多个获权楼栋；
- 一个或多个获权楼层。

“全部获权范围”由服务端展开为明确的获权楼层集合并固化到批次。请求包含任何未授权范围时整批拒绝，
不得静默删除无权房间。

### 4.3 可选业务筛选

- `cohort_ids`：一个或多个营期；为空表示不限制营期。
- `person_types`：学员、教练、生活老师、客服、行政、其他工作人员或临时访客；为空表示全部人员类型。
  “助教”是教学任务中的分配角色，不是独立人员档案类型，因此助教按其人员中心登记的工作人员类型归类，
  不因某一期教学分配临时改变实名报送人员类型。

筛选后的结果为空时不创建成功快照，返回 `housing_report_empty` 并保存不含实名数据的失败批次和安全
审计。导出用途 `purpose` 必填，并限制长度；用途用于批次业务记录，不复制进审计元数据。

## 5. 架构与组件边界

在现有 `app.housing` 领域内增加独立报送子模块，避免把敏感导出逻辑继续堆入目录或入住服务。

### 5.1 `reporting_projection`

- 在 PostgreSQL 一致性快照中读取实际住宿、房间、人员、营期和监护关系。
- 应用筛选并生成版本化、规范化的报送投影。
- 执行全部完整性校验；不负责 HTTP、文件格式或状态转换。

### 5.2 `reporting_snapshot`

- 把规范化投影序列化为确定性的规范 JSON。
- 使用现有应用层敏感字段加密基础设施加密，并记录密钥版本。
- 保存密文摘要和投影模式版本；负责解密、完整性校验和版本路由。

### 5.3 `reporting_renderer`

- 只接收已经解密并校验的版本化投影。
- 分别生成 Excel 字节和 CSV 压缩包字节。
- 不查询业务表、不写文件系统、不改变批次状态。

### 5.4 `reporting_service`

- 编排生成、列表、详情、下载、标记报送、作废和更正。
- 负责状态机、并发控制、事务、权限范围和审计。
- 下载时先生成完整内存结果并成功写入审计，再返回附件响应。

### 5.5 `reporting_router`

- 使用现有房态私有路由和统一问题响应。
- 只做输入解析、认证上下文、调用服务及响应头，不复制业务校验。

未来公安 API 适配器只能依赖版本化投影接口，不依赖 ORM 内部模型。

## 6. 数据模型

### 6.1 `housing_report_batches`

批次至少保存：

- `id`：稳定 UUID。
- `batch_number`：面向运营展示的唯一批次编号，不包含姓名等个人信息；使用数据库序列生成唯一后缀，
  禁止通过 `MAX + 1` 计算并发编号。
- `status`：`generated`、`marked_submitted`、`voided` 或 `failed`。
- `version`：状态修改的乐观并发版本。
- `range_start`、`range_end`。
- `cohort_filter`、`person_type_filter`。
- `purpose`。
- `projection_schema_version`。
- `snapshot_ciphertext`、`snapshot_key_version`、`snapshot_digest`；失败批次均为空。首版密钥版本固定为 `1`
  并使用现有字段加密主密钥；生产密钥轮换和密钥环在 Docker/NAS 专项中验收，但数据库字段和投影接口
  现在就保留版本边界。
- `resident_count`、`stay_row_count`、`guardian_row_count`。
- `created_at`、`created_by_user_id`。
- `submitted_at`、`submitted_by_user_id`、`submission_note`。
- `voided_at`、`voided_by_user_id`、`void_reason`。
- `corrects_batch_id`：可空自引用，形成不可变更正链。
- `failure_code`、`failure_summary`：只保存安全代码和数量，不保存逐人员实名资料。

批次不可删除。成功批次的加密快照、筛选、计数和创建者不可更新；只有状态相关字段可以通过规定动作
改变。数据库约束保证状态所需字段成组出现，例如 `marked_submitted` 必须有报送时间和操作人，`voided`
必须有作废时间、操作人和原因，`failed` 不得有快照密文。

### 6.2 `housing_report_batch_scopes`

每行保存批次实际包含的一个规范化楼层范围：

- `batch_id`
- `building_id`
- `floor_id`

同一批次的楼层不能重复。整栋请求在服务端展开为该楼栋全部实际包含楼层；“全部获权范围”展开为请求
时逐楼层授权检查后得到的明确楼层集合。用户显式选择整栋但其中任一楼层被拒绝时整批拒绝，不能把该
楼层静默删掉。逐楼层固化使后续下载能够重新应用楼栋允许、楼层允许和楼层显式拒绝，不依赖 JSON 字段
进行安全判定。

### 6.3 更正链约束

- 只有已作废批次可以成为 `corrects_batch_id`。
- 新批次必须重新读取当前业务数据、重新校验并形成新快照，不能复制后修改旧快照。
- 一次更正只指向直接前驱；再次更正指向最近被作废的批次，页面展示完整链。
- 数据库和服务层共同阻止自引用与环。

## 7. 报送投影

投影模式版本 1 包含两个逻辑集合。

### 7.1 `residents`

每个实际住宿/调房时段一行，字段包括：

- `row_id`：批次内稳定、不可推断个人身份的行编号。
- 人员内部稳定 ID、姓名、手机号、身份证、性别、出生日期、人员类型。
- 楼栋、楼层、房号及对应稳定 ID。
- 住宿用途：常住、随营或临时。
- 实际入住时间、实际退房时间和住宿状态。
- 营期名称及稳定 ID；无营期时为空。
- 临时访客来访原因；非临时访客为空。
- `is_minor_at_check_in` 和监护人行数。

`resident_count` 按去重人员计算，`stay_row_count` 按住宿时段行计算。调房会增加住宿行，但不会重复增加
人员数。

### 7.2 `guardians`

每位有效监护人一行：

- `resident_row_id`：关联对应住宿行。
- 学员稳定 ID 和姓名。
- 监护人稳定 ID、姓名、手机号和身份证。

是否未成年以住宿行的实际入住时间转换到 `Asia/Shanghai` 后的当地日期计算。未满 18 周岁的学员必须
存在至少一名在该参考时刻
有效的成年监护人；所有当时有效监护人都必须写入。“有效”要求参考日期落在 `valid_from` 至
`valid_until`（含首尾）内，并且关系尚未结束，或 `ended_at` 晚于该实际入住时刻。任一有效监护人的必填
实名字段缺失，也会导致整批失败。成年学员即使仍保留监护关系，也不在实名报送的未成年监护人表中重复
导出。

### 7.3 完整性校验
全部住户必须具备姓名、手机号、身份证、性别、出生日期和明确人员类型。每一行还必须具备有效房间层级、
实际入住时间、住宿用途和可解释状态。临时访客必须有来访原因。已完成实际退房的记录必须有实际退房
时间。

历史住宿不能因为住户或对应监护人的当前账号停用、人员档案后来被软删除而从候选名单消失；服务仍从受
保留的人员记录生成历史投影。相应实名密文已经不可用或无法解密时整批失败，不用空值代替。

任何一项缺失时整批失败。响应中的逐人员问题只包含人员内部 ID、姓名、掩码手机号、住宿 ID 和缺失字段
代码，不返回完整手机号或身份证。

## 8. 文件格式

### 8.1 Excel

Excel 工作簿包含：

1. `入住名单`：一行对应一个 `residents` 记录。
2. `未成年监护人`：一行对应一个 `guardians` 记录。

工作表首行固定、冻结并启用筛选。列宽保持可读，但不把姓名、手机号或身份证写入文件名或工作簿元数据。

### 8.2 CSV

CSV 下载返回一个 ZIP 压缩包，包含：

- `入住名单.csv`
- `未成年监护人.csv`

两个 CSV 使用 UTF-8 BOM 和 RFC 4180 兼容转义，保证 Windows Excel 可直接识别中文。空监护人集合仍生成
仅含表头的监护人文件，使文件结构稳定。

### 8.3 两种格式的共同规则

- 同一批次的 Excel 和 CSV 必须来自同一快照并保持字段语义一致。
- 行按楼栋目录顺序、楼层目录顺序、房号、实际入住时间、姓名和行编号稳定排序。
- 手机号、身份证、房号和批次编号强制按文本输出，避免科学计数法和前导零丢失。
- 任何以 `=、+、-、@`、制表符或回车开头的文本都按普通文本安全编码，阻止表格公式注入。
- 文件名只使用批次编号和格式，例如 `housing-report-HR-20260806-018.xlsx`。
- 响应使用正确 `Content-Type`、`Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`
  和 `Cache-Control: no-store, private`。

服务器不把生成文件写入公开目录、仓库、长期临时目录或审计。每次下载都从密文快照重新生成。

## 9. 状态机与人工报送

允许的状态转换：

```text
生成成功: generated
generated -> marked_submitted
generated -> voided
marked_submitted -> voided
生成失败: failed（终态）
voided（终态，可作为新更正批次的前驱）
```

标记人工报送必须填写精确报送时间，可填写备注；未来时间拒绝。作废必须填写原因。已经作废或失败的批次
不能再次报送或下载；已作废批次的原快照继续加密保留，只用于审计追溯，不再对普通下载端点开放。

状态修改在事务内锁定批次行，并校验请求版本。并发的报送、作废或更正只有一个能成功，其他请求返回
`housing_report_state_conflict` 并要求刷新。

## 10. API

### 10.1 生成和查询

- `POST /housing/report-batches`：生成成功或失败批次；成功返回批次摘要，失败返回问题响应并包含安全逐人员
  问题列表。
- `GET /housing/report-batches`：按状态、时间、楼栋、楼层、营期和创建人分页筛选当前获权批次；响应同时
  返回当前筛选下的各状态计数，供桌面和手机汇总卡使用。
- `GET /housing/report-batches/{batch_id}`：返回批次摘要、筛选、计数、状态、更正链和安全操作信息，不返回
  快照内容。

### 10.2 下载和状态动作

- `GET /housing/report-batches/{batch_id}/download?format=xlsx`
- `GET /housing/report-batches/{batch_id}/download?format=csv`
- `POST /housing/report-batches/{batch_id}/mark-submitted`
- `POST /housing/report-batches/{batch_id}/void`

创建更正批次仍使用生成端点，并传递 `corrects_batch_id`。服务先验证原批次已作废和当前用户仍有全部原
范围权限，再按新请求重新生成数据。

所有报送端点使用现有房态私有路由。问题响应和文件响应均禁止缓存。

## 11. 权限与隐私

### 11.1 权限键

所有报送能力统一使用 `housing.reports.export_sensitive`。超级管理员默认拥有；其他角色和账号必须由管理
员明确下发。拥有普通 `housing.read`、入住、调房或退房权限不自动获得实名导出权限。

### 11.2 对象范围

权限支持现有 `global`、`building` 和 `floor` 范围，显式拒绝始终优先。生成请求覆盖的每个规范化范围都
必须获准。批次列表只返回其全部范围当前均获准的批次。

访问具体批次时：

- 完全没有该敏感能力时拒绝请求。
- 具有敏感能力但批次不存在或超出当前对象范围时使用相同的私有 404 语义。
- 权限撤销立即生效；即使用户创建过该批次，也不能继续查看或下载。

### 11.3 页面最小披露

后台批次列表和详情只显示批次编号、筛选范围、用途、人数、行数、状态、操作人和时间，不直接展示完整
手机号、身份证或快照行。逐人员完整实名内容只进入获权下载文件。

## 12. 一致性、加密和完整性

生成服务使用专用数据库会话，并在该会话的第一次查询前开启 PostgreSQL `REPEATABLE READ` 事务。当前
权限、候选住宿及全部关联资料都在同一一致性快照中读取，保证一次投影不会混合并发修改前后的状态。
完整性校验、快照加密、批次写入、范围写入和允许/失败审计在受控事务边界中完成；不能留下“成功批次但
没有完整审计”或“部分实名快照”。

只有已经通过敏感权限和全部范围检查的请求才允许创建成功或失败批次；认证或范围拒绝只记录安全拒绝
审计，不能写入报送批次。

业务校验失败时，服务在事务内写入不含快照和逐人员实名内容的 `failed` 批次及安全审计，提交后再向
路由返回结构化问题；不能通过抛出异常把失败记录一起回滚。数据库连接、事务或审计基础设施自身失败时
不得伪造失败批次或成功响应。

规范 JSON 在加密前固定字段顺序、时间格式和排序。快照使用带密钥版本的现有应用层加密机制；数据库只
保存密文。`snapshot_digest` 是对存储密文计算的 SHA-256，只用于检测损坏，不作为公开内容，也不对实名
明文建立可比对摘要。下载前必须：

1. 重新鉴权并锁定或稳定读取批次状态。
2. 校验状态允许下载。
3. 校验密文摘要。
4. 按记录的密钥版本解密。
5. 按投影模式版本解析并验证。
6. 在内存中生成文件并完成安全审计。
7. 返回附件响应。

解密、摘要、模式、文件生成或审计任一步失败都不得返回表面成功文件。

## 13. 错误与审计

### 13.1 公开错误码

至少定义：

- `housing_report_empty`
- `housing_export_incomplete`
- `housing_report_scope_denied`
- `housing_report_state_conflict`
- `housing_report_correction_invalid`
- `housing_report_snapshot_unavailable`
- `housing_report_render_failed`
- `housing_audit_failed`（复用现有语义）

错误响应不得包含完整手机号、身份证、批次快照、无权房间或无权人员资料。

### 13.2 审计事件

记录允许、拒绝和失败结果：

- 批次生成成功、空结果和资料不完整。
- 批次列表及具体敏感批次详情读取。
- Excel 下载、CSV 下载和历史重下载。
- 标记人工报送。
- 作废批次。
- 创建更正批次。
- 权限拒绝、范围拒绝、状态冲突、解密失败和文件生成失败。

审计元数据只允许操作人、批次 UUID、范围对象 ID、数量、格式、结果、公开错误码和请求关联 ID。不得保存
姓名列表、手机号、身份证、用途、报送备注、作废原因、逐人员问题或文件内容。相关业务文本只保存在受权
批次记录中。

## 15. 测试策略

### 15.1 纯规则与服务测试

- 半开时间范围的前后边界、完全包含、跨范围和零长度拒绝。
- 仅实际入住；预约和取消不纳入。
- 待确认退房继续视为未结束，申请离开时间不能冒充权威实际退房时间。
- 调房分行和人员去重计数。
- 人员类型、营期、楼栋、楼层及组合筛选。
- 中国时区下刚好 18 周岁前后边界。
- 一个及多个有效监护人、成年学员保留监护关系、缺失监护人和监护人实名字段缺失。
- 临时访客原因、所有人员实名字段和已退房记录完整性。
- 规范化排序、确定性序列化、加密往返、密文损坏和投影版本拒绝。
- 状态机全部允许和禁止转换、更正链和并发版本。

### 15.2 文件测试

- 实际解析 Excel 两个工作表和 CSV 压缩包内两个文件。
- 比较两种格式的字段、行、排序和空值语义，不只比较 HTTP 状态。
- UTF-8 BOM、中文、逗号、引号、换行、长身份证、前导零和日期时间。
- 公式注入危险前缀全部保持普通文本。
- 同一批次在业务资料修改后重新下载，解析后的内容仍与原快照一致。
- 文件名和文档元数据不包含个人信息。

### 15.3 PostgreSQL 集成与并发

- 迁移升级/降级、约束、唯一编号、状态字段组合和更正链。
- 一致性快照期间并发修改入住、调房、人员或监护数据时，批次只能反映一个完整数据库时刻。
- 两名管理员并发报送、作废或创建更正时只有一个合法状态转换成功。
- 审计失败导致生成或状态动作回滚；失败批次不包含快照密文。
- 权限在列表、详情、下载或状态动作之间被撤销后，后续请求立即拒绝。

### 15.4 权限、隐私与审计

- 超级管理员、全局授权、单楼栋授权、单楼层授权、显式拒绝、越权和撤权。
- 混合获权/无权范围请求整批失败且不生成成功快照。
- 不存在与超范围批次保持私有 404 等价。
- 页面、API 摘要、错误、日志和审计元数据中没有完整手机号、身份证或快照内容。
- 每种允许、拒绝和失败操作产生预期安全审计；重复下载逐次审计。
- 所有成功和问题响应都验证禁止缓存头。

### 15.5 Web 和四视口 E2E

- 组件测试覆盖桌面表格、手机卡片、筛选、生成、错误、下载、报送、作废、更正链和权限隐藏。
- 四视口：`desktop-1440`、`desktop-1024`、`tablet-768`、`mobile-360`。
- 使用真实隔离 PostgreSQL，分别覆盖超级管理员、楼栋/楼层授权人员、无权人员和运行中撤权。
- 捕获实际下载并解析 Excel/CSV；验证快照重下载、状态变化和审计结果。
- 每个主要页面和对话框检查无横向溢出、移动导航不遮挡、触控尺寸、焦点进入/恢复和 Escape。
- 禁止用固定 sleep 或 `networkidle` 代替具体响应、可见状态和条件轮询。

### 15.6 完成门禁

必须通过：

- 后端全量测试与静态检查。
- Web 全量测试、类型检查、lint 和生产构建。
- 房态目录、个人门户、入住生命周期和实名报送的真实 PostgreSQL 四视口 E2E。
- `git diff --check` 及迁移检查。

Docker/NAS、公安在线 API 和生产备份未验收时，文档必须继续如实声明延期。

### 15.7 文件库依赖

当前 API 依赖没有 XLSX 生成库。实施时只新增一个受控、固定兼容区间的 Python XLSX 库，并同时用于测试
中解析生成结果；CSV 和 ZIP 使用 Python 标准库。依赖加入后必须纳入安全扫描、类型边界和构建验证，不
为了报送功能引入 `pandas` 等无必要的大型数据处理栈。

## 16. 验收标准

1. 时间范围有任何实际住宿重叠的记录均纳入，预约不纳入。
2. 调房历史按住宿时段分行，人员数和住宿行数分别统计。
3. 未成年学员的全部有效监护人进入独立监护人表；缺失任一必填资料时整批失败。
4. 同一批次可下载 Excel 和 CSV，两个格式解析后数据一致。
5. 历史重下载不受后续业务数据变化影响，并逐次重新鉴权和审计。
6. 已报送错误批次只能作废并建立更正链，不能覆盖或删除。
7. 敏感权限及楼栋/楼层范围在后端强制执行，撤权立即阻止历史下载。
8. 明文实名快照不进入数据库普通字段、页面摘要、应用日志、审计或长期文件目录。
9. 桌面、平板和手机完成相同核心操作，关键操作不被横向滚动或移动导航隐藏。
10. 全部本地非 Docker 门禁通过后，才可宣称房态第三实施单元完成；阶段 3 仍需保持 Docker/NAS 与公安
    在线 API 延期说明。

## 17. 最终确认

- 批次采用 PostgreSQL 加密不可变快照，文件按需生成。
- Excel 使用两个工作表；CSV 使用包含两个 CSV 的 ZIP。
- 报送后更正采用“作废原批次 + 新建关联批次”。
- 所有有效监护人均导出；是否未成年以实际入住时间和中国时区判断。
- 只有实际入住记录进入实名报送。
- 公安在线 API、Docker/NAS 和生产备份继续延期。
