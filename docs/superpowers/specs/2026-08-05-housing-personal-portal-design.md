# 学员/监护人住宿门户设计补充

**日期：** 2026-08-05

**状态：** 个人住宿门户本地实现与非 Docker 四视口门禁已完成；Docker/NAS、公安在线报送和生产部署仍未验证

**关联规格：** `docs/superpowers/specs/2026-08-03-housing-room-status-design.md`

**关联计划：** `docs/superpowers/plans/2026-08-04-housing-occupancy-lifecycle.md` 的 Task 9 和 Task 12

## 1. 目标

本补充规格收紧学员和监护人的住宿查看能力。系统提供独立的个人住宿接口与响应式页面，让学员查看本人，
让监护人查看有效监护关系内的一个或多个学员，同时严格限制室友和人员敏感信息。

本单元完成后：

1. 学员和监护人可以在独立的 `/me/housing` 页面查看当前住宿和未取消预约。
2. 未来预约提前显示楼栋、楼层、房间和计划日期，但实际确认入住前不显示未来室友姓名。
3. 监护人可以稳定切换多个学员；未解除的监护关系不会因学员成年自动失效。
4. 管理房态和查看个人住宿仍是两个互不提升的能力。
5. 所有住宿读取使用严格响应白名单、私有缓存响应和只追加敏感读取审计。

## 2. 范围边界

### 2.1 本单元包含

- `GET /api/v1/me/housing` 本人/家庭住宿接口。
- 门户上下文中的 `housing_available` 和 `housing_management_available` 服务端能力。
- 学员本人、监护人家庭范围、成年后继续有效关系和双重身份账号。
- 当前住宿、待确认入住预约、多学员切换和实际室友姓名。
- 独立 `/me/housing` 响应式页面、账号隔离缓存和四视口验收。
- 成功、拒绝和失败三种敏感读取审计。

### 2.2 本单元不包含

- 历史住宿列表、已退房住宿和已取消预约的门户展示。
- 学员或监护人在门户内办理入住、调房、退房或取消预约。
- 手机号、邮箱、身份证、生日、性别、账号状态、房间问题、住宿备注或室友账号资料。
- 管理员房态写操作；这些能力继续留在独立 `/housing` 管理页面。
- Docker、NAS、公安在线报送和生产部署。

## 3. 方案选择

采用“当前住宿与预约分开展示”的平衡方案：

- `current_stay` 只承载已经实际入住或待二次确认退房的住宿。
- `planned_stays` 承载所有仍为 `planned` 的未取消预约，按计划入住时间升序排列。
- 计划入住时间已到但尚未确认入住的记录仍保留在 `planned_stays`，页面标记为“待确认入住”，不会误报为
  已经入住。

未采用统一时间轴，因为它会增加前端状态推导和未来室友脱敏的复杂度。未采用“只显示当前住宿”，因为它
无法满足提前查看房间和计划入住日期的要求。

## 4. 组件边界

### 4.1 后端

- `housing/portal_service.py`：解析本人/家庭目标，执行住宿与室友安全投影；只读，不承载管理写操作。
- `housing/portal_router.py`：暴露 `/me/housing`，注册敏感读取审计并进行严格响应序列化。
- `housing/api_support.py`：复用私有响应、脱敏错误和一次性敏感读取审计边界。
- `portal/context_service.py`：每次请求重新计算个人住宿与房态管理能力。
- `portal/routing.py`：把 `/api/v1/me/housing` 纳入私有门户路径，覆盖错误方法和路由级失败。

个人住宿服务不得调用入住、调房、退房或问题房变更服务。房态管理权限也不得作为家庭目标来源。

### 4.2 前端

- `housing/MyHousingPage.tsx`：独立个人住宿页面。
- 门户 API 客户端：定义严格 DTO、账号级查询键和缓存撤销逻辑。
- 路由与导航：`/housing` 读取 `housing_management_available`，`/me/housing` 读取
  `housing_available`；浏览器不得根据角色名称推测权限。

## 5. 授权规则

### 5.1 候选目标

服务器以中国业务日期计算目标：

- 具有学员档案且获得 `housing.read` 的 `self` 范围时，账号本人是候选目标。
- 获得 `housing.read` 的 `family` 范围时，监护人所有当前有效关系内的学员是候选目标。
- 有效关系必须已经到达 `valid_from`、尚未 `ended_at`，并且未超过可选的 `valid_until`。
- 学员成年不自动结束关系；只要关系未结束且仍在有效期内，监护人继续查看。
- 同一账号同时是学员和监护人时，结果包含本人及家庭学员，并按人员 ID 去重。

服务器随后使用批量人员资源令牌和拒绝优先 RBAC 再次过滤候选目标。已删除人员、缺失学员档案、显式拒绝
或失效关系均不得进入住宿查询。

### 5.2 能力分离

- `housing_available`：至少存在一个通过本人/家庭授权的学员目标时为 `true`。
- `housing_management_available`：账号至少能读取一个全局、楼栋或楼层房态范围时为 `true`。
- 管理员或房态操作员不能仅凭管理能力获得个人住宿卡片。
- 管理员本人同时是获权学员或监护人时，才按相同本人/家庭规则获得个人住宿入口。

### 5.3 目标私有性

`GET /api/v1/me/housing` 不接受任意人员 ID 查询参数，而是一次返回当前账号全部获权目标。响应中的
`subject_person_id` 仅用于前端稳定切换，不得显示在页面。

没有任何获权目标、只有已解除关系目标、目标已隐藏或目标不存在，均返回相同状态、错误码和文案的私有
404。若仍有其他获权目标，隐藏目标直接从结果中消失，响应不得透露其存在。

## 6. API 数据合同

### 6.1 响应结构

```text
HousingPortalResponse
  as_of: AwareDatetime
  subjects: HousingPortalSubject[]

HousingPortalSubject
  subject_person_id: UUID
  subject_name: string
  current_stay: HousingPortalStay | null
  planned_stays: HousingPortalStay[]

HousingPortalStay
  building_name: string
  floor_name: string
  room_name: string
  stay_purpose: permanent | camp | temporary
  planned_check_in_at: AwareDatetime
  planned_check_out_at: AwareDatetime | null
  actual_check_in_at: AwareDatetime | null
  actual_check_out_at: AwareDatetime | null
  status: planned | checked_in | checkout_pending
  roommates: string[] | null
```

不增加 `access_source`、人员类型、住宿 ID、房间 ID、营期 ID 或其他内部字段。`subject_person_id` 是唯一为
多学员切换保留的技术标识。

### 6.2 状态与排序

- `current_stay` 只选择 `checked_in` 或 `checkout_pending`；领域约束保证每人最多一条当前住宿。
- `planned_stays` 只选择 `planned`，包括未来预约和计划时间已到但仍未人工确认的预约。
- `checked_out` 和 `cancelled` 不返回。
- 本人目标优先；其余学员按姓名和人员 ID 稳定排序。
- 预约按 `planned_check_in_at` 和住宿 ID 稳定排序。
- 没有住宿的获权学员仍必须返回，使用 `current_stay = null`、`planned_stays = []`，页面显示
  “暂无住宿安排”。
- 若数据库异常地存在多条当前住宿，接口整体失败，不选择任意一条或返回部分家庭数据。

`actual_check_out_at` 保留在统一住宿时间合同中，但本单元不返回已退房历史，因此正常情况下为空；前端不
显示空时间，也不得把计划离开时间当作实际离开时间。

### 6.3 室友规则

- 当前住宿的室友是同一时刻、同一房间内其他 `checked_in` 或 `checkout_pending` 人员。
- 当前室友仅返回姓名，按姓名和人员 ID 稳定排序；不返回室友 ID 或任何档案字段。
- `planned_stays.roommates` 固定为 `null`，表示“实际入住前不可查看”，不能使用空数组冒充没有室友。
- 当前住宿确实没有室友时返回空数组，页面显示“暂无室友”。
- 问题房状态、问题描述和待调房提醒不进入个人住宿响应。

### 6.4 时间

`as_of` 由服务器生成，客户端不能指定历史或未来读取时点。接口返回带时区时间，业务边界和页面显示统一按
`Asia/Shanghai` 解释；浏览器不得用本地系统时区重算住宿状态。

## 7. 数据流与缓存

1. 登录后前端获取门户上下文。
2. `housing_available` 为真时显示“住宿信息”入口并请求 `/api/v1/me/housing`。
3. 后端先解析账号、人员、有效监护关系和 RBAC，再读取获权目标的住宿。
4. 后端只为实际当前住宿读取室友姓名，构造白名单 DTO 后完成审计。
5. 审计成功后才发送响应；前端按学员切换展示当前住宿和预约。

前端查询键必须包含当前账号 ID。退出登录、切换账号、401、403、404、账号撤销、关系撤销或门户上下文能力
移除时，必须取消并删除完整个人住宿查询；不得把上一账号数据当作占位内容继续显示。

## 8. 隐私、错误与审计

### 8.1 响应白名单

响应模型采用严格字段白名单和禁止额外字段的配置。不得直接序列化 ORM 对象。以下字段及其实际值不得进入
JSON、浏览器 DOM、前端日志或查询缓存：

- 手机号、邮箱、身份证、生日、性别和账号状态；
- 学员编号、室友 ID、房间 ID、住宿 ID 和监护关系 ID；
- 住宿备注、来访原因、取消原因、房间问题描述和后台操作人；
- `access_source`、权限令牌和内部授权原因。

### 8.2 错误映射

- 未登录、会话过期、账号停用或撤销：401。
- 标准账号因强制改密等认证后限制而不可进入门户：403，不返回任何住宿目标信息。
- 没有任何获权目标、隐藏目标或不存在目标：统一私有 404。
- 获权学员暂无住宿：200，不是错误。
- PostgreSQL 或可恢复持久化失败：脱敏 503。
- 其他未映射失败或投影不变量破坏：统一脱敏 500。
- 审计写入失败：500 `housing_audit_failed`，不得先发送住宿正文。

所有成功、验证错误、错误方法、401、403、404、500 和 503 响应均带
`Cache-Control: no-store, private`。异常响应不得包含 SQL、表名、原始异常、姓名或目标存在性差异。

### 8.3 敏感读取审计

每次通过标准账号依赖并进入住宿投影边界的 `/me/housing` 请求最多追加一条 `housing.portal.read` 审计：

- 成功读取：`allowed`，元数据只含获权学员数量 `result_count`。
- 权限或目标拒绝：`denied`，只含统一公开错误码。
- 服务、数据库或响应投影失败：`failed`，只含统一公开错误码。

审计记录保存操作账号、请求 ID、动作、结果和必要的安全计数，不保存姓名、证件、联系方式、房间名称或室友
名单。读取接口除审计外不得写入人员、监护关系、住宿、房间、问题房或调房业务表。审计失败必须关闭访问且
不得自动重试同一请求。

## 9. 页面设计

- 页面标题为“住宿信息”，与“房态管理”保持独立导航和路由。
- 单学员账号直接显示内容；多学员账号在顶部提供全宽可访问选择器。
- 当前住宿卡片展示楼栋、楼层、房间、住宿类型、当前状态以及非空计划/实际时间。
- 预约列表展示相同房间与计划时间；室友区域显示“实际入住后可查看”。
- 计划入住时间已到但状态仍为 `planned` 时显示“待确认入住”，不能显示“已入住”。
- `checkout_pending` 显示“待确认退房”，房间和当前室友继续展示。
- `subject_person_id` 不渲染为文本、链接、测试 ID 或可见属性。
- 360 宽度使用纵向卡片和全宽选择器；768、1024、1440 自适应扩展，不依赖页面级横向滚动。
- 长姓名、楼栋名和房间名允许换行，键盘可以到达学员选择和主要内容。

## 10. 测试与验收

### 10.1 后端服务与 API

测试至少覆盖：

- 学员本人、一个监护人多个学员、成年后继续有效关系和本人加家庭双重身份。
- 尚未生效、已过期、已解除、已删除、缺失学员档案和显式拒绝目标。
- 管理员只有全局房态权限时没有个人住宿能力。
- 无住宿、当前入住、待确认退房、一个或多个预约和已过计划时间的待确认预约。
- 未来预约不查询或返回室友；确认入住后只返回当前室友姓名。
- 异常多当前住宿、数据库失败、审计失败和严格不返回部分家庭数据。
- 隐藏与不存在目标的状态、错误码、文案、私有响应头和审计结果等价。
- 每次请求恰好一条审计，且除审计外业务表零写入。
- JSON 键和夹具值双重禁止字段断言。

数据库相关用例使用隔离 PostgreSQL 测试库串行运行，不允许把跳过 PostgreSQL 用例声明为通过。

### 10.2 前端单元测试

测试至少覆盖：

- 服务端能力控制两种住宿入口，浏览器不检查角色字符串。
- 多学员切换、无住宿、当前住宿、待退房和预约排序。
- 未来室友文案、当前无室友和当前有室友三种不同状态。
- 账号级查询键以及退出、切换账号、关系/权限撤销和私有错误后的缓存删除。
- 禁止字段名和禁止夹具值不进入 DOM、错误文本或 TanStack Query 缓存。
- 长文本、触控尺寸、键盘可达性和无页面级横向溢出。

### 10.3 本地浏览器验收

Playwright 在 1440×900、1024×768、768×1024 和 360×800 四个项目下重复同一核心旅程：

1. 学员查看本人当前住宿和室友。
2. 监护人切换多个学员，查看无住宿、当前住宿和未来预约。
3. 未来预约只显示房间与日期，实际确认入住前不出现未来室友姓名。
4. 关系撤销或账号切换后旧住宿内容立即消失。
5. 页面无裁切、不可达内容、移动底栏遮挡或依赖横向滚动的核心信息。

本单元验收仍使用本地 API、Web 和 PostgreSQL，不启动 Docker，也不声称 NAS 或生产部署已经通过。
