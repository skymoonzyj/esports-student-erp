# 阶段 2 教学评价中心设计

- **日期：** 2026-07-30
- **状态：** 书面规格已确认；第一实施单元已完成，第二实施单元本地实现与非 Docker 门禁已完成
- **所属阶段：** 阶段 2；承接已完成的招生教学运营与教练/家庭门户

## 1. 目标

本阶段建立统一评价中心，并把现有独立项目
[`skymoonzyj/game-score-tool`](https://github.com/skymoonzyj/game-score-tool)
接入 ERP。评价中心同时覆盖三类业务：

1. 学员、获权监护人、教练或管理员上传游戏截图，由独立评分工具完成 OCR、规则评分、审核和发布。
2. 主教练及其他获权工作人员针对具体报名填写学员日报和周报，经过审核后向学员和有效监护人发布。
3. 学员账号及有效监护人账号在结营后分别评价本期实际服务人员、课程训练、住宿生活和服务管理。

完成后必须满足：

- 同一套系统评价页面既能独立打开，也能嵌入 ERP。
- 独立页面使用 ERP 账号登录，不建立第二套账号和密码。
- ERP PostgreSQL 是人员、报名、评价、审核、发布和历史版本的唯一业务主记录。
- 所有项目都能上传截图；只有经过验收并启用的适配器才能自动分析。
- 截图、评分、评语、问卷、权限和历史归属均可追溯。
- Web、Windows、macOS 和手机浏览器使用同一套响应式页面。

## 2. 范围

### 2.1 本阶段包含

- ERP 评价中心导航、工作台任务卡和角色化页面。
- 独立评分页面的单独打开、ERP 内嵌和无感登录。
- 保留现有评分工具页面结构，替换匿名上传和 SQLite 正式数据边界。
- 游戏 ID、辅助手机号、项目分析配置和版本化发布策略。
- 私有截图上传、媒体校验、任务队列、OCR/评分结果和人工审核。
- 每日/每周学员评语、审核、驳回、发布和修订历史。
- 营期工作人员配置、服务历史和结营匿名评价。
- 管理员实名查看、权限下发、审计和工作人员评价单打印。
- 本地开发、自动化测试和可迁移媒体目录。

### 2.2 明确不包含

- 录像上传、GPU 分析或视频评价。首版只显示禁用入口和未开放说明。
- 训练 OCR/识图模型或承诺全部项目立即具备自动分析能力。
- 将原评分工具的 SQLite 历史记录、旧截图、旧录像或临时文件迁入 ERP。它们不进入新系统；最终切换时
  按用户已确认的清理范围执行删除，但当前设计和本地开发阶段不触碰原仓库数据。实际删除前必须单独展示
  清单、备份位置和验收结果，并再次取得破坏性操作确认。
- 住宿房态、入住报送、真实支付、自助报名或天赋测评。
- Docker Compose、镜像、容器媒体卷、NAS 部署和容器验收。

Docker 只在全部 ERP 业务项目开发完成后启动统一整合。本阶段不得因为评价功能完成而提前修改
Compose 或 Dockerfile；代码只需保持路径、端口、服务地址和媒体存储可配置。

## 3. 既有基础与评分工具现状

ERP 已具备：

- 人员、实名资料、账号、监护关系、成年状态和未成年就绪策略。
- 电竞项目、职业队伍、营期、普通班/菁英班、教练分配和正式报名。
- 当前/历史教学信息、教练下一期名单、家庭多学员切换和本人付款门户。
- Cookie 会话、CSRF、账号停用、拒绝优先 RBAC、审计和私有禁止缓存响应。
- PostgreSQL 顺序迁移、React 响应式外壳和四视口 E2E。

现有 `game-score-tool` 是独立 FastAPI/Jinja 页面，主要包含：

- `scorer.py`：MOBA、FPS、和平精英及行为评分函数。
- `ocr_utils.py`：Pillow、Tesseract 和和平精英多截图识别。
- `main.py`：匿名页面、上传接口和提交接口。
- `database.py`：SQLite 玩家、比赛、媒体和历史查询。
- 首页、MOBA、FPS/和平精英、搜索、媒体库和评价快照页面。

评分工具仍是半成品。接入时复用页面、OCR 解析和评分算法，但不复用匿名身份、公开媒体路径或
SQLite 作为正式数据源。

## 4. 核心设计决策

### 4.1 一个评价中心，两个业务分支

评价中心统一入口下分为：

- **系统评价**：上传截图，执行 OCR/评分、审核和发布。
- **教学评价**：工作人员日报/周报，以及学员/监护人的营期评价。

二者共享人员、报名、项目、权限、工作人员关联和历史展示，但任务状态和数据表保持独立。

### 4.2 独立页面与 ERP 内嵌共用同一服务

系统评价页面保留独立服务：

- 可以单独打开。
- 可以在 ERP 评价中心内同源代理并内嵌。
- 两种入口使用同一份页面代码和同一套 ERP 正式数据。
- 首版保留评分工具现有视觉和页面结构，后续再逐页统一 ERP 视觉。

教学评语和营期评价使用 ERP 原生 React 页面，不放进评分工具。它们依赖 ERP 报名、家庭权限、
工作人员分配和打印能力，独立实现可避免评分工具承担无关业务。

### 4.3 ERP 是唯一主记录

评分工具不直接连接 ERP 数据库，也不维护第二套正式业务库：

- ERP PostgreSQL 保存人员关联、游戏 ID、任务、评分、审核、发布和版本。
- 截图保存在私有媒体目录；PostgreSQL 只保存不透明媒体编号、存储键和哈希。
- 评分工具只负责页面、OCR、评分算法、短期任务执行信息和可重试提交。
- 工具与 ERP 数据不一致时，以 ERP 已提交记录为准。

### 4.4 当前本地开发，最终统一容器化

当前阶段分别启动 ERP API、ERP Web、PostgreSQL 和评分工具本地进程。所有正式元数据从第一天起
进入 PostgreSQL，媒体进入 Git 外私有目录。数据服务器到位后迁移现有数据库和媒体，不重新开始。

全部 ERP 项目开发完毕后，再建立最终 Docker/NAS 专项，统一完成容器、卷、反向代理、备份恢复和
生产候选验收。

### 4.5 中国时间与截止边界

所有业务日期、周期和截止时间统一使用 `Asia/Shanghai`，数据库仍保存带时区时间戳：

- “开营前 7 天”从开营本地日期向前第 7 天的 `00:00:00` 开始。
- “结营后 N 天”截至结营本地日期之后第 N 个自然日的 `23:59:59.999...`，截止瞬间包含在窗口内。
- 日报和周报周期均按本地日期闭区间计算，不使用服务器默认时区。
- “一个自然月”按结营本地日期和时刻加一个日历月；目标月没有对应日期时取该月最后一天的相同时刻。
- API 返回明确的 `opens_at`、`due_at` 和时区，前端只展示，不自行重新推算。

## 5. 模块边界

### 5.1 ERP 后端

新增 `app.evaluations` 领域包，按职责拆分：

- `models`：游戏账号、媒体、分析配置、任务、结果、评语、问卷和工作人员服务记录。
- `schemas`：公开门户、内部操作和评分工具集成的最小响应模型。
- `context_service`：评价中心能力、任务数量和可见页面。
- `game_account_service`：游戏 ID、上限、解绑历史和辅助手机号匹配。
- `media_service`：流式上传、校验、哈希、私有读取和媒体清单。
- `system_evaluation_service`：任务状态、匹配、分析配置快照、审核、发布和修订。
- `student_report_service`：日报/周报周期、补录、审核和版本。
- `camp_survey_service`：问卷资格、工作人员快照、匿名投影和打印数据。
- `integration_router`：评分工具使用的版本化内部接口。
- `portal_router`：教练、工作人员、学员和监护人的评价页面接口。
- `admin_router`：配置、权限、待办、实名查看和打印接口。

评分工具不得导入 ERP SQLAlchemy 模型；双方只依赖版本化 HTTP 契约。

### 5.2 ERP 前端

新增评价区域：

- 评价中心首页和任务卡。
- 系统评价内嵌容器及独立打开入口。
- 日报/周报填写、审核队列、版本对比和历史页面。
- 学员/家庭评价历史和营期问卷。
- 工作人员匿名反馈与管理员打印页面。
- 游戏 ID、辅助匹配提示和项目分析配置页面。

### 5.3 独立评分工具

评分工具继续保留独立仓库，并逐步改造：

- 保留现有模板、静态资源、OCR 和评分函数。
- 用 ERP 登录桥接替代匿名访问。
- 用 ERP 集成 API 替代 `database.py` 正式读写。
- 用 ERP 媒体编号替代公开本地上传路径。
- 保留独立打开模式和内嵌模式。
- 保存明确的集成 API 版本，允许两个仓库分别迭代。

本地开发使用两个独立 Git 检出目录，通过配置的评分工具地址连接；ERP 仓库不复制或内嵌评分工具源码。
双方各自记录已验收的集成 API 版本和对应提交。最终容器化专项再决定镜像固定方式，不在本阶段引入
Git 子模块或容器镜像依赖。

## 6. 登录与会话桥接

### 6.1 单独打开

未登录用户直接打开评分页面时：

1. 评分工具生成包含版本、模式、随机 nonce、站内返回路径和 5 分钟到期时间的签名 `state`，再创建 ERP
   登录请求；`state` 不依赖浏览器临时 Cookie。
2. 用户在 ERP 登录页完成手机号和密码验证。
3. ERP 只允许白名单返回地址，并签发 60 秒有效、单次使用、限定评分工具受众的登录票据。
4. ERP 用一次性自动提交的后端表单 POST 返回票据，不把票据放进查询参数或片段。
5. 评分工具后端交换票据后建立独立命名、限定路径的 HttpOnly、SameSite 会话；生产环境强制 Secure，
   本地非 Secure 例外只允许显式开发模式和回环地址。不把 ERP 原始会话令牌交给前端脚本。
6. 评分工具只恢复签名 `state` 中经过校验的原始站内返回路径，用户返回原评分页面。

ERP 只加密保存并原样回传 `state`，不得解析或改写；评分工具回调必须验签、校验到期时间、模式和站内
返回路径。`state` 最多 1024 字符，只允许 Base64URL 字符、`.` 和 `-`。评分工具会话不得超过 ERP 原会话
剩余有效期，并保存 ERP 委派会话引用；ERP 登出、账号停用、权限收回或强制改密后，下一次业务授权请求
立即失败。票据消费后立即失效，不把可重放票据留在浏览器
历史、访问日志或页面 URL 中。

本地浏览器固定使用 `127.0.0.1` 打开 ERP，使用 `localhost` 打开独立评分页；ERP 的 `erp_session`
Cookie 只作用于 `/api`。内嵌评分会话使用 `/evaluation-tool` 路径 Cookie，独立评分会话使用 `localhost`
主机 Cookie，避免浏览器按主机而非端口发送 Cookie 时发生身份串用。

### 6.2 ERP 内嵌

ERP 打开系统评价页面时自动完成相同票据交换。内嵌页不显示第二个登录页，不建立独立账号。内嵌流量通过
ERP 配置的同源代理路径进入评分工具，评分工具必须支持可配置公共基路径，不能写死域名、端口或根路径。
页面只允许 ERP 白名单来源嵌入；父子页面如需通信，只使用固定来源校验的最小消息，不传登录票据、会话
令牌或完整业务数据。

### 6.3 授权边界

登录票据只证明账号身份，不承载长期业务授权。上传、媒体读取、审核、游戏 ID 和目标学员访问必须由
ERP 在每次业务请求重新判断。评分工具不得相信浏览器传入的角色、学员 ID 或权限标志。

## 7. 工作人员角色与服务历史

### 7.1 配置来源

管理员在开营前按营期和项目/班级配置：

- 主教练。
- 助教。
- 生活老师。
- 自定义工作人员角色。

现有 `coach_assignments` 继续作为主教练和助教来源。新增通用营期工作人员角色和分配，覆盖生活老师
及其他自定义角色。通用分配支持项目级或班级级目标，并保存 `valid_from`、`valid_until` 和实际结束时间。

### 7.2 学员关联

正式报名通过报名、班级、项目和时间区间自动关联本期工作人员，不手工给每名学员重复选择。工作人员
中途更换时，前后人员都保留服务历史；结营问卷列出所有与该报名时间重叠且实际服务过的人员。

### 7.3 角色类别

内置和自定义角色同时记录类别：

- `teaching`：主教练、助教及教学角色。
- `life_service`：生活老师及住宿生活角色。
- `operations`：客服、运营和服务管理角色。

管理员新增的所有项目角色都进入结营人员评价。角色类别只决定该工作人员还能看到哪一类匿名总体评价，
不决定是否接受个人评分。

项目工作人员角色可以附加本营期/项目范围内的能力，例如评语填写或审核。角色能力只在对应服务分配的
有效对象范围内生效，不能扩展为全局权限；账号级显式拒绝仍优先。对于营后仍在业务截止窗口内的上传、
日报整改和末周报提交，以“目标报名/周期是否与该人员服务期重叠”判断对象资格，能力延续到对应截止时间，
不因工作人员分配在结营时结束而提前失效。管理员显式收回或账号停用立即优先。

## 8. 权限设计

新增独立权限：

- `evaluation_center.access`：进入评价中心和建立评分工具登录桥接；不自动授予任何评价数据、上传或审核能力。
- `evaluation_media.upload`：上传截图。
- `evaluation_media.original.read`：查看或下载原图。
- `evaluation_jobs.review`：审核系统评价。
- `analysis_profiles.manage`：管理适配器、阈值和发布模式。
- `student_game_accounts.manage`：新增或解除游戏 ID。
- `student_reports.write`：填写日报和周报。
- `student_reports.review`：审核日报和周报。
- `camp_surveys.identity.read`：查看问卷评价者身份和完整原文。
- `camp_surveys.print`：打印工作人员汇总评价单。
- `cohort_staff.manage`：维护营期项目工作人员和自定义角色。

本设计中的“超级管理员”指现有固定 `admin` 角色，不新增第二套硬编码管理员层级。其他管理人员通过
项目工作人员角色能力或账号级权限覆盖获得具体功能。

默认授权：

| 身份 | 默认能力 |
| --- | --- |
| 超级管理员/管理员 | 全局配置、上传、审核、原图、实名、打印和工作人员管理 |
| 主教练 | 进入评价中心；本人负责班级的评语填写、系统评价审核、服务期内及未完成审核任务的原图 |
| 助教 | 进入评价中心；本人服务班级的已发布评价，以及服务期内获准查看的原图；默认不能填写评语 |
| 生活老师/自定义角色 | 进入评价中心并查看本人匿名反馈；默认不能填写评语 |
| 学员 | 进入评价中心；查看本人已发布评价；管理本人游戏 ID；默认不能上传 |
| 监护人 | 进入评价中心；查看有效家庭范围内已发布评价；默认不能上传或管理游戏 ID |

管理员可以按账号和对象范围追加或收回能力：

- 给助教、生活老师或其他工作人员开放评语填写。
- 给监护人开放家庭范围内的游戏 ID 新增和解除。
- 给学员、监护人、教练或其他获权账号开放截图上传。
- 给管理教员或其他角色开放评语/系统评价审核、实名查看和打印。

所有权限继续执行显式拒绝优先。上传权不自动带来原图、审核、实名或打印权。
客服角色默认没有评价中心入口；如业务需要，管理员可单独下发 `evaluation_center.access`，但仍不会因此获得
任何学员评价内容或其他评价操作能力。

除固定全局入口权限外，敏感能力授权必须同时保存对象范围与有效期；对象范围至少可限定营期、项目、班级、
报名、学员或工作人员。授权人不能转授自己不具备的范围，关系结束、服务分配结束、账号停用或授权到期后
下一次请求立即失效。列表、搜索、导出和打印与详情读取使用同一对象谓词，不能用全局布尔值绕过范围过滤。

## 9. 游戏 ID 与辅助手机号

### 9.1 游戏 ID

每条绑定包含：

- 学员人员 ID。
- 电竞项目 ID。
- 应用层加密的原始游戏 ID，以及由规范化值生成的带密钥 HMAC 检索值。
- 生效时间、解除时间、创建人与解除人。

规则：

1. 每名学员跨全部项目默认最多同时绑定 3 个游戏 ID。
2. 管理员可以为单个学员提高最高上限；上限变化必须审计。
3. 同一项目的同一规范化游戏 ID 同时只能绑定一名学员。
4. 新学员绑定前必须先解除原学员绑定。
5. 解绑不删除历史。原学员保留解绑前数据，新学员只看新绑定生效后的上传和评价。
6. 学员本人和管理员可管理绑定。
7. 监护人默认不能管理；管理员授予家庭范围权限后可以新增和解除。

### 9.2 辅助手机号

管理员可以给学员增加未验证辅助手机号：

- 使用与主手机号相同的字段加密和 HMAC 检索方式。
- 标记为未验证，不用于登录、找回密码或业务授权。
- 允许多个学员保存相同辅助手机号。
- 只能由管理员新增、修改或停用。
- 多人命中时不得自动归属评价任务。

## 10. 项目分析配置

每个电竞项目拥有版本化 `analysis_profile`：

- `manual_only`：允许上传，进入人工录入和审核。
- `automatic`：使用已启用且经过验收的 OCR/评分适配器。

配置版本至少包含：

- 适配器标识和版本。
- 评分规则版本。
- 必填识别字段。
- 字段置信度门槛。
- 允许自动发布的警告级别。
- 发布模式 `auto_publish | review_required`。
- 生效时间、配置人和变更原因。

所有项目均可上传。新项目默认 `manual_only`。当前工具已有通用 MOBA、FPS 和和平精英能力，但具体项目
只有在样本与规则验收后才能启用 `automatic`。

评价任务创建时保存完整配置快照。管理员修改配置只影响后续新任务；已创建任务继续执行原版本和原发布
模式。

## 11. 私有媒体

### 11.1 存储

PostgreSQL 不保存截图或录像二进制。媒体记录保存：

- 不透明媒体 ID 和不可猜测存储键。
- SHA-256、真实 MIME、扩展名、文件大小和像素。
- 上传人、项目和时间；目标学员与报名在待匹配阶段允许为空，确认后只能通过受审计的匹配操作写入。
- 存储状态、校验状态和删除/保留状态。

完整 OCR 原文默认不作为长期业务字段保存。ERP 长期保存评分所需的结构化识别字段、字段置信度、规则警告
和算法版本；确需诊断时只能保存脱敏诊断片段，并设置单独权限和有限保留期。原图仍按本节长期媒体规则
管理。

本地文件保存在 Git 外配置目录。未来数据服务器/NAS 到位后迁移同一目录结构和哈希清单。

### 11.2 上传校验

上传采用流式写入并校验：

- 真实 MIME 与允许扩展名一致。
- 仅接受 JPEG、PNG 和 WebP。
- 单张最大 20 MiB、最大 50 百万像素，每个评价任务最多 3 张截图。
- 文件大小、像素和解码有效性。
- 哈希重复和同一报名/项目的既有任务。
- 上传窗口和目标对象权限。

页面预览使用服务端重新解码生成、去除元数据的派生图，不直接内联原文件。原图下载响应固定真实媒体类型，
启用 `nosniff` 并使用安全文件名；派生图可重建，不替代受保护原图。

业务去重在归属确认后按学员、报名、项目和媒体哈希执行，相同截图返回已有任务，不生成重复历史。待匹配
阶段只允许存储层按哈希复用同一受保护文件，不据此向上传人透露其他任务是否存在。若已有业务任务处于
可整改、失败或被驳回状态，同时返回允许的“继续整改/重试”操作；不得因为去重使任务永久锁死。

本阶段新产生的截图和评价属于长期业务数据，不自动物理删除。无效、失败或被拒绝任务可以标记归档，
但媒体、原因和状态历史继续保留，直到未来形成经过批准的保留策略和可审计删除流程。

进入生产候选验收前必须形成数据生命周期矩阵，分别列明原图、派生图、隔离临时文件、失败/驳回任务、
结构化结果、评语、问卷、审计日志和备份副本的业务/法定依据、保留期限、法律冻结、删除申请、备份淘汰和
执行审计。当前本地阶段“不自动删除”不能被解释为生产环境无限期保留策略。

### 11.3 原图访问

默认可查看原图：

- 管理员。
- 该报名当前服务中的主教练/助教，以及仍有未完成审核或修订任务的原服务人员。
- 学员本人。
- 当前有效监护人。

管理员还可下发原图权限。查看和下载必须通过授权接口并记录审计，不提供公开静态 URL。

教练/助教分配结束后仍保留该营期已发布评价结果；当相关系统评价任务已发布或归档且服务分配已结束时，
其原图访问自动失效。确需复核旧原图时，由管理员下发绑定营期/报名/任务、原因和到期时间的临时权限。
监护人仅在关系持续有效时保留访问；学员成年不会自动结束监护关系，关系结束或到期后家庭访问立即移除。

## 12. 系统评价流程

### 12.1 上传资格和时间

截图上传窗口为营期开营前 7 天至结营后 7 天，使用 4.5 的中国本地日期边界。

可上传主体：

- 当前窗口内正式报名学员，且账号获得上传权限。
- 获权监护人代有效家庭范围内的当前窗口学员上传。
- 当前或曾在该报名对应项目/班级实际服务、且仍处于上传窗口的获权教练或工作人员。
- 管理员代窗口内任意正式报名学员上传。

非青训营学员、无服务关系的工作人员和未获权账号不能上传。管理员代上传时记录目标、操作者和原因。

### 12.2 自动匹配

系统把身份识别与正式评分识别拆为两个阶段。上传前已有游戏 ID 或手机号上下文时先直接匹配；否则只执行
受限的 `identity_extraction`，按以下顺序匹配：

1. 当前有效的项目游戏 ID。
2. ERP 主手机号。
3. 管理员维护的辅助手机号。

匹配只在上传人有权访问的学员及有效上传窗口内进行。未登录用户执行上传时先跳转 ERP 登录。无法唯一
匹配时任务进入 `pending_match`，停止 `scoring_ocr` 和正式评分；用户可管理本人游戏 ID，获权监护人可
管理家庭游戏 ID，或由管理员确认。`identity_extraction` 只提取配置允许的游戏 ID/手机号匹配字段，结果
只在服务端用于候选匹配，不向浏览器返回其他候选人或正式评分内容；确认归属后才允许完整 OCR。

### 12.3 状态机

```text
uploaded -> identifying
identifying -> pending_match | queued | manual_input
pending_match -> queued | manual_input
queued -> processing
processing -> published | needs_review | failed
failed -> queued | manual_input | archived
manual_input -> needs_review
needs_review -> published | rejected
rejected -> correction_pending | archived
correction_pending -> needs_review | queued
archived -> correction_pending | queued
published -> revision_draft
revision_draft -> queued | manual_input
```

待匹配任务确认归属后根据创建时配置快照进入 `queued` 或 `manual_input`。`automatic` 项目进入
`queued`，`manual_only` 项目直接进入 `manual_input`。`processing -> published` 只允许满足自动发布条件
时发生。失败任务保留错误分类和尝试次数；可重试错误按同一任务重新排队，永久错误或耗尽重试的任务转入
人工录入，也可由管理员记录原因后归档。

审核驳回必须填写原因。原录入人、当前审核人或获权管理员可在同一任务的 `correction_pending` 中修正并
重新提交；自动任务也可选择按同一任务重新排队。被驳回任务不得靠再次上传相同文件生成第二条历史。
归档只停止处理，不删除媒体或历史；管理员可在同一任务上审计后重新开放整改或重试。

### 12.4 发布

- `review_required`：所有结果进入审核。
- `auto_publish`：只有字段完整、全部关键置信度达标且没有阻断警告的结果自动发布。
- 低置信度、关键字段缺失或规则警告始终强制人工审核。

人工任务默认分配给当前班级主教练。没有主教练时进入管理员和获权审核人员公共队列，不自动发布。

### 12.5 修订

已发布结果不能就地覆盖。修订从 `revision_draft` 创建新版本，并按原任务配置快照进入自动处理或人工录入；
只有满足原自动发布条件时才能自动发布，否则重新审核。旧发布版本持续可见，直到新版本发布后成为当前
版本；全部历史、作者、审核人、适配器和规则快照永久保留。

### 12.6 视频占位

独立和内嵌页面均显示录像入口，但按钮禁用并说明 GPU 服务未就绪。本阶段不接收、保存或排队视频文件。

## 13. 日报与周报

### 13.1 记录单位

每条评语必须指向具体正式报名，并保存作者人员、工作人员角色、班级、项目、营期和周期。首版内容为一段
必填文字，不设置可视化评分维度；版本结构允许未来增加 JSON 维度而不改写历史文本。

同一作者、报名、评语类型和周期只能有一个有效评语。不同获权工作人员可以分别提交。

### 13.2 日报周期

- 从开营本地日期到结营本地日期，每个中国标准时间自然日生成一个日报周期。
- 不生成未来日报。
- 当日日报从该本地日开始后可以保存和提交。
- 允许补录过去日报。
- 日报首次提交截至结营本地日期后第 3 个自然日结束；按时进入审核流程的日报不因该截止到达而锁死。

### 13.3 周报周期

- 不按自然周，使用开营本地日期为锚点连续切分 7 天周期。
- 常见 21 天营期形成 3 个完整周期。
- 末周期不足 7 天仍生成周报。
- 周期进行中可以保存草稿，周期结束后才能提交审核。
- 上一周期周报可在下一周期结束前补交。
- 最后一份周报无论是否满 7 天，首次提交截至结营本地日期后第 7 个自然日结束。

### 13.4 填写权限

- 主教练默认可填写本人负责学员。
- 助教默认不能填写，管理员可按账号和班级开放。
- 管理员可以给生活老师或其他实际服务人员开放。
- 获权人员只能评价与本人服务时间和对象范围重叠的学员。

### 13.5 审核和版本

```text
draft -> pending_review -> published
pending_review -> rejected -> correction_draft -> pending_review
published -> revision_pending_review -> published(new version)
```

- 超级管理员默认审核，管理员可向管理教员或其他角色下发审核权限。
- 评语作者不得审核本人提交或修订的版本；没有独立获权审核人时继续留在公共审核队列，不自动发布。
- 驳回必须填写原因，原作者修改后重新提交。
- 首次提交截止只限制从草稿进入审核。已按时提交后若被驳回，原作者从驳回时刻起有 3 个中国自然日完成
  整改并重提；管理员可记录原因后再次开放整改窗口。
- 修改已发布评语创建新版本；旧版本在新版本审核通过前继续展示。
- 正常填写窗口结束后，已发布评语只能由管理员记录原因后发起修订或给原作者开放 3 个中国自然日的修订
  窗口，不能直接覆盖历史。
- 学员和当前有效监护人只看到已发布版本。

## 14. 营期结营评价

### 14.1 提交资格和窗口

针对每个正式报名：

- 学员本人账号可提交一份。
- 每个在提交时仍具有效监护关系的监护人账号可各提交一份。
- 学员和监护人互不覆盖，也不能编辑对方内容。
- 提交窗口从结营时刻开始，到中国时间下一个自然月对应时刻结束；下个月没有对应日期时，截止到该月
  最后一天的相同时刻。

每个评价者账号和报名只能有一份提交。首次提交后在窗口内最多修改一次，并保存两个完整版本。

### 14.2 问卷内容

结营时系统按工作人员服务历史为每个正式报名生成版本化人员名单快照，包含所有实际服务过该报名的
工作人员，包括中途结束和后来接替的人员。首份问卷提交前，管理员修正服务历史可重建快照；已有问卷
提交后不得静默改变名单。此后如需纠错，管理员必须创建有审计原因的新快照版本：既有回答保留原版本，
新增人员形成单独补充项，补充填写不占用问卷“一次修改”额度，被错误纳入的人员从后续汇总排除但不物理
删除历史。

每位工作人员：

- 1–10 分，必填、仅整数。
- 打分原因，选填。
- 给该工作人员的建议，选填。

总体维度：

- 课程训练 1–10 分，必填；原因选填。
- 住宿生活 1–10 分，必填；原因选填。
- 服务管理 1–10 分，必填；原因选填。
- 给教学团队的建议，选填。
- 整体建议，选填。

### 14.3 发布和匿名投影

提交后立即生效，不经过审核。

工作人员可匿名查看：

- 对本人的评分和原因。
- 与本人角色类别相关的总体评分和原因。
- 给本人的建议；教学角色还可看到给教学团队的建议。

教学角色可查看课程训练评价，生活服务角色可查看住宿生活评价，运营服务角色可查看服务管理评价。页面
不返回评价者账号、人员、手机号或精确提交时间。匿名是访问层隐藏身份，不承诺在极少提交者场景下无法通过
业务上下文推测。

超级管理员默认可查看评价者身份和完整原文，也可向其他账号下发实名查看权限。

### 14.4 打印

管理员及获权人员可按工作人员生成打印友好的汇总评价单，包含：

- 各评分平均值。
- 每次匿名评分明细。
- 打分原因。
- 给该工作人员的建议；教学角色评价单还包含给教学团队的建议。
- 营期、项目、角色和服务时间。

交付给工作人员的默认打印版本不包含评价者身份。实名打印或内部调查需另行使用实名查看权限并记录审计。

## 15. 页面与路由

ERP 路由：

- `/evaluations`：评价中心首页。
- `/evaluations/system`：内嵌系统评价。
- `/evaluations/reports`：日报/周报工作区。
- `/evaluations/reports/review`：评语审核队列。
- `/evaluations/surveys`：营期问卷和匿名反馈。
- `/evaluations/admin`：分析配置、待匹配、公共审核、实名和打印。

独立评分工具保留首页、MOBA、FPS/和平精英、查询、媒体库和快照路径。直接打开未登录时走 ERP 登录桥接。

### 15.1 评价中心首页

按账号能力显示：

- 可上传或历史系统评价。
- 待写日报/周报、待审核、被驳回数量。
- 待填写营期问卷及截止倒计时。
- 本人匿名反馈。
- 管理员待匹配、失败、公共审核和打印待办。

### 15.2 系统评价内嵌

- 提供明确标题、加载、错误和重新连接状态。
- 提供“单独打开”操作。
- 没有上传权时保持只读页面，不隐藏已发布历史。
- 手机端允许全屏打开，避免 ERP 底栏和评分工具导航同时挤压内容。

### 15.3 日报/周报

- 按营期、项目、班级、学员、周期和状态筛选。
- 手机端使用任务卡，桌面端使用紧凑表格和详情抽屉。
- 审核页显示版本差异、作者、所属周期和真实提交时间。

### 15.4 学员/家庭

- 复用现有多学员切换。
- 只显示已发布评语和系统评价。
- 获权且在窗口内时显示上传入口。
- 结营后显示问卷和一个月截止提示。

### 15.5 管理员

- 分析适配器、版本、阈值和发布模式。
- 工作人员角色、分配历史和权限。
- 游戏 ID 上限、辅助手机号、待匹配和冲突。
- 审核、实名查看、打印和审计。

## 16. 集成 API 与数据一致性

评分工具通过版本化内部接口完成：

- 登录票据交换和当前账号最小上下文。
- 上传资格、可见学员、项目和报名选项。
- 媒体上传与任务创建。
- 待处理任务领取和短时媒体读取。
- OCR/评分结果提交。
- 人工录入、审核、发布和历史查询。

### 16.1 调用身份与版本

- 浏览器只调用评分工具页面或 ERP 同源代理；评分工具后端再调用 ERP 集成 API，不把内部服务凭据发给
  浏览器。
- 服务调用使用与用户会话分离、可轮换且限定受众的服务凭据，同时携带 ERP 委派会话引用或明确操作者；
  服务凭据不能代替用户取得更大业务权限。
- 评分 Web 与后台 Worker 使用不同服务身份。Web 身份只代理登录和获权用户操作；Worker 身份只领取任务、
  读取其当前租约绑定的短时媒体并提交该尝试结果。凭据支持独立轮换、吊销和审计，浏览器永远不能获得。
- 接口主版本固定在路径中，请求和响应同时携带契约版本、追踪 ID 和时间戳。破坏性修改创建新主版本，
  保留双方都通过契约测试的迁移窗口。
- 评分工具启动时报告支持的接口、适配器和结果模式版本；ERP 不向不兼容实例派发任务。

### 16.2 幂等和媒体提交

评分工具不执行双写。所有正式写操作提交 ERP：

- ERP 为上传会话、媒体、评价任务和结果版本生成稳定编号。
- 上传先进入隔离临时区，校验、哈希和授权通过后，再以事务方式提交媒体记录与任务引用；未提交临时文件
  可按有限时间清理，不属于长期业务媒体。
- 创建任务和提交结果分别使用有作用域的幂等键。相同键和相同载荷重复请求返回原结果；相同键但载荷不同
  返回冲突并审计，不生成第二条评价。
- 工具端网络失败时使用同一任务 ID、版本和幂等键重传。ERP 已接受的结果始终为准。

### 16.3 Worker 租约和恢复

- 领取任务使用原子状态迁移，返回 `attempt`、不可伪造租约令牌和 `lease_expires_at`。
- Worker 可在仍持有租约时续租；过期租约提交被拒绝，防止旧 Worker 覆盖新尝试。
- ERP 保存任务、尝试和最终接收结果。评分工具重启后从 ERP 重新领取；未确认的临时结果可重算或按原
  幂等键重传，不把工具本地状态当作正式记录。
- 永久错误进入人工队列；限流、超时和服务端暂时错误按退避策略重试，并记录可审计错误分类。

## 17. 安全与隐私

- 所有评价页面要求 ERP 标准账号；上传动作不存在匿名例外。
- 登录票据短时、单次、限定受众；签名 `state` 包含随机 nonce，回调地址来自服务端白名单配置。
- Cookie、CSRF、会话停用和强制改密沿用 ERP 安全边界。
- 评分工具自己的页面会话也必须对全部状态变更请求执行 CSRF 校验；内部 API 使用服务认证和委派用户上下文，
  不用浏览器 Cookie 充当服务凭据。
- 私有响应使用 `Cache-Control: private, no-store`。
- 媒体文件不挂载为公开静态目录。
- 完整手机号和辅助手机号继续使用加密存储，日志只记录不敏感标识。
- 上传、原图、审核、实名、打印、游戏 ID 和权限变化全部审计。
- 审计元数据不保存图片、完整 OCR 文本、评分备注原文、手机号或身份证。
- 文件校验失败、越权和对象不存在使用统一错误，不泄露其他学员或游戏 ID 是否存在。
- 任务领取使用租约和原子状态变更，避免两个 Worker 同时处理。

## 18. 失败与边界行为

| 场景 | 行为 |
| --- | --- |
| 无法唯一匹配学员 | 进入待匹配；只允许受限身份字段提取，不运行完整评分 OCR 或评分 |
| 游戏 ID 已被占用 | 阻止新绑定，要求原学员先解绑 |
| 超出游戏 ID 上限 | 阻止绑定，提示联系管理员提高上限 |
| 项目没有自动适配器 | 进入人工录入，不伪造自动结果 |
| OCR 低置信或缺关键字段 | 强制人工审核 |
| 评分工具暂时不可用 | ERP 其他评价功能可用，系统评价显示重试状态 |
| ERP 暂时不可用 | 工具停止领取新任务，已完成结果按幂等键重试 |
| 重复截图 | 返回已有任务，不重复创建历史 |
| 评语被驳回 | 显示原因，按时首提的作者获得 3 个中国自然日整改窗口；管理员可审计后重开 |
| 监护关系结束 | 立即移除家庭评价与原图访问 |
| 教练分配结束 | 保留已发布结果；已完成任务原图自动撤权，旧原图仅可临时授权 |
| 评价配置改变 | 只影响新任务，旧任务使用创建时快照 |
| 视频入口 | 显示未开放，不接收文件 |

## 22. 已确认决策摘要

- 系统评价和教学评价共用 ERP 评价中心，但保持独立领域状态。
- 评分工具保留独立页面和独立仓库，可单独打开或 ERP 内嵌。
- 两种入口都使用 ERP 账号；ERP 是唯一业务主记录。
- 首版保留评分工具现有视觉；旧 SQLite 数据和旧媒体不迁移、不进入新系统，最终切换时按确认清单另行删除。
- 所有项目可上传；未验收项目只走人工处理。
- 自动发布由管理员按项目配置，低置信和警告始终强制审核。
- 游戏 ID 默认跨项目最多 3 个，历史归属不随解绑转移。
- 日报按中国自然日，周报从开营日每 7 天切分。
- 主教练默认填写评语，其他工作人员由管理员授权；评语发布前必须审核。
- 学员与每个有效监护人各提交一份营期评价，全部分数必填，可修改一次。
- 所有实际服务人员接受独立评分，工作人员只看与本人相关的匿名反馈。
- 当前只做本地开发；Docker/NAS 在全部 ERP 项目完成后统一启用。
