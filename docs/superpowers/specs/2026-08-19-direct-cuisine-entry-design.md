# 喜欢菜系直接输入设计

- **日期：** 2026-08-19
- **状态：** 书面规格已确认
- **所属规格：** `2026-08-11-food-preferences-survey-export-design.md`

## 1. 背景与目标

新数据库只预置不可删除的系统菜系“其他”。标准菜系依赖管理员后续维护，因此首次餐饮问卷只显示“添加菜系 其他”，用户还必须点击后才能看到自定义名称输入框。这个两步交互不直观，也使尚未配置菜系字典的系统看起来无法正常填写。

本次改为始终提供菜系名称输入框。用户无需等待管理员配置字典，即可直接添加最多 3 个不同菜系；管理员配置的标准菜系仍作为快捷选项保留。

## 2. 已确认规则

1. 每个人仍最多保存 3 个喜欢的菜系。
2. 用户可直接输入 1–3 个不同菜系，例如“川菜、粤菜、东北菜”。
3. 标准菜系按钮继续存在，但系统“其他”不再显示为可点击按钮。
4. 直接输入和标准菜系共用 3 项上限，并按 NFKC、折叠空白和 Unicode casefold 后的名称去重。
5. 单项清理空白后必须为 1–40 个字符；空值、重复值和第 4 项不得提交。
6. 自定义菜系标签、只读资料、历史、统计和导出均展示实际名称，不在用户界面前加“其他：”。
7. 现有菜系资料和历史保持兼容，不重写既有业务数据。

## 3. 方案比较

### 3.1 采用：多个自定义名称共用系统“其他”选项

每个直接输入的名称仍引用唯一的系统“其他”菜系 ID，但以独立位置和独立 `custom_name` 保存。这样无需让普通用户创建全局字典项，现有快照、统计和导出结构也无需改成另一种数据格式。

### 3.2 不采用：自动把用户输入加入全局菜系字典

个人自由输入会污染所有人的快捷选项，并引入全局字典权限、审核、停用和审计副作用。

### 3.3 不采用：把多个名称拼在一个“其他”字符串中

拼接字符串会破坏 3 项位置语义、精确去重、单项统计、历史对比和导出结果。

## 4. Web 交互

共享的 `FoodPreferencesPanel` 增加独立 `cuisineInput` 状态，并在所有可编辑入口使用同一套交互：

- “喜欢的菜系”区域始终显示“菜系名称”输入框和“添加菜系”按钮；
- 回车与点击按钮行为一致；
- 成功添加后清空输入框，并把实际名称显示为可删除标签；
- 达到 3 项时禁用输入框和添加按钮；
- 输入内容与任一已选标准或自定义菜系规范化后重复时，显示“不能添加重复菜系”；
- 标准菜系快捷按钮排除 `is_other=true` 的系统项；
- 载入旧的“其他 + custom_name”资料时，直接显示自定义名称并允许删除；
- 草稿、本人首次引导、本人资料、监护人/管理员代填以及营期问卷继续复用同一组件。

现有菜品自由输入、建议、版本冲突和撤权处理不变。

## 5. API 与服务规则

请求格式保持不变：自定义菜系仍发送系统“其他”的 `cuisine_option_id` 与实际 `custom_name`。因此无需新增公开字段或版本化 API。

当前通用校验会拒绝重复 `cuisine_option_id`，无法表达多个自定义菜系。调整后：

- Schema 层继续校验最多 3 项、自定义名称去重和菜品去重，但不在未知目录语义时拒绝重复菜系 ID；
- Service 在锁定并读取菜系目录后，允许 `is_other=true` 的选项重复出现；
- 每个“其他”选择必须携带非空且唯一的 `custom_name`；
- `is_other=false` 的标准菜系 ID 仍必须唯一，且不得携带 `custom_name`；
- 自定义名称与同次请求中的标准菜系名称规范化后也不得重复；
- 非法请求继续返回既有 422，且保持零偏好、零历史、零完成状态和零成功审计写入。

读取响应、历史快照和问卷快照结构均保持不变。

## 6. 数据库迁移

新增迁移 `0022`：

1. 删除 `person_food_preference_cuisines` 上覆盖所有行的 `(person_id, cuisine_option_id)` 唯一约束；
2. 新增仅约束 `custom_name IS NULL` 行的部分唯一索引，继续在数据库层禁止同一人员重复选择标准菜系；
3. 保留 `(person_id, custom_normalized_name)` 唯一约束，禁止同一人员重复自定义名称；
4. 保留位置主键和 1–3 位置检查，数据库仍不能写入第 4 项；
5. downgrade 在恢复旧唯一约束前先检查是否存在同一人员的多个“其他”行；若存在则明确拒绝降级，不丢弃或合并业务数据。

迁移只改变约束，不重写已有记录。当前只有一个自定义“其他”的资料继续有效。

## 7. 统计、导出与历史

统计和导出继续使用 `custom_name` 优先、标准名称其次的既有展示规则。三个直接输入的菜系分别计数，不合并为“其他”。版本历史和营期问卷继续保存每项的菜系 ID、名称快照和自定义名称，因此历史可读性和不可变保护不变。

## 8. 验证范围

### 8.1 后端

- Schema 接受同一“其他”ID 携带 2–3 个不同名称；
- Service 接受三个不同自定义菜系并按位置返回、保存历史；
- 重复自定义名称、重复标准菜系、标准菜系携带自定义名及“其他”缺名称均返回 422 且零写入；
- 标准与自定义名称交叉重复被拒绝；
- 迁移 upgrade/downgrade、部分唯一索引和不兼容 downgrade 保护；
- 统计、XLSX 与 CSV ZIP 对三个自定义菜系分别计数。

### 8.2 Web

- 目录只有“其他”时仍直接显示可用输入框；
- 点击和回车均可添加，最多 3 项，添加后清空输入；
- NFKC、空白及 Unicode casefold 重复被拦截；
- 自定义标签只显示实际名称；
- 标准快捷选项与直接输入共用上限；
- 注册引导、个人资料、代填和问卷草稿入口行为一致；
- 360、768、1024、1440 宽度无横向溢出，触控目标和读屏标签保持可用。

## 9. 部署与回滚

先在本地工作树完成迁移、API 和 Web 测试，再构建 NAS 镜像。部署时只执行 `alembic upgrade head` 并重建 API/Web 相关容器，不删除 PostgreSQL、媒体或其他 Docker 卷。升级失败时保持当前服务和数据库卷，禁止 `down -v`；应用切换前必须完成迁移与健康检查。
