# ReactionX 执行状态未知归档补充设计

状态：用户已确认本补充设计并要求实施。只补齐已复现的
“服务器发出开始、电脑尚未保存该命令即崩溃”边界，不改变评分或设备协议。

## 目的与已选方式

保留原始证据，又不让确实无法形成成绩的异常运行永久卡住待处理队列。
用户选择：超管确认关灯、填写原因并二次确认后，归档为
“执行状态未知，需复测”，不生成成绩、不排名，保留原记录和审计。

考虑的两种方式：继续保留无法核销的待处理状态，安全但长期占用队列；
增加独立的异常归档，增加一个受控流程但能够结束核对。用户选择后者。
不能替代为“未执行”“取消成功”“成绩已保存”或补造空成绩。

## 操作与限制

- 仅有效超级管理员，且仍有该人员/运行的处理权限，能看到并操作入口。
- 仅针对原连接器恢复后提供的受保护证据：本地没有已接受的开始命令、
  没有刺激或成绩记录；服务器确实发出过开始，且没有任何结果回执。
  这只能证明执行状态未知，不能断言没有执行。
- 必须由原连接器对本轮原设备完成实际关灯，并让服务器记录确认；
  网页勾选或收到 HTTP 请求成功，均不能替代设备确认。
- 后台展示异常事实，填写处理原因，先发起再二次确认；权限或证据变化
  会使确认失效，需要重新核对。正常训练、已有成绩、无关人员或设备均拒绝。
- 原因和两次操作记录进入审计。重复提交只返回原归档，不重复生成记录。
  归档不删除原运行、命令、原始证据，不改变被测者、操作人或连接器归属。
- 原连接器收到并持久化服务器的匹配归档凭据后，才将该条从“未处理”
  配额中移出。保留独立异常归档记录，不能伪装成成绩回执，也不能仅靠
  本地按钮清除待处理记录。
- 归档后不自动续跑、不自动开始新测试。原队列之外的数据和正常补传不变。
  如后来发现与归档矛盾的新证据，保留并明确拒绝自动覆盖，另行人工核对。

## 实施边界与验收

沿用现有 ERP 权限、审计和连接器用户级保护；新增独立的非成绩归档协议，
不修改 B1 成绩包、评分、排行榜或原手动训练规则。具体字段、状态、锁顺序
和接口由实施计划确定，不能利用普通成绩上传授权代替本流程的授权。

验收使用真实 ERP 接口和本地持久化，加模拟灯具：覆盖崩溃复现、错误权限、
缺少关灯、已存在开始/刺激/结果、二次确认失效、重复请求、丢失回执及重启。
只有匹配凭据落盘后释放该条待处理配额，其他原始资料保持不变。
Windows 真机和实体灯仍按用户安排后续验收，模拟通过不代表正式开放。
