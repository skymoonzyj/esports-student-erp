## 1. 目标

本阶段建立 ERP 的房间目录、实时房态、入住、预约、调房、退房、问题房和实名住宿导出能力。
系统以 ERP PostgreSQL 为唯一住宿业务主记录，面向学员、教练、生活老师、其他工作人员和已建立账号的
临时访客，满足当前内部运营和未来公安住宿报送的基础要求。

完成后必须满足：

1. 管理员可以维护多栋楼、楼层、单人房、双人房、三人房、自定义容量房和功能间。
2. 管理员或获权人员可以从账号人员名单中选择住户，填写入住时间，并选择长期居住或计划离开时间。
3. 房态由有效住宿记录实时计算，不依赖人工维护的“已占用”布尔值。
4. 系统强制阻止超额入住、同时间段异性同住、同一人员重叠入住和不可用房间入住。
5. 当前有人入住的房间显示红色；空闲且可分配的房间显示绿色；部分入住仍为红色，同时显示绿色剩余容量。
6. 房间性别由当前或目标时间段的首位住户决定；房间清空后恢复未指定。
7. 问题房保留原房型和容量，记录问题备注；已有住户时允许立即标记并产生待调房提醒。
8. 调房保留完整历史；计划离开、退营、退费或营期结束均不自动释放房间，实际退房必须二次确认。
9. 学员和监护人只能查看本人或家庭范围内的房间、期限和室友姓名，不得查看室友敏感资料。
10. 授权人员可以生成可审计的 Excel/CSV 实名住宿名单；正式公安在线接口后续通过版本化适配器接入。
11. Web、Windows、macOS 和手机浏览器使用同一套响应式页面。

## 4. 核心设计决策

### 4.1 房间目录与住宿记录分离

采用“房间目录 + 独立住宿记录”模型：

- 楼栋、楼层和房间保存相对稳定的物理资料。
- 住宿记录保存人员在某个时间段内使用某个房间的业务事实。
- 当前房态、当前性别、当前人数和剩余容量均由房间状态与住宿记录投影得到。
- 不在房间表写入 `occupant_1`、`occupant_2` 或 `is_occupied`。
- 不创建床位表，避免系统声称能够管理现实中未编号的床位。

该模型可以保留历史、支持未来预约和多栋楼，并能在数据库事务中可靠处理并发分配。

### 4.2 房型与问题状态分离

房型描述容量语义：

- `single`：单人房，容量固定为 1。
- `double`：双人房，容量固定为 2。
- `triple`：三人房，容量固定为 3。
- `custom`：自定义容量住宿房，容量至少为 1。
- `functional`：功能间，容量固定为 0，默认不可分配。

问题房不是房型。任意住宿房都可能临时进入 `problem`，同时保留原房型和容量。问题解除后不需要重新
选择房型。

### 4.3 房间有两个独立状态轴

房间同时具有：

1. **核对状态**：`pending_verification`、`verified`。
2. **服务状态**：`available`、`problem`、`maintenance`、`disabled`。

“可分配”是派生结果，不单独写库。只有满足以下全部条件时房间才可分配：

- 已核对；
- 服务状态为可用；
- 房型不是功能间；
- 容量大于目标时间段内的有效人数；
- 目标人员与目标时间段内其他住户性别一致；
- 不存在其他业务拦截。

### 4.4 性别由有效住户决定

房间不保存长期固定的男房或女房属性：

- 当前没有实际住户时，当前性别显示“未指定”。
- 首位实际住户决定当前显示为“男住”或“女住”。
- 后续异性入住由服务端强制拒绝。
- 最后一位住户实际退房后，当前性别恢复“未指定”。
- 未来预约按各自重叠时间段独立计算性别；同一房间可以在不重叠的未来时间段分别安排男性和女性。
- 入住人员性别只读取注册账号关联的 `Person.sex`，入住表单不得提供临时修改性别的入口。

### 4.5 账号人员名单是唯一入住来源

所有入住对象必须拥有有效人员档案和有效登录账号。学员、教练、生活老师、其他工作人员和临时访客都
从账号人员名单选择。住宿模块不提供临时手输姓名或创建无账号住客的旁路。

临时访客如学员家长，必须先在人员中心建立完整实名人员档案、访客档案和账号，再安排临时入住。

## 5. 领域模型

### 5.1 楼栋 `housing_buildings`

至少保存：

- `id`
- `code`：稳定代码，例如 `4`、`A`、`9`、`5`
- `name`：显示名，例如 `4幢`
- `display_order`
- `is_active`
- `notes`
- 创建、修改时间

楼栋停用只影响新分配，不删除历史。存在房间时不得物理删除楼栋。

### 5.2 楼层 `housing_floors`

至少保存：

- `id`
- `building_id`
- `number`：可排序的楼层数字
- `name`：例如 `二楼`
- `display_order`
- `is_active`
- `notes`
- 创建、修改时间

同一楼栋内楼层数字唯一。存在房间时不得物理删除楼层。

### 5.3 房间 `housing_rooms`

至少保存：

- `id`
- `floor_id`
- `room_number`：规范化显示房号
- `normalized_key`：用于同楼栋内唯一性检查
- `room_type`
- `capacity`
- `area_square_meters`
- `verification_status`
- `service_status`
- `notes`
- `version`：并发编辑版本
- 创建、修改时间和最后修改人

房间使用稳定 UUID 关联历史；修改房号或楼层不会改写过去住宿记录保存的审计快照。房型与容量必须满足
固定约束：单人房为 1、双人房为 2、三人房为 3、功能间为 0、自定义容量房至少为 1；面积可以为空，
填写时必须大于 0。存在当前住户或未来有效预约时：

- 不得把容量降到目标时间段最大人数以下；
- 不得改为功能间；
- 不得停用或移动楼层；
- 不得通过编辑绕过调房或取消预约流程。

### 5.4 问题记录 `housing_room_issues`

每次标记问题房创建独立记录：

- `id`、`room_id`
- 必填 `description`，描述具体问题
- `reported_at`、`reported_by_user_id`
- `status`：`open`、`resolved`
- `resolved_at`、`resolved_by_user_id`
- `resolution_note`

同一房间最多存在一条未解决问题。创建未解决问题后房间服务状态进入 `problem`。问题房已有住户时：

- 住户继续计入实际占用；
- 房间仍按“有人入住”显示红色；
- 额外显示问题标识和待调房提醒；
- 禁止新增入住和新预约；
- 不自动退房或自动调房。

解决问题时必须填写处理说明。房间只在已核对且没有其他不可用原因时恢复 `available`。

### 5.5 住宿记录 `housing_stays`

至少保存：

- `id`
- `person_id`、`room_id`
- `stay_purpose`：`permanent`、`camp`、`temporary`
- `duration_mode`：`long_term`、`fixed_term`
- 可选 `cohort_id`
- 临时住宿必填 `visit_reason`
- `planned_check_in_at`
- 固定期限必填 `planned_check_out_at`；长期居住为空
- `actual_check_in_at`、`actual_check_out_at`
- `status`：`planned`、`checked_in`、`checkout_pending`、`checked_out`、`cancelled`
- `created_by_user_id`、`checked_in_by_user_id`、`checked_out_by_user_id`
- 创建备注、取消原因和版本

`planned` 记录是未来预约。`checked_in` 和 `checkout_pending` 记录构成当前实际占用。`checked_out` 和
`cancelled` 不再占用容量，但永久保留。

正式人员档案可以选择常住、随营或临时住宿用途。访客档案只能选择 `temporary`，不能被设置为常住或
随营；临时住宿必须是固定期限并填写计划离开时间和来访原因。

### 5.6 调房记录 `housing_transfers`

调房记录保存：

- `id`
- `person_id`
- `from_stay_id`、`to_stay_id`
- `transferred_at`
- 必填 `reason`
- `transferred_by_user_id`

旧住宿记录、新住宿记录和调房记录在同一数据库事务中创建或更新。不得先释放旧房后再尝试写入新房。

### 5.7 导入批次与报送批次

`housing_import_batches` 记录初始房间导入的文件摘要、导入时间、操作人、条目数和清洗摘要。实现时把规范化
房间目录固化为可重复、幂等的种子数据；不依赖 `/Volumes` 中的原始文件，也不把原始 `.xls` 复制进仓库。

`housing_report_batches` 记录实名导出筛选条件、生成数量、操作人、用途及状态：

- `generated`
- `marked_submitted`
- `failed`

导出文件本身不长期保存在公开目录；业务主记录和审计保存在 PostgreSQL。

## 7. 时间与冲突模型

### 7.1 中国时间

所有 API 输入必须是带时区时间，数据库保存带时区时间戳。业务日期、表单默认值、筛选和计划任务统一按
`Asia/Shanghai` 解释，前端不自行用浏览器时区重新推导业务边界。

### 7.2 计划与实际时间

- 当前或过去时间可以直接确认实际入住，实际入住时间不得晚于当前时间。
- 未来时间只能创建 `planned` 预约。
- 到达计划入住时间不会自动写实际入住；授权人员必须确认入住，并重新校验全部约束。
- 固定期限到达计划离开时间后由调度任务转为 `checkout_pending`。
- `checkout_pending` 仍是实际占用，不释放容量。
- 长期居住没有计划离开时间，直到人工退房。

### 7.3 时间段规则

计划冲突按半开区间 `[planned_check_in_at, planned_check_out_at)` 计算；长期居住的结束时间视为无限远。
同一时刻上一段结束、下一段开始不构成计划重叠。

未来预约可以安排在当前定期住宿的计划离开时间之后，但到新住户实际入住时必须重新检查：如果上一位仍
是 `checked_in` 或 `checkout_pending`，新入住被阻止。这样既允许提前排房，也不会因未实际退房造成超住。

### 7.4 容量和性别投影

创建或修改预约时，系统在目标时间段内统计所有未取消的有效预约和实际住宿：

- 任一时刻人数不得超过房间容量。
- 任一重叠时间段只能存在同一性别。
- 同一人员在重叠时间段内只能有一条有效住宿记录。

实际入住时再次按当前数据库状态执行相同校验，不信任预约时的旧结果。

## 8. 房态投影、颜色与筛选

### 8.1 当前房态

当前房态使用 `checked_in` 和 `checkout_pending` 记录计算：

- `current_occupants`：当前实际住户数量。
- `remaining_capacity`：容量减当前实际人数，不小于 0。
- `current_gender`：无住户为未指定；有住户时取一致的人员性别。
- `has_future_reservation`：是否存在晚于当前时间的有效预约。

不得把未来预约计为当前入住，也不得因为存在未来预约提前把当前空房显示为红色。

### 8.2 颜色规则

- **绿色卡片**：当前无人、已核对、服务可用、住宿房且当前可分配。
- **红色卡片**：当前至少一名实际住户，包括 `checkout_pending`。
- **红色卡片 + 绿色容量标签**：当前有人，但仍有剩余容量并且没有其他不可用条件；标签显示
  “可继续入住 / 剩余 X 位”。
- **橙色问题标识**：问题房；如果已有住户，卡片仍以红色为主并叠加问题和待调房标识。
- **灰色卡片**：待核对、维修、停用或功能间。

所有颜色必须同时配套文字、图标和可访问名称，不能仅靠颜色传达状态。

### 8.3 筛选语义

顶部筛选包括：

- 楼栋、楼层、房号搜索。
- 单人房、双人房、三人房、自定义容量房、功能间。
- 男住、女住、未指定。
- 已入住、未入住、可入住、不可入住。
- 待核对、问题、维修、停用。
- 关联营期和人员类型。

筛选是独立轴并可组合：

- “已入住”表示当前实际人数大于 0。
- “未入住”表示当前实际人数为 0，无论房间是否可用。
- “可入住”表示当前还有容量且通过基础可分配条件。
- “不可入住”表示已满、待核对、功能间、问题、维修或停用。
- 部分入住且仍有容量的房间同时命中“已入住”和“可入住”。

## 9. 业务流程

### 9.1 核对初始房间

1. 管理员按楼栋或楼层查看待核对房间。
2. 管理员核对房号、房型、容量、面积和服务状态。
3. 如果已有住户，先补录现有实际住宿记录。
4. 管理员确认房间；系统记录操作人和时间。
5. 只有已核对且满足其他条件的房间进入可入住集合。

“确认空房”与“补录住户后确认”都是显式操作，不允许初始导入自动把全部房间标为空闲。

### 9.2 手动安排入住

授权人员从房间详情或统一“安排入住”入口操作：

1. 从有效账号人员名单搜索并选择人员。
2. 系统展示姓名、人员类型和注册性别；手机号只显示掩码。
3. 选择住宿用途、入住时间和长期/固定期限。
4. 固定期限填写计划离开时间；随营可从营期默认入住/退房时间带出并允许获权人员修改。
5. 临时访客填写来访原因。
6. 服务端验证账号、实名完整性、监护关系、房间状态、容量、性别和时间冲突。
7. 当前/过去入住写实际入住；未来入住建立预约。
8. 写入住宿记录和审计事件后刷新房态。

### 9.3 实名与未成年校验

确认入住时，入住人必须具备：

- 有效账号；
- 姓名、手机号、邮箱、身份证、出生日期和性别；
- 与账号一致的有效人员档案。

学员是否未成年按计划入住日期判断；直接补录实际入住时按实际入住日期判断。未满 18 周岁的学员必须
拥有至少一名在该日期有效、成年、实名完整、账号有效且具备监护人角色的监护人。复用现有
`GuardianReadinessPolicy`，不得在住宿模块实现第二套年龄算法。

### 9.4 确认实际入住

确认未来预约的实际入住时：

- 实际时间不得在未来；
- 预约仍须属于该人员和房间；
- 重新锁定人员与房间并检查容量、性别和其他状态；
- 房间如已转为问题、维修、停用或仍待核对，确认失败；
- 成功后状态转为 `checked_in`，房态立即更新。

### 9.5 调房

1. 授权人员从当前住户选择“调房”。
2. 选择新房间、调房时间并填写原因。
3. 服务端同时锁定人员、旧房和新房，按稳定顺序避免死锁。
4. 校验新房容量、性别、状态和时间冲突。
5. 同一事务内结束旧住宿、创建新住宿和调房记录。
6. 旧房和新房房态同时刷新。

调房不执行退营二次确认，也不把旧记录删除。失败时整个事务回滚，人员继续保留在旧房。

### 9.6 标记和处理问题房

标记问题房时必须填写问题描述。系统允许已有住户的房间立即进入问题状态：

- 禁止新增入住和预约；
- 当前住户继续显示；
- 生成待调房提醒；
- 详情页提供逐人调房入口；
- 不自动终止任何住宿。

问题解决时填写处理说明并关闭问题记录。若仍有住户，可以恢复房间服务状态；住户无需重新入住。

### 9.7 退房与退营二次确认

- 固定期限到期只进入 `checkout_pending`。
- 长期居住由授权人员主动发起退房。
- 第一次操作选择实际离开时间并核对人员、房间和住宿记录。
- 第二次确认再次展示人员、房号、实际离开时间和释放后的容量。
- 确认后写 `actual_check_out_at`、转为 `checked_out` 并释放容量。

营期结束、报名取消、退营或退款只创建待退房提醒，不得直接调用释放房间逻辑。最后一位住户退房后，
当前房间性别立即恢复未指定。

### 9.8 取消未来预约

未实际入住的 `planned` 记录可以由获权人员取消，必须填写原因。取消释放未来容量，但不改变当前房态。
已经实际入住的记录不能通过取消入口结束，只能走退房或调房流程。

## 10. 权限与隐私

### 10.1 权限键

新增细分权限：

- `housing.read`：查看获准范围内房态和非敏感住户摘要。
- `housing.rooms.manage`：维护楼栋、楼层、房间、核对状态、房型和容量。
- `housing.stays.manage`：创建/修改预约及确认入住。
- `housing.transfers.manage`：执行调房。
- `housing.checkouts.manage`：执行退房二次确认及取消预约。
- `housing.issues.manage`：标记和解决问题房。
- `housing.reports.export_sensitive`：生成实名导出并维护报送状态，标记为敏感权限。

管理员角色获得全部全局权限。其他工作人员角色不自动获得住宿操作权限，由管理员逐项下发。

### 10.2 楼栋和楼层范围

现有 RBAC 增加 `building` 和 `floor` 对象范围，并同步更新数据库约束、策略类型、授权目录、标签和权限
预览。楼层范围隐含该楼层内房间；楼栋范围隐含该楼栋全部楼层和房间。拒绝规则优先于允许规则。

后端每次请求根据房间稳定 UUID 构造资源令牌；前端隐藏按钮不是安全边界。

### 10.3 本人和家庭范围

角色默认只授予：

- 学员：`housing.read` 的 `self` 范围。
- 监护人：`housing.read` 的 `family` 范围。

学员可查看自己的当前房间、入住期限和室友姓名。监护人可查看有效监护关系覆盖的学员相同信息；监护
关系未解除时，即使学员成年也继续按家庭范围展示。室友手机号、邮箱、身份证、出生日期和账号状态均不
返回家庭端。

教练、助教、生活老师、客服和其他员工只有在管理员授予相应权限及范围后才能查看或操作房态。

### 10.4 敏感数据

- 普通房态卡片只返回住户姓名、人员类型、住宿期限和必要状态。
- 手机号只在获权内部操作的人员搜索结果中掩码显示。
- 身份证等完整字段只进入获权实名导出，复用现有字段级解密机制。
- 房态、人员搜索、详情和导出响应统一 `Cache-Control: no-store, private`。
- 权限拒绝优先于资源存在性和业务校验，避免通过错误差异枚举人员、房间或预约。

## 11. API 与模块边界

### 11.1 后端

新增 `app.housing` 领域包，按职责拆分：

- `models`：楼栋、楼层、房间、问题、住宿、调房、导入批次和报送批次。
- `schemas`：房态投影、内部管理、本人/家庭页面和导出请求的最小模型。
- `access`：全局、楼栋、楼层、本人和家庭对象级授权。
- `inventory_service`：目录、核对、房型、容量和状态维护。
- `occupancy_service`：预约、入住、冲突、调房、退房和房态投影。
- `issue_service`：问题房和待调房提醒。
- `report_service`：实名导出和报送状态。
- `seed`：规范化初始房间目录。
- `router`：内部房态管理 API。
- `portal_router`：本人和家庭最小住宿 API。

统一挂载在版本化 `/api/v1` 之下。服务层承担事务、锁和业务校验；路由只处理认证、请求映射、响应隐私
和审计上下文。

### 11.2 前端

新增 `apps/web/src/housing`：

- 房态总览与统计卡。
- 楼栋/楼层筛选和房间卡片网格。
- 房间详情抽屉或详情页。
- 房间编辑、核对、入住、预约、调房、退房和问题处理表单。
- 实名导出与报送记录页。
- 本人/家庭住宿卡片。

路由至少包括：

- `/housing`：内部房态总览。
- `/housing/rooms/:roomId`：可直接打开的房间详情。
- `/me/housing`：本人及家庭住宿信息。

导航入口依赖服务端返回的实际能力，不根据职位字符串猜测权限。

## 12. 页面设计

### 12.1 房态总览

顶部显示：

- 房间总数
- 已入住、未入住
- 可入住、不可入住
- 问题房、待核对房
- 总住宿容量、当前人数、剩余容量和入住率
- 单人房、双人房、三人房及功能间数量

统计使用当前同一时间快照，响应返回 `as_of`，避免卡片和顶部数字使用不同时间计算。

### 12.2 房间卡片

卡片至少显示：

- 房号、房型、面积
- 当前人数/容量
- 男住、女住或未指定
- 当前住户姓名和住宿期限
- 未来预约提示
- 问题备注摘要和待调房数量
- 可访问的文字状态

点击后查看当前住户、未来预约、历史住宿、调房历史和问题历史。操作按钮按服务端返回的对象级
`allowed_actions` 显示，前端不只依赖登录时缓存的全局权限。

### 12.3 响应式

- 桌面端按楼栋/楼层显示多列房间网格和常驻筛选栏。
- 平板端减少列数，详情使用侧边抽屉或全宽面板。
- 手机端使用单列或双列卡片，筛选折叠为底部面板，表单按钮满足触屏尺寸。
- 小屏不得通过横向滚动隐藏入住、调房或退房关键操作。
- Windows、macOS 和手机浏览器共享同一功能，不创建平台专用业务分支。

## 13. 实名导出与报送状态

授权人员选择日期/时间范围、楼栋、楼层、营期和人员类型，并填写导出用途。导出包括：

- 住户姓名、手机号、身份证、性别、出生日期和人员类型。
- 楼栋、楼层、房号。
- 住宿用途、实际入住时间、实际退房时间或当前状态。
- 临时访客来访原因。
- 按入住参考日期仍未满 18 周岁的学员对应有效监护人姓名、手机号和身份证。

导出前重新校验入住、换房、退房和监护数据一致性。任一必填实名字段缺失时，返回明确的逐人员错误，
不生成表面成功但内容不完整的文件。

生成 Excel/CSV 后写入审计和 `housing_report_batches`。授权人员可以标记为已人工报送，填写报送时间和
备注。未来公安 API 适配器只消费同一报送批次和版本化导出投影，不直接读取内部表。

## 14. 并发、错误与审计

### 14.1 并发

创建/修改预约、确认入住、调房和退房时按稳定顺序锁定：

1. 人员；
2. 涉及的楼栋/房间（按 UUID 排序）；
3. 相关有效住宿记录。

锁内重新执行账号、实名、监护、房间、容量、性别和时间重叠校验。后提交的冲突事务失败并提示刷新，
不得依赖前端先前看到的剩余容量。

### 14.2 公开错误码

至少定义：

- `housing_account_required`
- `housing_profile_incomplete`
- `minor_guardian_required`（复用现有语义）
- `housing_room_not_verified`
- `housing_room_unavailable`
- `housing_capacity_conflict`
- `housing_gender_conflict`
- `housing_person_time_conflict`
- `housing_stale_version`
- `housing_checkout_confirmation_required`
- `housing_room_has_active_stays`
- `housing_export_incomplete`

错误详情不得包含无权查看的人员姓名、完整手机号、身份证或隐藏房间信息。

### 14.3 审计

记录以下允许、拒绝和失败事件：

- 楼栋/楼层/房间创建、修改、核对、停用。
- 预约、取消、确认入住、调房、退房和二次确认。
- 问题房标记、解决和待调房处理。
- 房态敏感详情读取。
- 实名导出生成、失败和人工报送标记。
- 房态权限授予、拒绝和撤销。

审计元数据只保存安全标识、数量、范围和公开错误码，不保存身份证、手机号、问题描述全文或导出内容。

2. 171 间住宿房初始为待核对，17 间功能间可见但不可分配。
3. 管理员可以确认房间，也能增加楼栋、楼层、三人房和自定义容量房。
4. 授权人员可以从有效账号人员名单安排当前入住或未来预约，并选择长期或固定期限。
5. 未授权人员、无有效账号人员、实名不完整人员和未就绪未成年学员不能确认入住。
6. 单人房、双人房、三人房和自定义容量房均拒绝超住；同一人员不能重叠入住。
7. 首位住户决定目标时间段性别，异性被拒绝，最后一位实际退房后当前性别恢复未指定。
8. 空闲可用房为绿色；有人入住为红色；部分入住红色并显示绿色剩余容量。
9. 已入住、未入住、可入住、不可入住筛选语义独立，部分入住房同时命中已入住和可入住。
10. 问题房必须保存问题备注；已有住户时可立即标记、禁止新增并显示待调房提醒。
11. 调房原子完成并保留历史；失败不会丢失旧房住宿。
12. 到期、退营、退费和营期结束均不自动释放房间，二次确认退房后才释放。
13. 管理员可按楼栋/楼层下发权限，显式拒绝始终优先。
14. 学员和监护人只看到本人/家庭住宿及室友姓名，不看到室友敏感资料。
15. 获权人员能生成完整且可审计的 Excel/CSV 实名名单，并维护人工报送状态。
16. Windows、macOS、平板和手机页面完成同一核心操作。
17. 本地非 Docker 质量门禁通过；Docker/NAS 和公安在线 API 仍明确未启用。

## 17. 实施拆分建议

房态与实名导出适合拆成三个顺序单元，每个单元单独计划、实现和验收：

1. **房间目录与房态基础**：数据模型、RBAC 范围、初始种子、核对、统计、筛选和房间卡片。
2. **入住生命周期**：账号人员选择、预约、入住、性别/容量校验、问题房、调房、退房和家庭查看。
3. **实名导出与收尾**：Excel/CSV、报送状态、完整审计、全量响应式 E2E 和阶段文档。

第二单元的本地管理 UI、隔离启动器和完整四视口浏览器门禁均已完成。实名导出仍属于第三单元；公安在线
API 继续延期。

第一单元完成前不得宣称住宿模块可用；第三单元和全部本地门禁完成前不得宣称阶段 3 完成。

## 18. 最终确认

- 房态核心采用“目录 + 独立住宿记录”，不使用住户快照字段。
- 本阶段不建立床位表。
- 功能间保留显示，默认容量 0、不可分配。
- 问题房是状态并保存必填问题备注。
- 所有住户必须来自有效账号人员名单。
- 房间性别由首位有效住户自动决定，清空后重置。
- 部分入住房为红色并带绿色剩余容量标签。
- 初始房间全部先核对，不假设全部空闲。
- 退房必须二次确认。
- 本阶段只本地开发，Docker/NAS 最后统一处理。
