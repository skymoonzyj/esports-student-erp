# 自助注册、账号认领与监护人邀请设计

- **日期：** 2026-08-14
- **状态：** 本地实现与完整门禁已完成
- **所属总体规格：** `2026-07-26-esports-student-erp-design.md`
- **前置迁移：** `0016_camp_evaluation_surveys`
- **实现迁移链：** `0017_self_service_registration` → `0018_registration_review_metadata` → `0019_guardian_invitation_tokens` → `0020_registration_review_pending_guardian` → `0021_registration_review_candidate_binding`

## 1. 背景与目标

当前 ERP 只允许有权限的内部人员先创建人员档案，再由管理员开通手机号登录账号并交付临时密码。系统已经
具备实名人员、手机号密码登录、成年判断、监护人就绪、独立监护人账号、拒绝优先 RBAC、餐饮问卷引导和
招生报名等内部能力，但没有公开自助注册、联系方式验证、既有档案安全认领或自助找回密码。

本单元建立一个与正式 ERP 会话隔离的注册系统。学员、监护人、工作人员申请人和临时访客均可使用已验证的
手机号或邮箱申请基础账号；系统在不创建重复人员、不泄露账号存在性和不放宽未成年监护规则的前提下，安全
认领或创建人员档案。工作人员只能申请身份，管理员审核前不得获得工作人员权限。

本单元完成后，注册人能够得到可重复、可恢复、可审计的结果；项目选择、订单和真实支付仍属于下一单元。

## 2. 范围

### 2.1 包含

- 手机号或邮箱二选一注册，填写哪个就验证哪个。
- 手机号或邮箱加密码登录；同一账号补充第二个已验证标识后，两者均可登录。
- 手机和邮件验证码的统一服务边界、本地测试发送器、限流、过期和单次消费。
- 姓名、身份证、出生日期、性别的必填与结构化一致性校验。
- 既有无账号人员档案的安全认领，以及资料冲突的后台处理队列。
- 学员、监护人、工作人员申请、临时访客四种注册主要用途。
- 未成年学员注册完善区、监护人邀请、监护人本人实名确认和正式开通。
- 成年学员可选的监护人邀请，不阻止成年学员立即开通。
- 工作人员身份申请、管理员审核和既有 RBAC 权限下发衔接。
- 已验证手机号或邮箱的密码找回；成功后撤销全部旧会话。
- 版本化资料真实性确认、个人信息处理确认和监护关系确认。
- 仅邮箱账号的基础 ERP 访问，以及报名、付款和入住前的已验证手机号门禁。
- 仅监护人身份之外的账号与现有可跳过餐饮问卷引导衔接。
- 注册后台、工作人员申请后台、敏感资料分权、审计和四视口响应式页面。
- PostgreSQL 迁移、并发约束、API/Web 测试和本地非 Docker E2E。

### 2.2 不包含

- 项目、营期、普通班或菁英班的公开选择。
- 订单创建、支付跳转、支付回调或微信/支付宝适配器。
- 真实短信或邮件服务商接入；首版只提供通用接口和本地测试发送器。
- 第三方实名认证、身份证照片上传或 OCR。
- 公安在线报送、录像/GPU、天赋测评、Docker/NAS 或生产数据迁移。
- 用户自行授予教练、生活老师、客服、管理员或其他工作人员权限。

## 3. 已确认的业务规则

1. 成年学员完成联系方式验证和实名资料后立即开通，不需要管理员预审。
2. 未成年学员必须至少有一名有效成年监护人完成独立账号注册并确认关系，才能开通正式 ERP 账号。
3. 付款成功后进入待分配并由管理员确认的既有规则不变；本单元不创建付款。
4. 所有人均可自助申请基础账号，但注册时只能选择一个主要用途：学员、监护人、工作人员申请或临时访客。
5. 多身份只能在开通后由管理员按既有人员与 RBAC 流程追加。
6. 工作人员申请人可以选择拟申请身份并填写说明；审核前只有基础账号，不拥有任何工作人员权限。
7. 注册时手机号和邮箱二选一，填写并验证其中一个即可；姓名、身份证、出生日期和性别始终必填。
8. 仅邮箱注册的账号可以进入基础 ERP，但报名、付款和入住前必须补充并验证手机号。
9. 已验证联系方式和实名资料与既有无账号人员完全一致时，认领原人员档案；不得创建重复人员。
10. 既有人员已经拥有账号时，引导登录或找回密码，不创建第二个账号。
11. 手机号、邮箱或身份证命中不同人员，或者实名资料不一致时，进入管理员冲突处理，不自动合并。
12. 未成年学员等待监护人期间可以登录独立注册完善区，管理邀请和进度；不能进入正式 ERP、报名、评价或入住。
13. 未成年学员通过手机号或邮箱邀请监护人；监护人本人验证联系方式、完成实名资料并确认关系。
14. 成年学员可以自愿邀请监护人；该邀请不阻止本人开通，关系确认后沿用现有家庭范围权限。
15. 注册人不得代监护人设置密码或替监护人确认关系。
16. 首版只校验中国居民身份证格式、校验位、出生日期和性别一致性，不上传证件照片。
17. 注册和监护关系确认必须保存协议版本、确认时间和请求记录；普通日志不得包含身份证、验证码或完整联系方式。
18. 忘记密码支持已验证手机号或邮箱；重置成功后撤销账号全部旧会话。
19. 仅监护人主要用途的账号不进入餐饮问卷引导；其他注册账号沿用现有可跳过引导和持续待办。

## 4. 方案选择

### 4.1 采用：独立注册申请状态机

公开注册先写独立申请、验证、邀请和注册会话表。只有申请满足正式开通条件时，系统才在一个事务中认领或
创建 `Person`、`UserAccount`、登录标识、基础角色、用途资料、协议确认和审计。待监护的未成年人没有正式
ERP 会话，因此现有正式账号和业务接口不需要接受一种危险的“半开通账号”。

### 4.2 不采用：扩展正式账号状态

直接给 `user_accounts` 增加待验证、待实名和待监护状态，会要求所有现有 API 都正确识别每一种中间状态。
任一遗漏都可能让未完成注册的账号读取正式业务数据，且会与现有“待绑定未成年学员不能开通账号”的统一
就绪规则冲突。

### 4.3 不采用：立即创建账号后只依赖 RBAC

RBAC 适合正式账号的功能授权，不适合作为联系方式归属、实名冲突或监护人就绪的替代品。立即创建账号还会
放大重复人员、账号枚举和失败后半成品数据问题。

## 5. 模块与状态机

### 5.1 模块边界

新增 `app.registration` 后端包和 `apps/web/src/registration` 前端目录。注册模块可以调用身份、认证、监护人
就绪、RBAC、审计和餐饮引导服务的公开接口，但这些模块不得反向读取注册申请的内部状态。正式账号开通后，
人员、账号、关系和权限仍分别由现有模块作为唯一主记录。

通知发送通过两个小接口隔离：

- `VerificationSmsSender`：发送手机号验证码或邀请通知。
- `VerificationEmailSender`：发送邮箱验证码或邀请通知。

本地和自动化测试使用进程内测试发送器，只把验证码交给测试夹具，不把验证码写入 HTTP 响应、应用日志或
数据库明文字段。真实服务商适配器以后替换接口实现，不改变注册业务状态机。

### 5.2 申请状态

注册申请使用以下单向状态：

`draft -> contact_verified -> identity_completed -> ready_to_finalize -> finalized`

未成年学员在实名完成后进入：

`identity_completed -> pending_guardian -> ready_to_finalize -> finalized`

任何尚未完成的申请可以进入 `conflict`、`rejected` 或 `expired`。只有授权审核人员能从 `conflict` 处理为
`ready_to_finalize` 或 `rejected`；过期申请不能恢复，申请人必须重新验证联系方式并创建新申请。

正式开通是幂等操作。已经 `finalized` 的申请重复提交只返回同一个不含敏感信息的结果，不重复创建人员、
账号、角色或关系。

### 5.3 注册会话

联系方式首次验证成功后签发独立的 HttpOnly 注册会话。它使用与正式 ERP 会话不同的 Cookie 名称、令牌摘要
和依赖项，仅可访问注册申请本人、验证码重发、资料完善、邀请管理、协议确认和进度接口。

注册会话不能兑换成正式会话。正式开通后立即撤销全部注册会话，用户使用新账号登录接口建立正式 ERP 会话。

## 6. 数据模型

### 6.1 `registration_applications`

- `id`：UUID 主键。
- `primary_purpose`：`student | guardian | staff_applicant | visitor`。
- `state`：本设计冻结的申请状态。
- `verified_identifier_kind`：`phone | email`。
- `verified_identifier_digest`：标准化后使用 lookup key 计算的摘要。
- `verified_identifier_ciphertext`：加密联系方式，只供注册本人和获权审核人员使用。
- `password_hash`：使用现有 Argon2 密码服务；正式开通后清除。
- `full_name`、`identity_ciphertext`、`identity_digest`、`sex`、`date_of_birth`：实名申请快照。
- `matched_person_id`、`finalized_account_id`：安全认领和最终结果引用。
- `conflict_code`：仅保存稳定内部码，不保存自由文本证件信息。
- `expires_at`、`finalized_at`、`rejected_at`、时间戳。

申请表对已验证且未终结的联系方式摘要和身份证摘要建立并发保护；尚未验证的 `draft` 可并存，并在首次验证
成功时通过事务锁合并为一个有效申请。数据库约束与事务锁共同保证两个已验证请求不能同时认领同一个标识或人员。

### 6.2 `registration_verification_challenges`

- 目的：`registration | password_reset | guardian_invitation | add_login_identifier`。
- 标识类型和摘要、验证码摘要、过期时间、失败次数、最后发送时间、消费时间。
- 验证码有效 10 分钟，最多失败 5 次；成功后单次消费。
- 同一标识 60 秒内不能重复发送，并按标识摘要和请求来源摘要限流。

请求来源只用于安全限流并保存不可逆摘要；审计和普通日志不保存原始 IP。

### 6.3 `registration_sessions`

保存申请编号、会话令牌摘要、过期时间和撤销时间。删除申请敏感数据或正式开通时必须同步撤销相关会话。

### 6.4 `account_login_identifiers`

- `account_id`、`kind`、`identifier_digest`、`verified_at`、`verification_source`、`is_primary`。
- `identifier_digest` 全局唯一；每个账号至少一个已验证标识，且恰有一个主要标识。
- 原文不在本表重复保存；展示和通知从获权人员联系方式读取。

该表成为认证查询的唯一来源。现有账号的手机号登录摘要迁移为已验证手机号标识，来源标记为
`legacy_phone_login`；现有邮箱没有经过归属验证，不自动开启邮箱登录，用户验证后才新增邮箱标识。

迁移期间 `user_accounts.login_phone_digest` 和 `email_normalized` 改为可空并保留为兼容列，新代码不得写入或
依赖它们。旧手机号摘要可以暂留用于回滚核对；旧邮箱迁移到人员加密字段并完成一致性校验后必须置空，不能以
“兼容”为由继续保留明文。两个旧列待后续独立清理迁移再删除，避免本单元同时承担不可逆列删除。

### 6.5 邮箱隐私迁移

现有 `people.email` 是明文。本单元增加 `email_ciphertext` 和 `email_digest`，迁移并验证全部已有邮箱后清空旧明文
值。认证只使用登录标识摘要，业务展示只在已有权限允许时解密邮箱。API、审计和缓存继续使用明确字段白名单。

### 6.6 `guardian_registration_invitations`

- 学员申请或已开通成年学员、被邀请联系方式摘要、关系、是否主要监护人、状态和 7 天到期时间。
- 状态：`pending | accepted | revoked | expired`。
- 重发生成新邀请并立即撤销旧邀请；同一邀请重复接受不重复建立关系。
- 未成年学员可邀请多名监护人，但至少一名满足现有有效监护人规则即可开通。

监护人接受时调用现有监护关系服务，继续执行成年、实名、独立账号、监护人角色、日期范围和防循环校验。

### 6.7 `staff_identity_applications`

- `person_id`、申请的 `staff_type`、申请说明、状态、审核人、审核原因和时间戳。
- 状态：`pending | approved | rejected | withdrawn`。
- 同一人员同一工作人员类型同一时间最多一条待审申请。
- 批准时创建或更新 `StaffProfile` 并授予该身份的最低基础角色；额外权限继续由现有 RBAC 单独下发。
- 驳回不停用基础账号，历史不物理删除。

### 6.8 显式人员用途

现有身份服务把没有学员、工作人员或访客资料表的人员默认推断为监护人。该推断无法区分“独立监护人”和
“工作人员申请中”。本单元新增显式 `GuardianProfile`，并把现有无其他资料类型的监护人安全迁移进去。

正式开通时：

- 学员创建 `StudentProfile`，学员编号由系统生成且全局唯一，初始状态为 `draft`。
- 监护人创建 `GuardianProfile`；没有关系时仍是监护人，但没有任何家庭对象范围。
- 临时访客创建 `VisitorProfile`，注册表单必须填写访问原因。
- 工作人员申请人只创建基础人员和 `staff_identity_applications`；批准前不得创建 `StaffProfile` 或工作人员角色。

身份服务移除“无资料即监护人”的运行时默认，人员类型只由显式资料或关系返回。

### 6.9 `registration_consent_acceptances`

保存申请或账号、确认类型、协议版本、协议内容摘要、确认时间、请求编号和行为来源。监护人接受邀请时单独保存
监护关系确认。表中不保存身份证、验证码、完整联系方式或协议正文副本。

## 7. 正式开通与账号认领

### 7.1 新人员

实名和联系方式均无匹配时，在一个事务中创建 `Person`、用途资料、`UserAccount`、登录标识、最低权限
`registered_user` 角色、确认记录和审计。密码摘要从申请转入正式账号后立即从申请清除。

学员、显式监护人和访客可以在最低权限角色之外获得各自现有的基础角色；所有对象读取仍受本人、家庭关系或
明确资源范围约束。工作人员申请人只获得 `registered_user`，直到申请获批。

### 7.2 安全认领既有人员

自动认领必须同时满足：

- 身份证摘要只命中一个未删除人员。
- 已验证联系方式与该人员同类型联系方式一致，或该人员对应联系方式为空且没有被其他人员使用。
- 姓名、身份证、出生日期和性别规范化后完全一致。
- 该人员尚无正式账号。
- 申请主要用途与已有资料不冲突。

人员已有账号时，公开接口只返回通用“请登录或找回密码”结果。身份证、联系方式分别命中不同人员，命中已删除
人员，或者任一实名字段不一致时，申请进入 `conflict`，不自动修改现有人员。

### 7.3 冲突处理

拥有 `registration.review` 的人员可以读取脱敏冲突列表；查看完整候选资料还需要独立的
`registration.sensitive.read`。审核人只能在全部规范化实名字段一致后把申请绑定到既有人员，否则应先通过既有
人员资料更正流程处理，再重新运行匹配，或填写原因驳回申请。

冲突列表、公开错误和审计事件不返回“哪个字段属于哪个账号”等可用于枚举的信息。

## 8. 监护人流程

### 8.1 未成年学员

年龄继续按 `Asia/Shanghai` 业务日期和现有 18 周岁规则动态判断。实名完成时仍未满 18 周岁的学员进入
`pending_guardian`，注册完善区提供：

- 查看通用进度和已发送邀请的脱敏目标。
- 重发尚有效邀请。
- 撤销或更换待确认邀请。
- 修改并重新验证自己的手机号或邮箱。
- 重新确认更新版本的协议。

完善区不返回正式 ERP 导航、项目、评价、住宿、人员名单或其他账号信息。

监护人可以是新注册人，也可以是现有账号。接受邀请前必须使用受邀联系方式完成验证；新监护人还必须填写
完整实名资料和密码。监护人确认关系并通过现有就绪校验后，系统锁定学员申请、创建关系并重新计算状态。至少
一名有效监护人存在时，学员进入 `ready_to_finalize` 并正式开通。

### 8.2 成年学员

成年学员在实名完成后立即开通。其可选邀请使用同一监护人确认流程，但不影响账号状态；关系生效后，监护人
沿用既有家庭范围查看权限，直到关系结束或到期。学员成年不会自动解除关系。

## 9. 登录、补充联系方式与找回密码

登录请求字段改为通用 `identifier`。服务端先规范化为手机号或邮箱，再计算摘要查询
`account_login_identifiers`。错误、限流和耗时路径保持统一，不向未登录用户区分“不存在、已停用或密码错误”。

正式账号可以在个人资料中新增第二种联系方式。新增标识必须先通过对应验证码，且摘要未被其他账号占用；成功
后在同一事务中更新人员联系方式、登录标识和审计。

仅邮箱账号拥有基础 ERP 访问。招生报名确认、付款创建或归属、住宿安排和实名报送在业务写入前调用共享的
“已验证手机号”门禁；缺少时返回稳定 `verified_phone_required`，不产生业务行或成功审计。

找回密码按手机号或邮箱发送验证码。无论标识是否存在，公开响应均相同；只有真实账号的有效验证码可完成
重置。重置事务更新密码、清空失败计数、撤销全部正式会话和注册会话，并写入安全审计。

## 10. 工作人员申请与权限

工作人员申请可选择 `coach`、`life_teacher`、`customer_service`、`administration` 或 `other`，并填写 2–500 字
说明。申请人无法请求具体权限或资源范围。

后台能力分离为：

- `registration.review`：处理普通注册状态和脱敏冲突。
- `registration.sensitive.read`：查看处理所需的完整实名资料。
- `staff_identity_applications.review`：批准或驳回工作人员身份。
- 既有 RBAC 管理权限：在身份批准后另行授予具体功能和资源范围。

超级管理员拥有上述能力，也可以分别下发。客服默认不拥有任一注册审核或敏感资料能力。批准工作人员申请不能
顺带授予超出最低身份角色的权限。

## 11. 页面与交互

### 11.1 公开页面

- `/register`：选择主要用途和手机号/邮箱。
- `/register/verify`：发送与验证验证码。
- `/register/profile`：密码、实名资料、用途专属字段和协议确认。
- `/register/guardian`：未成年完善区及监护人邀请。
- `/register/status`：通用结果、冲突处理中或工作人员申请状态。
- `/forgot-password`：手机号/邮箱验证码和新密码。

登录页增加“注册账号”和“忘记密码”，登录输入标签改为“手机号或邮箱”。返回地址继续使用现有白名单规则，
不得让公开注册参数形成开放重定向。

### 11.2 分步体验

所有页面共用同一响应式表单状态机：1440 和 1024 桌面端使用居中卡片，768 平板和 360 手机端使用单列布局。
步骤切换保持已验证状态，但浏览器本地存储不保存身份证、密码、验证码或完整联系方式。

身份证输入后可以辅助填充出生日期和性别，但两个字段仍明确展示并由用户确认；服务端始终重新校验，不能信任
前端派生结果。

公开错误只说明下一步操作，例如重新输入、等待验证码、登录、找回密码或等待管理员处理。内部候选人员编号、
账号状态、字段命中来源和审核备注不得出现在公开页面。

### 11.3 开通后的入口

正式开通后首次登录：

- 仅监护人主要用途直接进入基础工作台。
- 学员、工作人员申请人和访客进入现有可跳过餐饮问卷引导。
- 餐饮问卷跳过不改变账号状态，首页继续显示既有待办。
- 工作人员申请人在工作台看到自己的申请状态，但看不到审核人内部备注或其他申请。

## 12. 安全、隐私与保留

- 验证码只保存带服务端密钥的摘要，永不保存或记录明文。
- 身份证、手机号和邮箱原文使用现有字段加密能力；匹配只使用域隔离 lookup 摘要。
- 登录标识摘要、人员联系方式摘要和验证码目标摘要使用不同 domain，不能跨用途直接关联。
- 注册、验证、登录和找回密码均按标识摘要与请求来源摘要限流。
- 公开接口对存在和不存在的账号返回相同结构，并走密码或验证码的等价验证路径。
- 注册会话和正式会话使用不同 Cookie 名、令牌 pepper、依赖和撤销表。
- 所有写接口使用现有 CSRF、防缓存和请求编号规则；验证码发送入口不返回 CSRF 可替代验证码。
- 未完成申请在最后活动 30 天后过期并清除实名密文、联系方式密文和密码摘要；只保留申请编号、终结状态、时间、
  非个人原因码和审计引用。
- 已完成申请在正式数据创建后立即清除密码摘要和临时联系方式密文，只保留正式人员/账号引用与最小审计字段。
- 邀请有效 7 天；撤销、重发、接受和过期均保留不含完整联系方式的历史。
- 普通日志、错误追踪、测试快照和机器可读验收结果均禁止身份证、验证码、密码、完整手机号或完整邮箱。

## 13. 错误、事务与并发

公开接口使用稳定错误码，但错误细节按访问能力裁剪：

- `verification_invalid_or_expired`
- `verification_rate_limited`
- `registration_action_unavailable`
- `registration_conflict_pending_review`
- `guardian_confirmation_required`
- `verified_phone_required`
- `staff_application_already_pending`

验证码消费、申请状态转换、人员认领、正式开通、监护关系确认、登录标识新增和密码重置都必须锁定相应摘要或
业务行。数据库唯一约束负责最终防线，服务层把并发冲突转换为稳定业务结果，而不是返回原始完整性错误。

正式开通事务必须原子创建或更新人员、用途资料、账号、登录标识、基础角色、确认记录和审计。任何一步失败，
不得留下半成品正式账号。失败事务外只允许按既有独立安全审计模式记录脱敏拒绝事件。

## 14. 迁移与兼容

`0017_self_service_registration` 在 `0016_camp_evaluation_surveys` 后执行，并完成：

1. 新增注册、验证码、注册会话、登录标识、监护邀请、工作人员申请、显式监护人资料和确认记录表。
2. 为人员邮箱增加加密值与 lookup 摘要，迁移并校验旧邮箱数据后清空旧明文值。
3. 把现有账号的手机号登录摘要回填为 `legacy_phone_login` 标识，不自动把未验证邮箱变成登录标识。
4. 把现有无其他资料类型的监护人迁移到显式 `GuardianProfile`，再移除运行时默认推断。
5. 把 `UserAccount` 旧手机号和邮箱列改为可空，让认证服务改读登录标识表；保留旧手机号摘要用于回滚核对，
   已迁移的旧邮箱明文必须置空。
6. 播种注册审核、敏感读取和工作人员申请审核权限，以及最低权限 `registered_user` 角色。
7. 更新 schema manifest 和迁移测试范围为 `0013 -> 0014 -> 0015 -> 0016 -> 0017`。

`0018_registration_review_metadata` 在注册申请中补充冲突审核决策、原因与审核时间；
`0019_guardian_invitation_tokens` 为对外邀请生成独立 256 位 Base64URL 令牌，数据库仅保存带域隔离的 keyed digest，后台管理 UUID 不再作为邀请凭证。升级到 `0019` 时撤销旧版待处理 UUID 链接并清除临时联系方式；存在监护邀请历史时拒绝降级回旧格式。
`0020_registration_review_pending_guardian` 扩展注册审核状态约束，使已审核通过但仍未完成监护确认的未成年冲突申请可以安全回到 `pending_guardian`；若已存在这类记录，降级会在修改约束前拒绝执行。

`0021_registration_review_candidate_binding` 为等待监护确认的审核结果增加候选人员外键与状态约束。升级无法从旧数据安全推断候选人员，因此遇到未绑定的已审核待监护申请会在 DDL 前拒绝；降级在仍有活动绑定时同样拒绝。监护确认最终只能开通本次审核固定的候选，候选漂移或账号停用会回到冲突状态且不产生正式业务写入。

升级必须先断言每个现有正式账号都能得到唯一手机号登录标识；发现重复或缺失时迁移失败并保持原 schema，不
静默生成占位联系方式。降级只在没有新式邮箱登录账号、邮箱唯一账号或未完成注册数据时允许，否则安全拒绝。

## 15. 测试与验收

### 15.1 单元和服务测试

- 手机号、邮箱、身份证规范化、domain 隔离摘要和掩码。
- 验证码 10 分钟边界、5 次失败、60 秒重发、单次消费和限流清理。
- 18 周岁、中国业务日期和身份证出生日期/性别一致性。
- 新人员、完全匹配认领、已有账号、跨人员命中、已删除人员和实名不一致。
- 未成年待监护、至少一名有效监护人、成年可选邀请和重复邀请确认幂等。
- 工作人员申请批准前零工作人员权限，批准后只获得最低基础角色。
- 手机或邮箱登录、补充第二标识、重复标识拒绝和密码重置撤销全部会话。
- 邮箱唯一账号在报名、付款和入住写入前得到 `verified_phone_required` 且零业务写入。
- 30 天申请清理和 7 天邀请过期不保留敏感原文。

### 15.2 PostgreSQL 与迁移测试

- 两个验证码请求竞争消费时只有一个成功。
- 两个申请竞争同一身份证、手机号、邮箱或既有人员时只有一个正式开通。
- 监护人重复确认和工作人员重复审批保持幂等。
- 失败事务不留下人员、账号、角色、关系或成功审计。
- 从空库升级到 `0017`，现有夹具升级，schema manifest，以及受保护降级拒绝。
- 邮箱明文迁移后旧列无残留，所有现有手机号账号仍可登录。

### 15.3 API 和隐私测试

- 存在、不存在、停用、冲突和无权目标的公开响应不泄露账号或人员存在性。
- 注册会话不能调用任一正式 ERP API，正式会话不能越权读取其他注册申请。
- 缺失、过期、撤销或错误范围的邀请返回等价私有错误且零关系写入。
- 所有 selector 状态覆盖缺失、删除、停用、不合格、拒绝和错误范围。
- API、审计、错误和日志扫描拒绝身份证、验证码、密码、完整手机号和完整邮箱。

### 15.4 Web 与四视口 E2E

在 `desktop-1440`、`desktop-1024`、`tablet-768` 和 `mobile-360` 覆盖：

- 手机号新注册和邮箱新注册。
- 安全认领既有无账号人员。
- 已有账号转登录或找回密码。
- 未成年完善区、邀请重发/更换、监护人新注册与确认、学员正式开通。
- 成年学员可选监护人邀请。
- 工作人员申请、管理员审批和权限即时生效/撤销。
- 邮箱账号基础访问、已验证手机号业务门禁和补充手机号后的解除。
- 仅监护人与其他用途不同的餐饮引导行为。
- 无横向裁切、被遮挡按钮、不可达错误提示或敏感 DOM/浏览器缓存数据。

### 15.5 完整本地门禁

- API 全量 pytest，PostgreSQL/并发测试零非规格 skip。
- Alembic 空库升级、兼容升级、schema manifest 和受保护降级测试。
- Ruff、mypy、Web Vitest、ESLint 和生产 build。
- 单一非 Docker 注册 E2E runner，使用隔离测试数据库和本地短信/邮件发送器。
- `git diff --check` 和独立规格、质量、安全审查。

## 16. 实施顺序与完成边界

1. 登录标识与邮箱隐私迁移。
2. 验证码、注册申请、注册会话和清理服务。
3. 实名匹配、安全认领和原子开通。
4. 未成年完善区与监护人邀请。
5. 工作人员申请与后台审核。
6. 通用手机号/邮箱登录、第二标识和找回密码。
7. 已验证手机号跨招生、付款和住宿门禁。
8. 响应式页面、四视口 E2E、完整门禁和文档。

只有上述门禁全部通过，才能表述为“自助注册本地实现完成”。该结论不表示项目选择、支付平台、真实短信/邮件
服务商、第三方实名认证、Docker/NAS 或生产部署已经完成。
