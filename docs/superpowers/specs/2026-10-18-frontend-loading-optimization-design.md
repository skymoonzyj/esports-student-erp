# ERP 前端加载优化设计规格

状态：用户已确认本规格；进入实施计划审阅，产品代码及线上配置尚未修改。

本轮减少登录和常用业务页面首次打开时不必要的下载与脚本执行，同时保持权限、表单、房态筛选和测试计分行为。顺序固定为：基线测量、发布更新保护、业务路由拆分、模块内部优化。完成本规格审阅后编写实施计划，再按已确认的协作方式开发。

## 1 范围与完成标准

适用于 ERP Web 的所有现有角色，不新增功能权限、业务接口或数据库迁移。登录、房态、人员中心是主要测量入口；财务、资产、报表、评价及天赋测试是主要延迟加载对象。桌面和手机浏览器都要验收。

已确认的目标是降低冷启动成本，不承诺未经测量的倍数提升。登录冷启动所需 JavaScript 总压缩传输量以相同测试环境下减少至少 40% 为首轮目标。若未达到，交付中列出实际差异和剩余依赖，不能宣称目标完成；功能和安全检查仍全部适用。

不做框架重写、CDN 接入、Service Worker、离线业务、新设备权限、登录协议修改、增加权限缓存时长或把个人资料写入浏览器持久存储。原方案的有限预加载扩展已于 Task11 获用户限定批准为以下两个常用页的代码准备；仍不得在登录后自动下载所有模块。

## 3 可重复性能基线

使用同一源码基线、生产构建方式、浏览器版本、压缩方式和虚拟业务数据比较前后结果。登录匿名测量不访问真实账号；已登录的房态和人员页面仅使用隔离环境的合成账号和数据库。

测量矩阵：桌面 1440×900、手机 390×844；分别记录首次空缓存打开、同版本暖缓存重开、模块首次进入和再次进入。主要可重复慢网条件为下载 10 Mbps、上传 2 Mbps、RTT 150 ms、CPU 4 倍减速；记录未限速结果作为补充。每组至少 7 次有效运行，保留中位数、最慢值及失败次数，不删除慢样本来改善结果。

冷启动的资源统计从导航开始，持续至页面真实可操作后 2 秒；汇总所有实际请求的首屏脚本和样式，包含公共分包、modulepreload 和自动预取。发布版本检查若在此期间发起也计入请求。登录、房态、人员页面的可操作标记必须对应可使用的控件及已完成的必要授权状态，不能以占位画面替代。

报告至少包含：压缩响应体总字节、请求数、FCP／LCP、可操作时间、脚本执行及长任务、模块首次进入耗时、资源错误和业务错误。完整查询参数、Cookie、密码、验证码、姓名和证件内容不进入性能报告或可发布目录。报告只记录资源类别、公开资源路径、聚合时间和数量。

## 4 发布更新保护

### 4.1 缓存与版本识别

当前 HTML 与公开的最小版本标识文件使用 `Cache-Control: no-cache`，错误响应不得变成长期缓存。版本标识只含非敏感的构建标识，必须与运行中的前端构建对应；不包含内部地址、凭据或业务数据。哈希静态资源保持 7 天 immutable 缓存，缺失资源返回真实 404，不回退成 HTML。

仅在动态资源加载失败或用户明确检查更新时查询版本标识，不增加每次路由跳转的同步请求，也不将版本检查置于正常登录必经的阻塞路径。

### 4.2 旧资源保留

历史资源随新的 Web 镜像携带，不增加共享持久卷，不依赖飞牛功能。每次最终镜像仍以干净的 Nginx 基础镜像构建，不能以上一版生产镜像为父镜像持续叠加。

保留集合为当前构建的全部公开资源，以及满足以下任一条件的已成功发布历史资源集：刚被替代的上一版、被替代时间距本次发布不超过 7 天的版本。7 天从该版本退出活跃服务时计算，避免长期未发布后立刻删除用户仍在使用的文件。原有版本首次纳入时按本次替代时间开始计算。

候选镜像中全部可服务构建资源的去重、未压缩实际字节数上限为 512 MiB，包含当前版及保留集；同路径同内容只计一次。超限或磁盘不足时，候选发布在初始化媒体、迁移或切换服务之前失败，不静默删除保留窗口内的资源。过期且不是上一版的集合可在下一次构建候选镜像时剔除，不在运行镜像中按天删除；清理不得删除当前运行镜像、数据库、备份或任意宿主路径。

只从部署锁内已核实的活跃 Web 容器对应的不可变镜像 ID 提取构建产生的公开资源，不按可变 tag 找镜像，也不从宿主工作树或任意目录收集。活跃标记、容器和源码发布身份不一致时拒绝继续。使用镜像 ID、发布标识、资源清单、长度和 SHA256 建立对应关系；禁止符号链接、硬链接、特殊文件、路径越界和同名异内容，读取和解包期间同样限制字节数。首次启用允许从这个确定的旧镜像生成一次受限资源清单；之后缺少清单或校验失败不能退回无清单扫描模式。HTML、环境文件、源码、source map、日志、测试凭据和运行数据不能进入历史资源集。

资源合并到当前 `/assets/` 下，仍只提供当前 HTML。每个历史集合保留完整依赖，包括旧主入口、共享分包及 CSS，不能只挑路由文件。维护清单放在不可公开访问的位置，记录资源归属及替代它的成功发布标识。新镜像构建时尚不知道激活时间，立即前驱始终保留；后一次构建结合该替代版本的已核验激活记录计算期限。时间记录缺失、关联不匹配或异常时不得提前过期，保守保留并受容量门禁约束。失败候选不得成为下一次发布的历史来源。

历史资源作为独立受校验的派生构建输入，记录前驱 Web 镜像 ID、资源清单摘要及最终 Web 镜像 ID，不能声称已被原源码摘要覆盖。受控构建上下文与源快照分离，相关临时目录由发布脚本创建、验证和清理，不进入源码打包或恢复源码归档。最终镜像在激活前再次验证资源字节、集合完整性及容量。保留窗口保障静态文件可用，不承诺旧前端与以后改变的业务接口永久兼容。

### 4.3 备份与发布证据

继续走实际启动仓库的 `scripts/deploy-nas.sh --source`，不得用临时复制或 Docker 命令替代正式发布。`--source` 不会自动换成源目录内的另一份启动脚本；实施脚本和实际启动入口若不同，分别检查和测试本次必需改动，保留现有差异。增加发布能力版本契约，源要求资源保留而实际入口未提供该门禁时拒绝发布。

现有备份保存 Web 镜像 ID，适合保全镜像内的旧资源；新验收还须验证恢复后的 Web 镜像包含当前及保留资源，并核对清单、字节与响应。数据库恢复成功不能替代静态资源恢复证明。旧备份保持兼容：不把缺少新资源保留证明的历史归档误记为已完成这项验证。

候选构建、资源校验、健康检查或规定的备份／恢复验证失败都阻断完成声明。沿用现有前向恢复及数据保护规则，不为前端回退而恢复数据库。域名、HTTPS 18080、密钥和业务数据卷保持不变。

## 5 加载失败交互

新增统一的页面模块加载边界，但不合并网络错误、授权错误和业务错误。网络故障显示可重试提示；确认服务器构建标识与本地不一致时显示可更新提示；无法确认版本时不能声称会话失效或强制退出。

监听动态导入失败并配合页面级错误边界，不无条件调用 `location.reload()`。成功显示的页面外壳保持稳定；局部面板加载失败只影响面板，不能清除父页面表单。

“重试加载”只针对失败模块，不重新创建 AuthProvider、QueryClient 或整个 Router。需要应对 React／浏览器对失败模块的缓存；不能承诺每次原地重试都会重新下载，也不通过任意查询参数复制公共模块实例。如果重试仍失败，保留中文说明并提供用户主动刷新。主动刷新前明确提示未保存内容会丢失，由用户确认后进行；不自动持久化敏感草稿。

账号切换、退出或撤权仍按原逻辑立即清理私有数据。避免加载闪动不能成为保留失效权限页面的理由。

## 6 业务路由拆分

保留稳定的认证、轻量路由定义、权限守卫及公共界面。登录页不静态依赖完整后台工作台；进入已认证区域时再加载工作台，进入具体业务域时加载对应页面。

按人员、房态、招生教学、资产采购、财务分成、评价、设置运维、报表和天赋测试组织加载边界。保留现有 URL、菜单名称、跳转目标和权限要求。公开注册、忘记密码、激活页面各按入口需要加载，不随登录页一次加载全部步骤。

先抽离被公共界面引用的轻量路径常量、查询键和类型，避免从完整页面模块导入这些对象。保持一个运行时的认证上下文和 QueryClient，不使用每个路由单独创建 React 或认证副本的机械分包策略。公共依赖是否独立拆分，以真实资源图、缓存稳定性和重复代码检查为依据。

`lazy` 声明位于模块顶层，正常渲染不重建组件类型。Suspense 范围以业务内容／面板为主；工作台侧栏和布局不因切页反复卸载。已有权限守卫的卸载、隐藏及重新验证策略逐一保留，不统一改成保留旧数据。

Task11 性能定位后的限定机制例外：仅 `HousingOverviewPage` 与 `PeoplePage` 在现有顶层模块工厂选择 controlled-pending，不创建新的叶级 Suspense。获准挂载后由 effect 启动资源加载，pending 是普通加载内容而非抛出 Promise，页面／查询仍待资源成功后才挂载。工厂只缓存组件类型、稳定快照和单次在途尝试；当前 props/context 由当前已授权树提供，不能缓存旧账号元素。复用原 `ModuleLoadError`、显式 JS 重试、CSS sticky 失败及 `ModuleBoundary`；卸载／撤权不因代码迟到而复活页面。其他路由、AppShell、面板与游戏保持默认 React.lazy/Suspense。此例外须经原 14 项诊断及完整性能门禁验证，不能由单元通过推断性能达标；不改变权限、筛选 revision、HTTP no-cache 或认证请求。

Task11 后续 throttled 生产诊断确认这两页仍有 CSS gate→page import 串行网络阶段，因而仅两页追加并行启动例外：沿原有限 `lazyPages` 包装器同时启动原 CSS gate 与当前页面 import，立即观察页面拒绝，但必须先确认 CSS 成功再交付页面组件。两者均失败时，无论先后均优先 sticky CSS 失败，CSS 失败后晚到 JS 不产生未处理拒绝、挂载或查询；JS-only 仍只允许显式重试。代价是获准请求的页面可能在 CSS 完成前求值，不代表提前挂载或预取；其他页面、面板与游戏仍 CSS→import 串行。真实测试须证明 CSS pending 时确有页面网络请求但无页面 DOM／查询，释放后实际资源重叠且 CSS-before-mount；保留真实 guard／身份生命周期验证。此候选不声称修复其余脚本排队、断言轮询或 no-cache 成本，280 门槛不变。

业务 CSS 随模块加载，公共排版与控件样式保留在基础层。检查不同进入顺序下样式优先级，不能依赖某个无关页面恰好先加载，也不删除动态类名对应样式。

Task11 用户批准的常用页修订：已认证 layout effect（含会话恢复，不含匿名／强制改密）可准备 PeoplePage 与 HousingOverviewPage 的代码及既有静态 CSS 闭包。People 严格使用当前全局 people.list；Housing 使用现有 global/scoped housing.read 且当前账号既有 portal capability 成功、非 fetching/error、housing_management_available=true。复用同一 controlled 工厂的 start、组件身份、重试与 CSS gate，不增加 auth/context 查询、第二缓存或预取注册表。准备不挂页面、不发 catalog/overview/list/count 私有查询、不保存账号／props／数据；权限和当前 props 仍由实际导航决定，晚到代码不复活已移除树。后台失败保持静默，只有获准导航才显示原恢复边界。

该修订提前应用 CSS 的实际副作用须验收：people.css 的 subtleStatus 仅在 peoplePage/personDetailPage，formSection 仅在 personFormPage/assistedPersonForm，两个 formSubmitError 规则仅在 personFormPage/guardianPanel/assistedPersonForm 下生效，使用 :where 保留 specificity 与声明值；Accounts/Permissions/Assets 不因提前准备改变错误或提示样式，合法 owners 保持原样。其他页面／游戏仍按进入时加载。既有 14case／38phase 被动诊断保留时序与 ready 判据，静态资源完整性按 setup+first 联合检查，并记录两页资源有限分类、实际 bytes/requests、分段及整文档 ScriptDuration；不得把移入 setup 的工作称为消失。API-login 后 goto 的 setup 不冒称表单登录端到端。原 280 collector、基线、7 次样本、2 秒 settle、profile 和比较阈值不变，旧 final-3 的 24PASS/16FAIL 原样保留；仅两个 throttled warm-login 的 revalidation 成本有用户单独接受说明，不豁免其他失败。

Task11 有限打包候选：仅将现有 Housing 四个纯图标叶模块 download/filter/pencil/trash-2 与 AppShell 十二个叶模块 activity/calendar-days/chevron-down/message-square-text/plane-takeoff/wallet-cards/mail/shield-check/sliders-horizontal/user-plus/user-round/x 合为一个 `authenticated-icons` 共享块。采用当前 Rolldown 的精确模块选择器与 `includeDependenciesRecursively:false`；不合整个 lucide/vendor、不设置全局 minSize、不移动 helper/React/Auth/Query、业务/API/日期/CSS，不增加预取或改变传输。首个使用者可能附带其余纯图标（预算约6KB未压缩，需记录实际产物），故要求构建图证明16叶恰一真实 final manifest/dist 文件、登录静态闭包不增加这些叶／领域实现、helper仍在原位置、无静态循环或重复运行时身份、CSS ownership不变。既有14case/38phase诊断与完整280仍是独立后续门禁，分组本身不保证排队或<=10%目标已解决。

## 7 模块内部优化

天赋测试 1 先按页隔离，再按项目加载八个游戏。历史和报告页面不加载游戏实现。游戏开始按钮只有在必要代码、样式和布局就绪后才可用；保留音频的用户手势要求，加载时间不计入响应、计时或成绩，不改变随机、评分、提交和中断规则。

代建档案的申请与审核复用页面可共享分包，管理直建及所属人员列表独立加载，不为很小的包装组件强行制造额外请求。人员详情的纠正面板按实际打开时加载，避免共享表单经其他入口重新进入登录依赖图。

其他大型编辑、打印及报表面板按实际显示条件拆分。拆分前后功能、导出格式、幂等键生命周期及返回路径不变。保留已存在的天赋测试 2 延迟加载，不把其三维渲染器误计为登录首屏节省量。

## 8 状态与安全不变量

- 房态筛选 provider 保留账户隔离和现有存活范围；只保留筛选值，不增加房间记录、选中人员或弹窗内容的持久缓存。
- 普通聚焦回归、模块加载和查询刷新不清空原本可以保留的表单、步骤或验证码输入；账号变更和撤权必须清除。跨路由草稿持久化仍不属于本轮。
- 审核编辑版本、管理直建幂等键和登录异步响应代次保持原生命周期，不因加载包装组件重复提交或接受过期响应。
- 不修改 `/auth/me`、CSRF、会话恢复、注销屏障、角色重验和服务器权限边界；菜单代码按需加载不构成新的授权机制。
- 不通过删除权限检查、延长敏感查询缓存、隐藏错误或改变测试业务断言来满足性能目标。
- 原生 iOS 待验收源码继续与 NAS 隔离。手机浏览器通过不能标成 App／软键盘／真机通过；不新增证书、签名或手机操作授权。

## 9 验收与交付

| 类别 | 必须验证的结果 |
| --- | --- |
| 冷启动 | 同条件统计全部首屏资源，报告是否达到 JavaScript 至少减少 40% 的目标；对比可操作时间与长任务 |

| 数据安全 | 无效会话、撤权、切账号、迟到响应仍受控；未保存表单、房态筛选和编辑版本按原规则保留或清理 |
| 测试与媒体 | 八个游戏及现有三维／听声项目的资源准备、开始、中断、提交正常，加载不进入计分 |
| 样式与兼容 | 桌面和手机多种进入顺序无布局跳变；保持既定浏览器兼容边界，不将浏览器模拟替代原生验收 |
| 恢复 | 当前和历史静态资源随 Web 镜像恢复，校验清单和公开响应；无业务数据恢复覆盖 |
| 上线 | 实际脚本成功、活跃发布和镜像一致、公开 HTTPS 健康及静态哈希一致，规定备份／恢复通过 |

执行 Web 全量测试、类型构建和 lint；新增依赖图／体积预算、模块加载失败、部署资源保留及发布脚本测试。按实际影响运行认证、权限、注册激活、房态和人员浏览器回归；涉及后端业务改动时扩展对应 API 检查。本轮不计划修改后端业务，不能以性能名义扩大范围。

按阶段进行实现和独立复核，正式发布只使用验证过的源码。先完成更新保护与路由拆分，再实施模块内部优化；每阶段都报告完成项、实际性能和剩余问题，不能把所有脚本拆成小文件就称为优化完成。

## 10 依据与下一步

采用现有 React 的组件延迟加载机制，并保持组件类型稳定，见 [React lazy](https://react.dev/reference/react/lazy)。动态导入在发布后可能因旧文件缺失而失败，需要结合 HTML 缓存和错误恢复处理，见 [Vite Load Error Handling](https://vite.dev/guide/build.html#load-error-handling)。两者用于实现机制，不替代本项目性能及权限验收。
