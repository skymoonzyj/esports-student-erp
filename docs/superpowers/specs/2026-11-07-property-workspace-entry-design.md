# 物业导出与工作台审批入口

日期：2026-11-07。用户已回复“按此实施”，授权按上一条推荐分工直接开发及同步 NAS；不再追加设计确认。

## 目标与边界

- 房态页“物业基础导出”仅在账号包含物业角色且具备有效基础导出权限时显示。兼任物业也适用；仅有行政/超管角色不显示这块专用入口。原有普通/敏感导出入口、接口授权、角色种子均不改。
- 房态总览不再放物业变更申请/审批列表。工作台增加“物业变更审批”，只向服务端确认具有审批权限的账号显示；未授权者不读取申请列表。审批范围仍按房间有效权限与显式拒绝判断，不能按角色名推测授权。
- 房间详情保留物业提交变更、查看本人各状态申请、撤回本人待审申请；不在房间详情执行审批。审批放在工作台完成，非本人、版本冲突、审核后生效、审计等既有保护保持不变。
- 不改变房态、统计、保洁、房卡业务规则，不修改真实人员或线上权限，不开放普通管理员审批，不新增依赖或数据库迁移。

## Approaches

采用用户确认的“专用导出按物业身份显示、审批搬到工作台、提交留在房间详情”。仅搬动现有混合组件会把兼任者的本人申请与审批列表混合，因此复用服务和组件、明确区分视图，而不复制独立流程。

不采用撤销行政/超管导出接口权限的方式：用户要求的是专用入口显示，不是收紧其他现有业务能力。不建设新审批系统或大改工作台布局。

## 实施选择

### 用户追加：行政变更不审核

2026-11-07 用户明确补充“行政提交的房态变更不需要审核”，作为当前已授权实施的规则修订，不再请求重复确认。

- 行政及超管复用现有房间直接编辑接口，按当前房间实际 `allowed_actions.edit` 显示编辑入口，保存立即生效。房间详情补齐现有 RoomDialog 入口；不新建一套保存流程，不伪造自审。问题房仍使用现有上报/解决问题流程。
- 新建物业申请与历史申请生命周期资格分离：新增 `can_create_request`。仅有效物业提交者、且不兼任行政/超管、且没有该房间直接管理能力时可新建待审申请。行政/超管即使兼任物业也走直接编辑；直接管理被拒绝时不退回申请来绕过拒绝。
- 旧 `can_submit_changes` / `can_submit` 继续服务于历史申请可读、撤回及审批复核，行政旧待审申请仍可处理但不自动通过、不删除。submitted 视图使用该生命周期资格与本人条件，默认 all 保留原谓词。
- 新客户端不向直接管理者显示待审提交表单；旧客户端误向 proposal POST 提交时服务端拒绝并明确提示使用直接编辑，不生成待审记录或直接改房间。后端保留全部直接编辑的锁、版本、容量/入住冲突、权限复核及审计。

- 能力接口新增 `show_basic_export`，由服务端计算 `property` 角色存在且 `can_export` 为真；旧三项能力语义不变。前端缺少新字段时按不展示处理。
- 列表增加可选 `view=all|submitted|review`，默认 `all` 保留旧行为。submitted 仅本人且在当前可提交房间范围；review 仅当前可审批房间范围。筛选先于计数与分页；不通过客户端过滤当前页实现。
- 工作台以服务端 `can_review` 门控，列表使用 review 视图；房间详情使用 submitted 视图。审批列表可以展示授权房间内的历史/本人申请，但本人申请不出现审批动作，也不在工作台提供撤回/提交动作。
- 权限核验中的旧数据不展示；换账号、角色/权限变更、范围变更、错误和异步响应保持隔离。无房态读取能力的工作台用户不请求房态目录或物业能力，不出现错误提示。
- 沿用 A/B 样式、分页、中文反馈；通过/驳回后刷新审批列表及相关房态缓存，不跳转回房态页。

## 验收与发布

覆盖物业、行政、超管、普通管理员、兼任、显式拒绝、范围化审批、无房态角色；验证隐藏入口且不请求私有列表、本人提交/撤回保留、不能自审、角色变化后的迟到下载不触发。

运行全部受影响房态 API/服务/数据库/单元测试与权限/工作台交叉回归、真实隔离浏览器流程、完整前端回归和静态检查；不将此前全后端结果当作本次证据。独立复核后使用 `NAS_SSH_PORT=202 scripts/deploy-nas.sh --source "$PWD"` 发布并核验版本/健康/备份恢复。保留当前外部托管工作树，不提交、重置或覆盖已有改动。
