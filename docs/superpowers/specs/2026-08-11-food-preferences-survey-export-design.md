# 人员饮食偏好、营期问卷同步与统计导出补充设计

- **日期：** 2026-08-11
- **状态：** 书面规格已确认（含注册后可跳过引导）
- **所属总体规格：** `2026-07-26-esports-student-erp-design.md`
- **所属评价规格：** `2026-07-30-teaching-evaluation-center-design.md`
- **影响计划：** `2026-08-09-camp-evaluation-surveys.md`、`2026-08-09-stage2-local-acceptance.md`

## 1. 背景与目标

营期评价问卷需要新增“喜欢的菜系”和“最喜欢的菜”两类问题。问卷中的偏好描述目标报名对应的学员，
不是填写问卷的监护人本人。与此同时，饮食偏好属于人员长期资料：每个有账号的人员应能修改自己，
有效监护人应能修改关系内学员，获权管理人员应能修改任意人员；没有账号的人员由后台维护。

后台需要提供稳定的菜系统计、菜品统计和人员明细，并允许拥有独立批量导出权限的人员在“仅学员”与
“所有人员”之间选择，按需包含停用或历史人员，导出 XLSX 或 CSV ZIP。

本设计采用独立饮食偏好模块作为主记录。营期问卷保存提交时的不可变快照，并在同一事务内把确认后的
偏好同步回学员当前资料。该边界避免把人员资料绑死在问卷中，也使没有参加青训营的员工、监护人和访客
仍能维护饮食偏好。

账号创建后还需要提供一次餐饮问卷引导。除“仅监护人身份”的账号外，所有普通个人账号在首次进入系统时
看到该问卷；允许跳过并正常使用 ERP，但首页持续显示待办，直到本人完成确认。服务账号不参与该流程。

## 2. 范围

### 2.1 包含

- 后台可维护的标准菜系字典及不可删除的“其他”选项。
- 每个人最多 3 个喜欢的菜系和 3 个最喜欢的菜。
- 菜品自由填写、规范化精确去重和不带人员身份的自动补全。
- 人员当前饮食偏好、乐观版本和追加式历史。
- 本人、有效监护人及获权管理员的读取和修改。
- 营期问卷预填、必填校验、并发防覆盖、不可变快照和资料同步。
- 学员或所有人员统计、有效或含历史人员筛选、XLSX 和 CSV ZIP 导出。
- 独立权限、拒绝优先对象授权、缓存撤权、安全审计和四视口页面。
- 注册后可跳过的餐饮问卷引导、账号级完成状态及首页持续提醒。

### 2.2 不包含

- 食物过敏、禁忌、疾病、营养或其他医疗信息。
- 菜品配料、制作步骤、采购、排餐、库存或外部菜谱链接。
- 基于相似词或机器学习的模糊菜名合并。
- 自动把个人偏好转换成食堂菜单或采购计划。
- Docker、NAS、生产备份恢复或真实数据迁移。

## 3. 已确认的业务规则

1. 喜欢的菜系和最喜欢的菜均最多 3 项。
2. 营期问卷提交时至少填写 1 个菜系和 1 个菜品；个人资料在问卷外允许暂时为空。
3. 菜系来自后台字典；管理员可新增、排序和停用，已使用项不能删除。“其他”为始终有效的系统项，
   选择后必须填写自定义菜系名称。
4. 菜品允许自由填写，并根据系统中已有的规范化菜品名称提供自动补全。
5. 菜品只保存名称，不保存配料或做法。
6. 问卷中的偏好属于被评价学员。学员和每个有效监护人的问卷彼此独立，各自保存提交时的偏好快照。
7. 问卷预填学员当前偏好；提交或唯一一次问卷修订时，在同一事务内同步学员当前资料。
8. 本人可修改自己，有效监护人可修改关系内学员，获权管理员可修改全部人员；无账号人员由后台维护。
9. 后台导出可选“仅学员”或“所有人员”。默认只含当前有效人员，可显式包含停用或历史人员。
10. 注册后餐饮问卷允许跳过；跳过不写完成状态，也不阻止进入 ERP，首页持续显示待办。
11. 引导适用于学员、教练、生活老师、客服、其他员工、管理员及拥有账号的访客；仅监护人身份和服务账号
    不参与。账号同时具有监护人与学员、员工或访客身份时仍需填写。
12. 首次本人确认要求至少 1 个菜系和 1 个菜品；完成后仍可在个人资料中改为 0–3 项，完成状态不会重置。
13. 管理员或监护人代填不能替代账号本人确认；已有偏好只用于首次问卷预填。

## 4. 方案选择

### 4.1 采用：独立规范化模块、当前状态与不可变历史分离

菜系字典、人员当前偏好、偏好历史、问卷快照和导出审计分别承担单一职责。当前偏好使用规范化关联行，
历史和问卷保存完整快照。该方案能在数据库层约束最多 3 项，支持可靠统计、并发防覆盖和长期审计。

### 4.2 不采用：直接在 `people` 保存两个 JSON 数组

JSON 数组开发较快，但无法自然维护菜系字典外键、位置约束、历史版本和稳定统计；应用层漏校验时容易出现
第四项、重复项或已停用菜系。

### 4.3 不采用：只在营期问卷保存再投影到个人资料

该方案会使人员资料依赖是否参加过营期，也无法覆盖员工、访客和未参加营期的监护人，不符合“所有个人
资料均可随时维护”的要求。

### 4.4 采用：账号级完成标记与可跳过待办

在 `user_accounts` 保存一次性的完成时间，而不是通过“当前偏好是否存在”推断。注册成功后进入独立引导页；
跳过只做前端导航，不产生数据库写入，首页依据服务端状态显示持久待办。本人成功提交 1–3 个菜系和 1–3 个
菜品后，在同一事务内保存偏好并设置完成时间。

不采用“存在偏好即完成”，因为管理员可能在注册前代填；也不采用每次登录强制弹窗，因为用户已明确允许
跳过。完成标记与当前偏好分离后，后续清空或修改偏好不会重新触发注册问卷。

## 5. 迁移顺序与模块边界

饮食偏好是营期问卷的前置依赖，应独立于问卷先交付：

1. 新增迁移 `0015_food_preferences`，创建菜系字典、人员当前偏好、当前关联行和偏好版本历史，增加账号完成时间，
   并播种权限。
2. 原营期评价迁移顺延为 `0016_camp_evaluation_surveys`，问卷版本增加饮食偏好快照字段。
3. 阶段 2 总验收的迁移往返范围相应更新为 `0013 -> 0014 -> 0015 -> 0016`。

饮食偏好服务位于身份/人员边界，不依赖评价服务。营期问卷服务通过明确的调用接口，在调用方事务内锁定并
更新偏好；偏好模块不能反向创建、修改或查询营期问卷。

## 6. 数据模型

### 6.1 `food_cuisine_options`

- `id`：UUID 主键。
- `name`：展示名称，去首尾空白后 1–40 字符。
- `normalized_name`：NFKC、折叠连续空白并 `casefold` 后的唯一键。
- `sort_order`：非负整数。
- `is_active`：是否可供新选择。
- `is_other`：系统“其他”项标记；全库恰有一条且不能停用或删除。
- `created_by_user_id`、`updated_by_user_id`、时间戳。

已被当前偏好或任一历史/问卷快照引用的菜系不得删除。普通项可停用；停用后不出现在新选择列表，但旧资料、
历史、问卷和统计继续显示保存的名称快照。

### 6.2 `person_food_preferences`

- `person_id`：关联 `people.id` 的主键，`RESTRICT` 删除。
- `version`：从 1 开始递增的乐观锁版本。
- `updated_by_user_id`、`updated_at`。
- `source`：`profile_self`、`profile_guardian`、`profile_admin` 或 `camp_survey`。

人员尚未填写时可以不存在该行；首次保存空偏好没有意义，服务不创建空记录。

### 6.3 当前菜系与菜品

`person_food_preference_cuisines`：

- `(person_id, position)` 唯一，`position` 只能为 1、2、3。
- `cuisine_option_id` 关联菜系字典。
- `cuisine_name_snapshot` 保存选择时显示名。
- `custom_name` 与 `custom_normalized_name` 仅在选择“其他”时允许且必填，长度 1–40。
- 同一人员不能重复选择相同菜系；“其他”的自定义规范名也不能重复。

`person_food_preference_dishes`：

- `(person_id, position)` 唯一，`position` 只能为 1、2、3。
- `display_name` 为去首尾空白、折叠连续空白后的名称，长度 1–40。
- `normalized_name` 使用 NFKC、空白折叠和 `casefold`；同一人员内唯一。

自动补全只返回不带人员信息的规范化菜品展示名，按当前使用人数、名称和稳定键排序；不进行模糊合并。

### 6.4 `person_food_preference_versions`

- `(person_id, version)` 唯一，版本必须连续递增。
- 保存完整菜系与菜品 JSON 快照、来源、操作者和创建时间。
- 版本行禁止更新和删除；数据库触发器保护不可变性。
- 自定义菜系与菜品正文保存在业务历史中，不复制到通用审计元数据。

当前关联行可在受控事务中替换；任何成功变化必须先追加新版本。提交的规范化内容与当前内容完全一致时，
服务返回当前版本，不创建重复历史。

### 6.5 `user_accounts.food_preferences_onboarding_completed_at`

- nullable、带时区时间；空值表示本人尚未完成注册后餐饮问卷。
- 仅本人成功提交注册后餐饮问卷时写入，和偏好版本在同一事务提交。
- 一旦写入不因后续偏好修改、清空、角色变化或监护关系变化而自动清除。
- 管理员、监护人或其他获权人员代填资料不得写入该字段。
- 是否需要引导还要结合人员类型：仅监护人身份和服务账号始终为 false；多身份账号只要同时是学员、员工或
  访客，即按普通个人账号判断该字段。

### 6.6 营期问卷快照

每个 `camp_survey_version` 增加：

- `favorite_cuisines`：1–3 项闭合 JSON，每项保存字典 UUID、名称快照及可选自定义名。
- `favorite_dishes`：1–3 个规范化后的展示名。
- `food_preference_version`：同步成功后的人员偏好版本。

问卷历史不引用人员当前关联行。后续资料修改、字典改名或停用都不得改写旧问卷。

## 7. 规范化与校验

- 所有文本先执行 Unicode NFKC，再去首尾空白并折叠内部连续空白。
- 菜品和自定义菜系用 `casefold` 后的值判断重复；保留用户确认的展示形式。
- 不自动把“宫保鸡丁”和“宫爆鸡丁”等近似名称合并。
- 个人资料接受 0–3 个菜系和 0–3 个菜品；注册后首次本人确认和营期问卷均接受 1–3 个菜系和 1–3 个菜品。
- 已停用菜系不能用于新增或替换，但在未改变该项的乐观更新中可继续保留；重新选择时必须改为有效项。
- “其他”缺少自定义名、非“其他”携带自定义名、重复项、第四项、空文本和超长文本均返回闭合验证错误。

## 8. 权限与隐私

新增稳定权限 ID：

| 权限 | UUID 尾号 | 默认授权 | 说明 |
| --- | --- | --- | --- |
| `food_preferences.read` | `000047` | admin global；student self；guardian family | 查看个人饮食偏好 |
| `food_preferences.update` | `000048` | admin global；student self；guardian family | 修改个人饮食偏好，敏感写权限 |
| `food_preferences.catalog.manage` | `000049` | admin global | 管理菜系字典，敏感权限 |
| `food_preferences.export` | `000050` | admin global | 批量统计与导出，敏感权限且仅支持 global |

普通个人账号可通过固定的 `/me` 接口读取和修改自己，不能借此指定其他人员；该 self 基线仍应用账号级 deny，
因此管理员可以撤销。客服、教练、生活老师和普通工作人员不获得读取他人或导出权限。管理员可通过现有
拒绝优先 RBAC 下发有限权限，但首版导出只接受 global 能力，因为导出范围没有营期或班级对象范围。

人员目标的授权顺序固定为：

1. 验证标准账号及操作级权限；完全没有该操作能力返回 403。
2. 使用 `self`、当前有效 `family`、精确 `person` 或 `global` 令牌授权人员目标。
3. 缺失、删除、已结束监护关系、错误人员和 deny override 对有操作能力的账号返回相同私有 404。

监护关系结束、账号停用或权限撤回后，下一请求必须重新判权。失败路径不得更新偏好、历史或通用审计。

## 9. API 契约

新增以下路径：

```text
GET    /api/v1/food-preferences/cuisines?include_inactive=
POST   /api/v1/food-preferences/cuisines
PATCH  /api/v1/food-preferences/cuisines/{cuisine_id}
GET    /api/v1/food-preferences/dish-suggestions?query=&limit=
GET    /api/v1/me/food-preferences
PUT    /api/v1/me/food-preferences
GET    /api/v1/people/{person_id}/food-preferences
PUT    /api/v1/people/{person_id}/food-preferences
GET    /api/v1/food-preferences/statistics?population=students|all_people&include_inactive=
POST   /api/v1/food-preferences/exports
```

菜系列表要求任意有效 `food_preferences.read` 能力，默认仅返回有效项；只有拥有
`food_preferences.catalog.manage` global 的账号可请求 `include_inactive=true`。菜系新增和修改要求
`food_preferences.catalog.manage` global。

所有响应使用严格闭合模型并返回 `Cache-Control: no-store, private`。人员读取和修改只返回目标人员 UUID、当前
版本、菜系和菜品；不返回手机号、身份证、账号、监护关系细节或修改人身份。

`PUT` 请求包含 `expected_version`、有序菜系列表和有序菜品列表。人员尚无偏好时期望版本为 0。成功后返回
递增版本；版本不一致返回类型化 409，响应不回显他人刚写入的正文，客户端需重新 GET。

菜品自动补全要求 `food_preferences.update` 的任意有效能力，只返回最多 20 个菜名，不返回人数、人员或来源。
空查询不返回全量字典。

`GET/PUT /me/food-preferences` 只允许活动的普通个人账号访问，目标永远取认证上下文中的本人，不能传人员 ID。
仅监护人身份账号可日常维护自己的偏好但不显示注册问卷。对于需要引导且完成时间为空的账号，首次 `PUT`
要求菜系和菜品各 1–3 项；成功时原子写偏好版本和完成时间。账号已完成后，同一路径按日常资料规则接受
0–3 项。显式 self deny 返回 403 且偏好、历史、完成时间和审计均零写入。

统计接口和导出接口均要求 `food_preferences.export` global。统计响应包含聚合与分页人员明细；导出请求体包含：

```json
{
  "population": "students",
  "include_inactive": false,
  "format": "xlsx",
  "purpose": "安排下一期营地餐食"
}
```

`purpose` 去空白后 4–200 字符。导出为一次性附件响应，不保存文件或偏好快照到服务器文件系统。

## 10. 人员资料与问卷数据流

### 10.1 注册后餐饮问卷

账号创建或首次登录后的服务端上下文返回 `food_preferences_onboarding_required`。它仅在以下条件同时满足时为
true：活动普通账号、人员具有学员/员工/访客中至少一种身份、完成时间为空，并且本人 read/update 未被 deny。
监护人多身份账号按其他身份参与；仅监护人身份和服务账号固定为 false。显式 deny 时不显示一个必然失败的
待办入口，撤销 deny 后下一次上下文请求会重新出现。

前端在注册成功后优先打开 `/onboarding/food-preferences`。页面读取本人当前偏好作预填，提供“完成填写”和
“稍后填写”两个动作：

1. “稍后填写”只进入安全主页，不调用完成接口；首页显示可再次进入的待办横幅。
2. “完成填写”要求菜系和菜品各 1–3 项，使用当前 `expected_version` 提交。
3. 服务锁定账号、本人 `Person` 与当前偏好，重新校验资格、deny 和版本。
4. 内容变化时追加偏好历史；无变化时复用当前版本；两种情况都可在同一事务首次写入完成时间。
5. 成功后刷新认证/门户上下文并移除待办。管理员或监护人代填、跳过、失败和版本冲突均不得写完成时间。

### 10.2 个人资料修改

1. 服务重新授权目标人员并锁定 `Person` 与当前偏好行。
2. 校验 `expected_version`、字典状态、数量、顺序和规范化重复。
3. 内容变化时追加完整历史版本并替换当前关联行。
4. 通用审计仅记录 `person_id`、旧/新版本、菜系/菜品数量和来源，不记录正文。
5. 事务成功后失效当前账号下该人员的饮食偏好、人员详情和统计缓存。

### 10.3 营期问卷同步

打开问卷时返回学员当前偏好及 `expected_food_preference_version`。问卷中的值始终描述该学员；监护人自己的
偏好不受影响。

首次提交或唯一一次问卷修订在营期问卷原事务中完成：

1. 重新验证问卷窗口、回答者身份和有效监护关系。
2. 按问卷既定锁序锁定营期、报名、问卷周期和 submission。
3. 锁定学员 `Person` 与当前偏好，比较期望版本。
4. 保存不可变问卷版本和工作人员评分。
5. 内容变化时更新学员当前偏好并追加偏好历史；相同内容复用当前偏好版本。
6. 同一事务写安全审计并提交。

任一步失败都回滚问卷、评分、偏好和审计。版本冲突返回 409，前端保留输入，读取最新偏好并要求回答者再次
确认。学员和各有效监护人的 submission 相互独立；后提交者只有基于最新偏好版本才能修改当前资料。

工作人员快照纠错后出现的补充评分只补充工作人员项目，不再次提交饮食偏好，也不修改人员当前资料。
问卷的一次修订机会用完或问卷窗口关闭后，个人资料中的饮食偏好仍可按日常权限随时修改。

## 11. 统计口径

`population=students`：

- 默认只含未删除且 `StudentProfile.status == active` 的学员。
- `include_inactive=true` 时加入 draft/inactive 学员和已软删除的历史学员。

`population=all_people`：

- 默认包含所有未软删除人员，不以是否有登录账号为条件。
- `include_inactive=true` 时加入已软删除人员；人员类型和各 profile 状态按快照显示。

所有统计在授权过滤后、同一数据库快照中计算。每个人只计一次：

- 总人数、已填写人数、未填写人数和填写率。
- 每个菜系的选择人数及占目标人数比例；同一人员同一菜系只计一次。
- 每个规范化菜品的选择人数及占目标人数比例；展示稳定的规范化展示名。
- 分页人员明细：姓名、人员类型、状态、菜系、菜品和最后更新时间；没有偏好显示“未填写”。

排序固定为人数倒序、规范化名称、稳定 UUID；人员按姓名、人员 ID 排序。统计不把历史版本重复计数，只读取
当前偏好；已软删除人员仅在显式包含历史时读取其最后一个当前状态。

## 12. 导出与审计

导出同时支持：

- XLSX：`人员偏好明细`、`菜系统计`、`菜品统计` 三个工作表。
- CSV ZIP：同名三个 UTF-8 BOM CSV 文件。

明细包含姓名、人员类型、人员状态、最多 3 个菜系、最多 3 个菜品和最后更新时间。未填写人员仍保留一行并
标记“未填写”。统计文件与页面使用完全相同的数据库快照和口径。

渲染全部在内存中完成。任何以 `= + - @` 开头的文本在 XLSX/CSV 中按安全文本写入，防止公式注入。服务器
生成固定格式文件名和正确 `Content-Disposition`，不得使用请求中的目的或人员姓名构造路径。

成功导出写一条安全审计，元数据只允许：population、include_inactive、format、person_count、filled_count、
文件 SHA-256、purpose 和 request ID。不得把菜系、菜品、姓名或导出文件内容写入审计、日志或错误响应。

无权限、权限刚撤销、请求无效、渲染失败或客户端断开时不得写成功审计。导出文件不落盘，不提供历史重下载；
每次导出都重新授权并生成当前一致性快照。

## 13. Web 页面

复用一个闭合的 `FoodPreferencesPanel`：

- 管理人员档案 `/people/:personId`：根据服务端动作显示只读或编辑状态。
- 本人入口 `/me/profile`：只投影本人可见的基础资料和饮食偏好，不开放通用人员管理能力。
- 家庭学习页 `/learning/:studentId`：有效监护人可在当前学员卡片中编辑饮食偏好。
- 营期问卷 `/evaluations/surveys`：预填当前偏好并显示同步说明、版本冲突恢复和必填提示。
- 注册引导 `/onboarding/food-preferences`：展示可跳过的本人餐饮问卷；完成前首页显示持久待办横幅。

后台新增：

- `/people/food-preferences`：统计、范围切换、包含历史开关、分页明细和导出 Dialog。
- `/settings/food-cuisines`：菜系新增、排序和停用管理。

组件使用标签式多选，菜系和菜品分别显示 `0/3` 至 `3/3`；达到上限后禁止继续添加但允许删除。所有按钮、
输入和标签删除操作具有可访问名称及至少 44px 触控区域。360px 使用单列，表格在 768px 以下变为带字段名
卡片，不产生横向滚动。

查询 key 按账号和授权 revision 隔离。权限、账号或监护关系变化时，先取消请求、移除当前账号的饮食偏好
缓存、关闭编辑/导出 Dialog，再导航到安全落点；旧账号数据不能在重新登录后闪现。

## 14. 错误与失败副作用

- 没有任何操作能力：403。
- 有操作能力但目标缺失、删除、无 family 关系、错误 scope 或 deny：相同私有 404。
- 偏好版本冲突：409 `food_preference_version_changed`，零写入。
- 已停用菜系、重复项、数量越界、“其他”缺自定义名或文本非法：422 闭合字段错误。
- 问卷窗口、回答者或修订次数错误：沿用营期问卷私有错误，不单独泄露偏好版本。
- 导出权限不足或刚撤销：不生成文件、不写成功审计。
- 数据库、渲染或网络异常：事务回滚；错误响应不回显菜品、菜系、人员或文件内容。
- 注册问卷跳过：正常进入主页且零写入；首次提交缺任一类偏好返回 422，保留输入且完成状态仍为空。
