# ERP 前端加载优化：常用公共代码合包补充规格

状态：用户于 2026-10-19 确认本书面补充规格，现进入补充实施计划审阅。当前不改产品代码、不运行新测速、不发布 NAS，不重做原计划已完成的任务。

## 1 目标、依据与当前状态

延续[原规格](2026-10-18-frontend-loading-optimization-design.md)及[原计划](../plans/2026-10-18-frontend-loading-optimization.md)：减少登录和房态、人员中心的加载成本，保持所有角色权限、业务行为、表单、房态筛选、评分及更新保护不变。

本补充只修改公共静态代码的构建分组，目的是减少常用路径上零散文件的请求，不将完整业务页面合为大包。它不假定减少文件数量必然减少可操作时间，也不声称能够消除全部网络排队或渲染等待。

- 当前产品树为 `e051b0579a80688d606cc62c47dad9655a8dc47d`，与试验前 `0e99e949af09a4c76ef210921a134c058bb0164a` 的整棵 tracked tree 相同；AppShell controlled-pending 试验已拒绝并撤回。
- 保留已完成的拆分及获准的两页静态准备，不重新引入被撤回的 AppShell 调度改动。
- 原正式性能比较仍为 40 组、每组 7 次。试验前版本为 31 组通过、9 组数值失败；被撤回试验为 29 组通过、11 组失败。保留两份结果，不替换基线、不把撤回认定为修复了原失败。
- 现有依赖图提示，下面两个精确分组可减少碎片；三个入口的额外静态 JS 联合闭包预计从 16 个文件降为 11 个。该数值是当前构建图推导，不是新产物或浏览器测速结果。

本次只读核对使用上述恢复版本的本地 `.build-metadata/{bundle-graph,vite-manifest,assets-manifest}.json`，而非把本地构建当作 NAS 产物。当前共有 191 个 JS chunks，匿名初始静态闭包为 11 个。图标候选分散在 5 个文件，合计原始 5,894 字节；两个日期文件合计原始 3,327 字节。这些是现有文件大小，不是未来合包大小、压缩传输量或新增流量承诺。

## 2 选定方案及取舍

采用两个小型、职责分离的公共包；不同时实施“当前页面优先预加载”、HTTP 协议改造或加载器重写。保留细分包并只改准备顺序是备选方向，不属于本候选。

| 分组 | 精确范围 | 取舍 |
| --- | --- | --- |
| 图标包 | 扩展已有 `authenticated-icons`，16 个纯图标叶模块增加为 21 个 | 减少零散图标请求；使用其中一个图标的页面可能同时下载其余这组图标，但不能带入业务组件 |
| 日期工具包 `common-date` | 仅 `src/shared/date.ts` 与 `src/teaching/datetime.ts` | 合并两个小工具块；不改变函数、格式、时区或日期规则，也不并入工作台／图标包强制所有登录用户下载 |

图标白名单完整清单：`download`、`filter`、`pencil`、`trash-2`、`activity`、`calendar-days`、`chevron-down`、`message-square-text`、`plane-takeoff`、`wallet-cards`、`mail`、`shield-check`、`sliders-horizontal`、`user-plus`、`user-round`、`x`、`clipboard-pen-line`、`gamepad-2`、`file-spreadsheet`、`landmark`、`refresh-cw`。只选择现有 `lucide-react/dist/esm/icons/` 中对应的模块。

使用项目锁定版本已经支持的精确构建分组。禁止整个 `lucide-react`／vendor／业务目录合包、全局最小块大小规则或递归吸收依赖。公共 helper、React、React DOM、认证 Context、QueryClient 和其他运行时仍按原结构共享，不能复制或移入新组造成循环依赖。

只读检查中，21 个图标叶仅调用现有 helper 建立组件，不包含业务请求、CSS 或 DOM 操作；两个日期模块仅声明／重导出函数和正则，没有顶层时间读取、网络或状态。当前匿名入口以及公开注册、激活、忘密等动态入口的静态闭包均不触达这两组。后续以真实新产物再验证这些边界，不能仅依赖本次人工观察。

不纳入 `HousingDialogShell`（具有模块状态和挂载副作用）、Housing／People API（业务函数及状态）、人员展示模块（目前已是单个文件）、CSS-owner JS、工作台里已经内联的其他图标。这些项目或有不同生命周期，或不能通过单独命名一个组进一步减少文件数；不会为了扩大合包而加入。

首轮只接受上述两个分组。若实际构建发现模块副作用、循环、CSS 归属变化或无法减少原有请求，保留证据并重新评估，不临时扩大白名单或通过修改业务导入关系凑出结果。

## 3 加载、授权和失败行为

登录匿名初始闭包不得因本次分组新增业务实现；财务、采购、资产、报表、评价、游戏及完整人员／房态页面继续保持原按需边界。代码文件本身不是授权边界，任何合包都不授予业务读取权限。

认证恢复、强制改密、角色重验、CSRF、退出及会话代次完全不变。现有人员页和房态页的静态准备时机、权限及 capability 条件不变；准备代码不挂载页面，不提前发起人员、房态或其他私有查询。换账号、撤权、离开页面后的迟到完成不能恢复旧界面或数据。

页面、工作台、可选面板和游戏仍沿用现有加载工厂与错误边界。复用原 JS 显式重试、CSS sticky 失败及用户主动更新提示；不自动刷新、注销、绕过 CSS gate 或重建认证／查询客户端。成功挂载后的工作台和表单身份保持稳定。

CSS 不纳入这两个组，不改样式内容、作用域或加载顺序。实际产物仍须证明共享样式归属正确，页面在样式完成前不会挂载或请求私有数据。新公共块下载失败时，受影响入口按原错误边界处理，不把网络错误包装成“无权限”。

构建检查扩展为：图标组恰为上述 21 叶，日期组恰为上述 2 模块；两组均不得包含 CSS、API 客户端、页面、业务查询或额外运行时。检查实际文件存在、静态依赖完整、无循环／重复运行时、匿名初始闭包不扩大，以及工作台／房态／人员静态闭包变化。

## 5 验收及失败处置

先验证产物，再运行已存在的浏览器与性能流程，不新造一套较宽松的性能标准：

1. 自动测试先证明精确分组要求在旧构建下未满足，再实现。覆盖未知模块、递归依赖、匿名闭包扩张、CSS 混入、缺失产物、静态循环及重复运行时等拒绝条件。
2. 运行相关测试、全量 Web 测试、TypeScript／生产构建、lint 和实际构建图检查；记录两个组及受影响角色路径的字节数、静态文件数和新增携带代码。必须实际减少目标路径的碎片文件，不以配置文本代替产物验证。
3. 冻结候选并独立复核。使用原生产浏览器回归确认授权／拒绝、样式、表单和房态筛选、首次／再次进入、公开入口及资源失败恢复。构建分组涉及的公共消费者也纳入现有对应回归，不只验证管理员页面。
4. 前项通过后，运行原 280 次正式性能协议：桌面 1440×900、手机 390×844，原慢网／CPU 与未限速对照，原 2 秒统计窗口、可操作判据、7 次样本、基线和 10% 门槛不变；不删慢样本、不重跑直到得到有利中位数。记录所有提前准备工作的实际下载和执行成本。
5. 登录冷启动 JavaScript 至少减少 40% 的目标保持不变。版本保护成本仅按用户已经明确批准且证据核实的范围另作说明；原数值结果不改写，不机械减去 150ms，也不豁免其他或混合来源的等待。
6. 若候选未改善目标路径或引入回退，保留所有结果，撤回本候选或提出有证据的设计调整；不得继续无边界试改。先前任务的纠错次数与未解决发现保留，不借本补充重新开启旧纠错循环。
