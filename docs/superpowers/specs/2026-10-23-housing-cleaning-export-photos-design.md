# 房态保洁、筛选导出及房间照片设计

日期：2026-10-23（中国时间）

状态：2026-10-23 用户已确认规格及实施计划；产品实现、独立审查、整体验证和恢复演练已完成，标准脚本 NAS 发布成功。实际发布及数据保全证据见 `docs/superpowers/verification/2026-10-23-housing-care/task-7-browser-and-restore.md`；不将浏览器触屏模拟等同真机验收。

## 1. 目标与确认边界

行政、管理员及超级管理员需要在现有房态内管理每间房的每日保洁安排、退房后的待保洁状态与照片，并按楼栋和房态导出当前台账。不新增独立保洁人员系统，不改变现有人员、账号、入住历史或房间容量。

用户明确要求：

- 每间房增加“是否每日保洁”的选项。
- 导出可选择已入住、未入住、待核对等状态及楼栋。
- 退房后显示待保洁，完成保洁前禁止新入住。
- 房间照片为可选项，有照片时允许 1–3 张；管理员和行政可删除或替换，超级管理员沿用管理能力。

用户在“多人间退一人也标记待保洁，现住客不受影响，仅暂停新入住”的建议后回复“开始吧”，本规格按该规则展开。

以下配套设计随本书面规格一并确认：调房迁出也触发原房待保洁；每日保洁仅为房间服务选项，不自动每天生成待保洁；保留原历史入住导出，另增当前房态导出；旧房间不追溯触发保洁。

## 2. 方案与取舍

采用“独立房间保洁状态 + 现有房态权限 + 独立照片记录”。是否每日保洁与当前是否待保洁是两个独立概念：前者表示安排，后者决定当前能否新增入住。

不把待保洁塞入现有正常、问题房、维修中、停用这组服务状态。否则清洁完成容易错误解除维修或问题状态，也无法准确表达“有人住、维修中且待保洁”。

不引入床位级保洁任务或保洁排班系统。当前用户按房间管理，本版按整房阻止补住；若以后需要分别放行已清洁床位，再另行设计床位模型。

## 3. 保洁业务规则

### 3.1 每日保洁选项

- 房间编辑增加“每日保洁：是／否”；新建及已有房间默认否，避免无依据认定已安排每日服务。
- 房态卡片、房间详情、当前房态导出显示该值，可按是／否筛选。
- 修改不重置结构核对状态，不改变入住、不清除待保洁、不覆盖维修或问题状态。
- 本版不生成每日打卡、不做每天清零或定时阻止入住，也不新增通知渠道。

### 3.2 待保洁生命周期

状态为 `ready`（无待保洁）及 `pending`（待保洁）。`ready` 只表示没有待处理阻断，不代表旧房间已发生有记录的保洁。

| 操作 | 原房保洁状态 | 对现有住客的影响 |
|---|---|---|
| 发起退房、尚未确认 | 保持 | 仍按现有待退房流程占用 |
| 正常确认一人退房，包括多人房 | 置为待保洁 | 其他住客仍在住 |
| 调房成功 | 原房置为待保洁；目标房须可入住 | 其他住客不变，调房链保持 |
| 取消从未入住的预约 | 保持 | 无保洁事实产生 |
| 修改计划入住／离开日期 | 保持 | 不腾床，不触发保洁 |
| 历史住宿作废 | 保持 | 不把历史纠错当作实际退房 |
| 管理员、行政或超管确认保洁完成 | 清除待保洁 | 不改变任何入住记录 |

当前实际办理的补记退房同样从操作时刻标记待保洁；不扫描历史记录自动补建任务。开启每日保洁不是退房待保洁的前提，每间住宿房均适用退房规则。

待保洁时，后端拒绝新建入住／预约、既有预约确认入住、调房迁入，返回明确中文说明“该房间待保洁，请完成保洁后再安排入住”。已有预约保留但不能绕过确认入住检查。退房、调出、取消预约及资料修改不因待保洁被阻止。

保洁完成只清除保洁阻断；房间仍需满足核对、启用、维修／问题、容量及性别等全部既有条件才能可入住。历史导入、人员详情安排入住及其他入口必须调用同一后端约束。

### 3.3 并发及版本

- 退房成功与原房置待保洁在同一事务，调房成功与原房置待保洁也在同一事务，失败整体回滚。
- 使用现有房间行锁与 `room.version`；保洁完成提交预期版本，锁后重新核验当前权限、版本及状态。
- 每次成功退房／迁出均递增房间版本，即使房间已经待保洁也递增。这样旧的“完成”请求不能清掉后来另一人退房产生的新待办。
- 完成先提交、随后退房：最终仍待保洁。退房先提交、旧完成请求后到：返回版本冲突，要求重新核对。
- 锁顺序兼容现有人员→房间（UUID 排序）→住宿；保洁及照片操作只锁必要房间，不反向锁人员。
- 不确定结果先刷新读取，不盲目重复写入。已完成的重复请求不增加第二次完成审计。

## 4. 权限和显示

每日保洁设置、完成保洁、照片上传／替换／删除须同时满足：当前实际角色属于 `admin`、`administration`、`super_admin` 之一，且具备目标房间现有 `housing.rooms.manage` 权限。保留楼栋／楼层范围及显式拒绝，不仅以前端菜单决定权限。不自动给其他岗位新增管理权。

房态管理内的照片读取沿用该房间的完整房态查看边界；仅拥有个人住宿、监护住宿或邀请人住宿摘要的用户，不因此获得完整房间详情、照片或室友信息的新入口。没有权限的图片请求不透露对象是否存在，原图不能公开直链访问。

概览新增“待保洁”统计及筛选；卡片同时显示入住状态、每日保洁和待保洁标签。现住人数大于零仍保持已入住红色，另加醒目的待保洁提示；空房待保洁不显示成绿色可入住。保洁完成按钮只对有权限者显示，点击确认当前房号后提交，无批量清空功能。

“待核对”是核对维度，“待保洁”是保洁维度，二者可同时存在。统计、筛选、调房候选及详情使用同一投影判定，包含移动端与人员详情入口。保留现有筛选持久化、切回页面不重置、身份切换清理缓存等行为。

操作写入中文可读审计：操作人、目标房间、变化及操作时间。用户页面日期仍按现有年月日规范，审计保留小时分钟。不写入照片二进制、完整证件、手机号或敏感导出内容到普通日志。

## 5. 导出

### 5.1 当前房态导出（新增）

导出弹窗提供“当前房态”和“入住记录（含历史）”两种明确类型，新界面默认当前房态。当前房态可选择：

- 楼栋：全部有权限楼栋，或多选指定楼栋；楼层选项只来自已选楼栋。
- 入住：全部／已入住／未入住，未入住指当前没有住客，不等于可入住。
- 核对：全部／已核对／待核对。
- 保洁：全部／待保洁／无待保洁；每日保洁全部／是／否。
- 可入住性、现有服务状态及房型筛选继续保留。

首次打开导出弹窗带入页面当前筛选，用户可在弹窗修改，不反过来重置页面。不同维度取交集，同一多选维度取并集，冲突组合允许为空并给出“没有符合条件的房间”，不自动扩大导出范围。

以房间为主表，每个匹配房间至少一行：空房人员字段留空；多人房按当前住客每人一行重复房间信息。只关联当前有效 `checked_in`、`checkout_pending` 住宿，不夹带以前退房者；预约不冒充已入住。

列为楼栋、楼层、房号、房型、床位数、当前入住人数、入住状态、核对状态、服务状态、是否可入住、每日保洁、保洁状态、入住人、性别、证件号、手机号、实际入住日期、计划离开日期、人员类型、账号状态、档案来源。长期居住的计划离开日期留空；房间照片不嵌入表格，也不提供绕过鉴权的链接。

支持现有 XLSX／CSV，保留导出用途必填、敏感导出权限、范围校验、导出审计、公式注入防护和有效住宿定义。对多次数据库查询使用同一一致性快照及 `as_of`，不让人数与人员清单来自不同并发时刻。输出范围是全部匹配的有权限房间，不仅当前页；沿用合理的资源限额和失败提示。

### 5.2 兼容原导出

现有 `/housing/exports` 的旧请求保持原默认逻辑与字段：按选中房间输出有效当前及历史入住。不得把旧调用静默改为仅当前人员。新增快照采用独立 `POST /api/v1/housing/room-status/exports` 端点，接受独立的多栋及保洁筛选请求；历史类型仍可选择既有楼栋／房间状态筛选，并明确这些筛选是当前房间状态，而非历史时点状态。

不改变实名报送批次、已生成快照或已下载的文件。不借本次功能导出已作废住宿，不扩张原敏感信息权限。

## 6. 房间照片

- 可不上传；上传后每房最多 3 张。详情显示 3 个图片位置，支持放大、逐张替换或删除。概览仅显示图片标记或小缩略图，不自动加载全部原图。
- JPEG、PNG、WebP，单张原始上传上限 10 MiB，限制实际解码像素数；按真实文件内容校验，不只看扩展名。其他格式明确提示转换，不声称支持尚未接入的 HEIC。
- 图片按正确方向重新编码并去除位置等 EXIF 元数据，生成受控缩略图；失败保持旧照片，不先删后传。展示提示不要上传证件或他人隐私照片。
- 数据库单独照片表关联稳定房间 UUID，位置限定 1–3，并约束同房位置唯一。原图及缩略图独立延迟加载，概览／导出只查询元信息。
- 沿用现有资产照片的数据库持久化思路，纳入既有加密数据库备份与恢复，不依赖飞牛特有目录，也不只存在浏览器或 Docker 临时层。
- 上传、替换、删除锁目标房间并检查照片版本／目标位置，避免并发超过三张或覆盖别人刚替换的照片。图片接口重新鉴权、CSRF 保护、禁止共享缓存及 MIME 嗅探。
- 首版只在完整房态管理详情中查看照片，不扩展邀请人摘要、个人住宿门户和公开分享。房间照片没有人物身份匹配或自动识别功能。

## 7. 数据迁移与实现边界

在当前实际迁移头之后追加迁移，不重写旧迁移。房间增加每日保洁布尔值、保洁状态、最近待保洁发生时间、最近完成时间及操作者等必要字段；保持现有房间版本、服务状态、核对、人员及住宿关系。连续事件由审计留存，不用“最近一次”字段替代历史审计。

已有房间初始化为每日保洁否、无待保洁，时间与操作者为空；不伪造一次保洁完成，不回放所有旧退房，更不修改最近导入的人员和房号。照片初始零张。

新增规则拆分为保洁服务和照片服务，复用房间鉴权与锁；入住服务只接入触发及可入住检查，不把图片处理并入入住事务。当前房态导出与旧历史导出分别承担各自语义，共享筛选和授权投影。

主要触及 `apps/api/app/housing/`、照片校验的可复用基础能力、审计动作映射、数据库迁移及 `apps/web/src/housing/`。不顺带修改其他业务，不清理工作区已有改动，不对真实人员做测试退房。

## 8. 验收与发布

1. 单人房退房、多房间调房、多人房退一人、已待保洁房再退一人均正确置待保洁，现住客及调房链保留。
2. 所有新入住、预约确认、调入入口不能绕过待保洁；从待保洁房退房／调出可正常办理；修复或保洁不能意外解除另一种阻断。
3. 完成保洁与退房／入住的独立数据库连接并发测试证明版本和锁有效；失败时住宿、房态及审计一并回滚。
4. 管理员、行政、超管及多角色／受限楼栋／显式拒绝／权限撤销场景通过；未授权图片及写操作拒绝；旧个人和邀请人摘要范围不扩大。
5. 导出覆盖空房、多人房、待核对、待保洁、多栋、空结果及跨页，人数与人员一致；当前导出不含历史，旧导出和实名报送回归不变。
6. 照片 0–3 张、第四张拒绝、并发新增、替换失败保留旧图、删除及撤权后的访问、超大／假格式／损坏图片均有验证。桌面及手机可操作，列表不批量载入原图。
7. 验证旧房间初始化不改变可入住结果、原人员与住宿，照片及保洁数据可经现有备份恢复；有损降级不得静默丢弃照片或保洁事实。
8. 产品实现后通过适用后端、前端、类型和真实浏览器回归，再按仓库要求运行 `scripts/deploy-nas.sh`；不得跳过备份或迁移预检。失败即报告发布阻断，不绕过脚本直接复制代码。
9. 上线仅用非破坏性读检查和授权的测试数据验收，不改变任何真实住客状态。界面检查、测试通过、部署成功各自记录证据，不混作完成声明。
