# 邀请人及组织查看受邀人员住宿

日期：2026-10-10（中国时间）

状态：用户于 2026-10-10 确认书面规格；进入实施计划审核，尚未为本功能修改业务代码或发布 NAS。

## 1. 目标与已确认内容

邀请人能查看自己邀请人员的住宿情况；组织通过超管指定的负责人查看本组织邀请人员。邀请方无须取得住房管理或财务权限。

用户已确认：

- 展示住宿状态、楼栋房号、入住日期、离开日期。
- 仅查询，不允许安排入住、调房或退房。
- 不展示室友、身份证和手机号。
- 超管可为一个组织指定一个或多个负责人；负责人各自使用现有 ERP 账号，不创建共享组织账号。
- 移除负责人后立即撤销对应组织的读取授权。

本规格补充的默认规则，随本文件一起确认：

- “受邀人员”指已完成注册、已写入 `StudentReferralBinding` 的学员，不含待审批或待验证的申请，不扩展多级邀请链。
- 只提供当前住宿摘要及必要的最近一次退房信息，不开放完整住宿历史、导出、支付记录或分成金额。
- 负责人可关联多个组织；只能在自己当前负责的组织之间切换。
- 停用邀请码不抹去既有邀请关系，因此不单独撤销历史受邀人员的查看权；停用组织、移除负责人或禁用负责人账号会停止该组织授权。
- 独立“我的邀请”入口不取代原有“我的分成”，也不改变邀请二维码生成权限。

## 2. 现状与方案选择

现有邀请归属已记录个人或机构来源快照，能作为行级范围的权威数据。机构目前只有名称、启用状态和审计操作人，没有负责人登录映射。`created_by_user_id` 不能作为机构所有权依据。

现有个人住宿门户仅面向本人/监护关系，还会查询和返回室友姓名；全量房态接口按楼栋/楼层授权。两者都不能直接开放给邀请方。

采用独立邀请住宿查询：复用已有邀请归属、住宿记录、日期语义和审计机制，增加组织负责人映射、独立只读权限及白名单响应。

不采用给邀请人授予全局房态权限的方案，避免看到无关联住客；不采用共享组织账号，保留每个实际操作人的身份、撤权与审计能力。代价是新增一个关联表和查询入口，不改动既有住宿及分成主流程。

## 3. 页面及使用流程

### 3.1 我的邀请

新增个人入口“我的邀请”，页面路径 `/me/invitations`，采用门户 capability 控制菜单和路由。存在本人邀请码、本人来源的既有邀请关系或有效组织负责人关联，且读取权限允许时才显示入口；无上述来源的账号不显示。

- 来源可选“我邀请的”及当前有效负责组织；只返回有权访问的来源，不列举其他组织。
- 列表显示姓名、昵称（有则显示）、邀请来源、住宿状态、楼栋/楼层/房号以及明确标注的计划和实际入住/离开日期。
- 日期按中国时间显示 `YYYY-MM-DD`，不显示小时分钟；计划日期缺失显示“未确定”，长期入住显示“长期入住”。未发生的实际入住/离开日期显示“—”并通过状态说明未入住/未退房，不虚构实际时间。
- 支持住宿状态筛选和分页，默认每页 20 人，上限 100；总人数、页数和筛选均在授权范围内计算。
- 暂无受邀人员显示空列表；已授权人员暂无住宿安排显示“未安排住宿”，两者不可混淆。
- 桌面采用表格，手机使用适合窄屏的列表或卡片；无安排入住、调房、退房、实名导出按钮。
- 可从原“我的分成”邀请区增加跳转链接，但新的独立页面不请求财务接口，也不授予分成权限。

### 3.2 超管配置负责人

在现有“邀请与分成管理”的机构区域增加“查看负责人”及“添加/移除负责人”。只允许真实 `super_admin` 角色并满足 `revenue_share.manage` 全局权限的账号操作；普通管理员、财务和负责人本人均不能通过直接调用接口修改负责人。

候选人为未删除、可用的现有登录账号；搜索/展示仅提供选择所需的姓名、昵称、账号标识，不返回身份证、手机号或邮箱。不要求被选账号具有财务或工作人员角色。

添加同一负责人不重复创建映射；移除操作需明确确认机构和人员。变更均记录操作人、组织、变更对象及时间。只修改负责人关联，不改变受邀学员的邀请归属和结算受益人。

## 4. 授权规则

新增独立读取权限 `referrals.read_invited_housing`，作为可单独禁止的功能开关，标准角色默认获得 `self` 范围。此权限本身不能产生任何受邀人员范围。

每次请求从数据库重新计算可访问来源：

1. 个人来源：绑定快照的 `source_kind=person` 且 `referrer_person_id` 等于当前认证人员。
2. 组织来源：绑定快照的 `source_kind=organization`，且当前账号具有该启用组织的有效负责人关联。
3. 结果只能是上述范围的并集，并排除已删除人员；不根据邀请码字符串、机构名称、客户端提交的人员列表或创建机构的操作人放行。

RBAC 必须与关系范围同时满足：

- 功能检查使用当前操作者的 `self` 和全局资源标记；显式禁止优先。
- 对已经通过关系筛选的人员再应用 `person` 范围的显式禁止，禁止单个被邀请人时列表与计数均排除。
- 即便账号获得该权限的 global/person allow，也不能扩大邀请关系确定的范围。本人门户、监护人门户和全量房态权限维持原规则。
- `invitations_available` 仅用于菜单和页面准入，不能代替查询时的关系及权限校验。负责人暂时没有受邀人员时允许进入空列表。
- 请求其他组织/人员时使用不暴露存在性的私有 404；未登录及整项功能被禁止按既有认证/授权约定处理。

移除负责人提交后，所有后续读取请求立即重新判定，旧会话和缓存不能授权。前端在退出登录、账号切换、页面重获焦点、来源切换及权限错误时清除旧数据；显示页面定期重新校验（最长 30 秒），失败时不继续展示过期私有列表。

“立即撤权”指变更提交后不再允许新读取。已经发送到其他设备屏幕的数据无法追溯收回，不承诺在断网设备上瞬间消失。

## 5. 住宿状态口径

一个人员的摘要按以下优先级选择，不将调房结束的旧记录误判为当前退房：

| 条件 | 展示 |
| --- | --- |
| 有 `checked_in` 当前记录 | 已入住，展示当前楼栋房号和实际入住日期 |
| 有 `checkout_pending` 当前记录 | 待确认退房，保留当前房号；不显示为已退房 |
| 无当前入住、有有效 `planned` | 已预约；计划入住日期已到但尚未确认时为待确认入住 |
| 无当前入住及有效预约、有已结束的真实入住 | 已退房，展示最近一次实际入住/离开日期及当时房号 |
| 从未安排，或仅存在取消的预约 | 未安排住宿 |

当前住宿优先于下一次预约；若同时存在预约，作为单独的下一次计划展示，不能覆盖当前房号。多条预约取计划入住时间最早者，同时间以稳定 ID 排序。最近退房按实际退房时间取最新记录，不以最后修改时间决定。

到达计划离开日期不等于实际离开，沿用现有待确认退房机制。计划日期和实际日期须分开标注；长期入住或缺失日期保留原始含义。查询发现异常的多个当前入住记录时安全报错，不任选一条形成错误状态。

## 6. 数据、接口与性能边界

- 增加机构负责人关联表，关联现有机构与 `user_accounts`，约束同一机构/账号不出现重复有效映射，保存授权和撤销信息；变更历史进入现有审计。
- 不将现有机构创建人自动提升为负责人。迁移后机构初始没有负责人，需要超管明确指定。
- 新增邀请住宿访问服务、分页查询接口、独立 DTO；接口只返回授权人员的必要标识、姓名/昵称、来源及住宿摘要。不返回室友数组、联系方式、证件、住宿备注、完整人员档案或财务字段。
- 负责人读取/增删及候选账号查询使用超管专用授权；写操作遵循现有 CSRF、事务和审计机制，并在事务内重新校验操作人权限和目标状态。
- 批量查询当前页人员的住宿和来源，不逐人查询；邀请来源、负责人映射及住宿查询需要的索引随迁移补齐。分页和汇总以权限过滤后的人员为准。
- 私有查询使用禁止存储缓存的响应策略，前端查询键隔离账号、来源、筛选和分页。不把住宿列表写入持久化浏览器存储。
- 复用既有读取审计：记录查看人、时间、查询范围/动作，不在错误日志中记录证件、联系方式、住宿备注或整个响应。

主要涉及现有 `revenue_share` 邀请模型/管理页面、独立邀请查询模块、`housing` 只读摘要、RBAC、门户 capability、菜单/路由及对应测试。不会扩大既有全量房态接口权限。

## 7. 验收与发布

自动化验收覆盖：

1. A 邀请人仅能查看 A 的受邀人员，不能通过人员 ID、组织 ID、来源筛选、分页或总数看到 B 的数据。
2. 一个组织多个负责人、一个负责人多个组织正确隔离；机构创建人未被指定时没有查看权。
3. 没有分成权限的学员/注册用户成为负责人后能看邀请住宿，但仍不能访问财务接口。
4. 普通管理员/财务/负责人不能添加或移除负责人；超管可操作且有中文审计记录。
5. 移除映射、禁用账号、停用组织及显式禁止后，旧登录状态和旧来源参数无法继续读取；前端焦点刷新、账号切换和过期响应不能恢复旧数据。
6. 邀请码停用保留已建立邀请关系；未完成注册不被错误计入。取消、预约、待入住、入住、待退房、退房、长期入住和调房状态正确，日期使用中国时间。
7. 响应严格排除室友、证件、手机号、邮箱、备注和财务信息；不影响原本人/监护人住宿功能。
8. 列表分页/人数/筛选在授权之后计算，查询数量不随当前页人数线性增长；新表迁移不改变旧邀请归属与分成数据。
9. 桌面及移动视口浏览器验收，未授权状态无菜单/操作入口且后端独立拒绝。

通过适用后端、前端、迁移、静态检查及浏览器验收后，必须从主仓库运行 `scripts/deploy-nas.sh --source <当前发布源>`，执行迁移前备份、健康检查和加密备份隔离恢复。部署失败视为发布阻断，不绕过脚本。
